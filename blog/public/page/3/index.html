二、核心设计：复用会话抽象

为什么群聊几乎不用新写消息逻辑

M2 已经建立了：

所以群聊 = Type=2 的会话 + groups 表（群元信息）。

  • 群消息发送：直接复用 chatservice.SendMessage（它只认 conversation_id）
  • 群消息推送：直接复用 ws.PushMessage（它查会话所有成员并逐个推送）

M3 新增的只有「群的生命周期管理」：建群、拉人、踢人、改资料、解散。

这就是好的抽象的价值：M2 多花一点心思设计会话+成员+消息，M3 就几乎免费。

三、数据模型

groups 表

字段 说明
conversation_id 关联会话（唯一）
owner_id 群主
name 群名称
avatar 群头像
announcement 群公告
member_count 冗余人数（列表展示）
max_members 人数上限（默认 200）
status 1 正常 / 2 已解散

为什么 member_count 要冗余

群列表/群详情要显示”多少人”。如果不冗余，每次都要 COUNT(*) FROM conversation_members WHERE conversation_id=?。
加人/踢人时同步更新 member_count（用 gorm.Expr("member_count + ?") 原子自增，避免并发覆盖）。

四、建群：为什么必须是事务

建群要做 4 件事：

  1. 创建 conversations（Type=2）
  2. 创建 groups（关联 conversation_id）
  3. 插入群主到 conversation_members（Role=1）
  4. 插入其他成员

任何一步失败，不做事务就会产生脏数据：

  • 有会话没群 → 会话列表出现一个没有名字的会话
  • 有群没会话 → 群消息发不出去
  • 有群没群主 → 群没人能管理

面试点：事务边界 = 一个完整业务语义。建群是一个业务动作，必须原子。

五、成员管理的权限规则

操作 谁可以
拉人进群 任何群成员（类微信）
踢人 只有群主
退群 任何成员（群主不能直接退）
改群名/公告 只有群主
解散群 只有群主

权限校验的统一套路：

群主不能直接退群

如果群主退了，群就没人管了。正确做法：

  • 转让群主（M3 简化未做，M4 可加）
  • 或者先解散群

六、人数上限与并发

上限校验

并发安全

两个请求同时拉人，可能都通过上限校验 → 超员。
M3 用 gorm.Expr 原子自增保证计数不丢，但上限校验仍有竞态。

彻底解决（M4）：

  • 事务里 SELECT ... FOR UPDATE 锁群行
  • 或用 Redis 分布式锁
  • 或不严格限制（超一点可接受）

面试点：乐观 vs 悲观。计数用原子表达式是乐观；上限校验加行锁是悲观。

七、踢人/退群：为什么要事务

踢人要：

  1. 删除 conversation_members 里的一行
  2. member_count - 1

不是事务的话，删了成员但人数没减 → 群人数显示错误。

八、解散群

为什么保留数据：群消息、群记录保留，便于审计/追溯。

软删除 vs 物理删除：IM 的群、消息一般软删（合规/回溯），个人数据可以用物理删（如黑名单）。

九、群消息：复用 M2

群消息的发送和推送完全复用 M2：

唯一要担心的：群成员多时（比如 200 人），一次消息要推 200 次。

  • M3 是同步循环推
  • M4 会讨论「扇出放大」问题（可以用 goroutine 池、MQ 异步）

二、数据模型：会话 + 消息 + 成员

2.1 为什么单聊和群聊共用一张会话表

  • 单聊：Type=1，两个成员
  • 群聊：Type=2，多个成员（M3 复用同一套表）

好处：消息表不需要区分单聊/群聊，统一按 conversation_id 查。

2.2 为什么会话冗余最后消息

conversations.last_message_id / last_message_at

如果会话列表要展示”最后一条消息”，每次都去 messages 按 conversation_id 查最新一条，数据量大时很慢。
把最后消息信息冗余到会话行 → 列表查询变成一次简单查询（空间换时间）。

2.3 未读数怎么算

conversation_members.last_read_message_id 记录”我读到哪了”。

标记已读 = 更新 last_read_message_id（只前进不后退）。

比单独建 message_reads 表简单，M2 先用这个方案。

三、消息幂等（重点）

问题

网络重试、用户连点、WS 重发都会导致同一条逻辑消息被发送多次。

方案：客户端生成唯一 client_msg_id

服务端处理：

  1. 先查 (sender_id, client_msg_id) 是否已存在 → 存在直接返回（重复请求返回同一条）
  2. 不存在 → 插入
  3. 并发下两个请求同时插入 → 唯一索引让第二个报 Duplicate
  4. 捕获 gorm.ErrDuplicatedKey → 再查一次返回已有消息

结果：无论客户端重试多少次，数据库里只有一条消息。

配套：TranslateError: true

GORM 配置里开启 TranslateError，把 MySQL 的 Duplicate entry 错误翻译成 gorm.ErrDuplicatedKey，
这样业务代码用 errors.Is(err, gorm.ErrDuplicatedKey) 判断，不用匹配错误字符串。

四、分页：为什么用游标不用 offset

返回时把倒序结果翻转成正序，前端直接渲染。

五、WebSocket 架构（M2 最核心）

5.1 三个角色

5.2 为什么读写分离

gorilla/websocket 不允许并发写。如果多个 goroutine 同时写同一个连接会 panic。
所以：

  • ReadPump：唯一从 socket 读的 goroutine
  • WritePump：唯一往 socket 写的 goroutine
  • 其他 goroutine 想发消息 = 往 Client.send channel 里塞数据

5.3 Hub 的并发安全

  • Hub 被「连接建立/断开」和「消息推送」多个 goroutine 同时访问 → 必须加锁
  • 读写锁：读多写少，比 Mutex 性能好
  • SendToUser 里先把连接列表复制出来，再释放锁发送，避免持锁做 IO

5.4 心跳机制

作用：清理「网线拔了但 TCP 没断」的僵尸连接。

5.5 慢消费者隔离

如果客户端很慢，send channel 满了，直接阻塞会拖垮推送方（可能是给其他用户推消息的 goroutine）。
用 non-blocking 写 + 断开慢连接，保证一个慢客户端不影响其他人。

这是消息系统「慢消费者」问题的通用解法（Kafka/RabbitMQ 里也有类似思路）。

5.6 推送路径统一

HTTP 发消息 和 WS 发消息，最终都要「推送给会话所有在线成员」。
所以抽出 ws.PushMessage(convID, item)：

  • HTTP handler 发完消息调用
  • WS 的 handleText 发完消息也调用

为什么放 ws 包而不是 service：service 不应该依赖 WebSocket（M6 拆 gRPC 时没有 WS）。

六、鉴权：WS 怎么带 token

浏览器 WebSocket API 不能自定义请求头（不能带 Authorization）。
所以：

服务端在升级连接之前先校验 token，非法直接 401，不浪费连接资源。
（同时兼容非浏览器客户端的 Authorization: Bearer。）

七、在线状态与离线消息

在线状态

  • Hub 里 IsOnline(userID) 判断是否在线
  • 接口：GET /api/v1/online?ids=1,2,3 → {"online_ids":[1]}

M2 是单机内存；M4/M6 多实例要改成 Redis（每个实例写入在线用户 + TTL 续期）。

离线消息

不需要单独的表：

  • 消息已经落库到 messages
  • 用户上线后通过 GET /conversations/:id/messages 拉历史
  • 通过 unread 计数知道有多少没读

这就是”离线消息”的标准做法：持久化 + 上线拉取 + 未读数。

九、注意点清单

  1. gorilla/websocket 不能并发写 → 写操作只在 WritePump
  2. WS 的 ctx 用 context.Background()：连接生命周期远长于 HTTP 请求
  3. Hub 持锁时不要做 IO/channel 操作 → 先复制连接列表再发
  4. 慢消费者要断开，不能阻塞推送方
  5. WS 鉴权在 Upgrade 之前，别升级完再校验
  6. CheckOrigin 生产环境必须校验，否则有 CSWSH 跨站 WebSocket 劫持
  7. 消息 ID 用自增：单库单表够用；分库分表时要用雪花算法/号段
  8. 未读数是 N 次 count，会话多时要优化（Redis 计数）
  9. 游标分页不要用 offset
  10. client_msg_id 必须由客户端生成，服务端不能自己造（否则重试无法幂等）

二、分层架构

关键原则：

  1. Handler 不写业务：只做「解析 → 调 service → 写响应」。
  2. Service 是事务边界：一个业务动作涉及多表时，事务写在 service。
  3. Handler 用 *gin.Context，Service 用 context.Context：
    • 解耦：service 不依赖 gin，M6 拆 gRPC 时不用改
    • 可测试：单测 service 不用构造 gin.Context
    • 衔接：c.Request.Context()

三、数据库设计（6 张表）

表 作用 关键约束
users 用户主体 username 唯一；phone/email 可空唯一
user_settings 隐私/通知设置（1:1） user_id 唯一
friend_requests 好友申请 UNIQUE(from_user_id,to_user_id) + INDEX(to_user_id,status)
friendships 好友关系（双向两行） UNIQUE(user_id,friend_id)
friend_groups 好友分组 UNIQUE(user_id,name)
blacklist 黑名单 UNIQUE(user_id,blocked_user_id)

设计决策 1：好友关系存「双向两行」

A、B 成为好友后，插 (A,B) 和 (B,A) 两行。

  • ✅ 「查我的好友」只需 WHERE user_id=?，不用 OR、不用排序
  • ✅ 每行可以独立存「备注、分组、星标」（A 备注 B ≠ B 备注 A）
  • ❌ 写入要写两行 → 必须用事务

设计决策 2：软删除

  • friendships.status：1 正常 / 2 已删除
  • friend_requests.status：0 待处理 / 1 已接受 / 2 已拒绝

软删除保留历史，便于审计和”重新加好友”时恢复。

设计决策 3：可空字段用指针

Phone *string、Birthday *time.Time：区分「没填」和「填了空值」。
配合 MySQL 唯一索引「允许多个 NULL」，多个用户可以都不填手机号。

四、认证：双 Token 无感刷新（重点）

4.1 为什么需要双 token

单 token 双 token
有效期长 体验好，但泄露风险大、无法撤销 —
有效期短 安全，但频繁掉登录 —
双 token — access 短（2h）+ refresh 长（30d），体验和安全兼得
  • access token：2 小时，每个请求携带
  • refresh token：30 天，只用来换新 access
  • refresh 的 jti 存 Redis：让无状态 JWT 可以「撤销」

4.2 全流程

4.3 关键设计点

① 为什么用 GETDEL 原子消费？

Exists + Del 是两步，中间有时间窗口，并发下两个请求都可能通过 → 都签发新 token（rotation 失效）。
GETDEL 把「取 + 删」合成一个原子操作 → 只有一个请求能成功。

② rotation（轮换）

每次刷新都签发新 refresh，旧的作废。这样被盗的 refresh 只能用一次，且会触发复用检测。

③ 复用检测

旧 jti 不存在（被消费/已撤销）却仍被使用 → 可能是盗用 → 撤销该用户所有 refresh（强制全设备下线）。
代价：客户端并发刷新会被误判。所以客户端要做 single-flight（刷新单飞）。

④ 用户不存在/禁用时也要撤销

刷新时查用户，若用户被删/禁用 → DeleteAllRefreshJtiinRedis，避免”已删除用户的 token 还能用”。

4.4 为什么 Parse 里必须校验算法

不校验会有 算法混淆攻击：

  • alg=none：攻击者把算法改成 none、签名留空，某些库会直接放行
  • HS256/RS256 混淆：用服务端公开的 RSA 公钥当 HMAC 密钥签名，骗过服务端

五、好友模块

5.1 发好友申请要拦哪些情况

  1. 不能加自己
  2. 目标用户必须存在
  3. 不能已是好友
  4. 不能重复发「待处理」申请（已拒绝的可以重发）
  5. 对方拉黑了我 → 拒绝（且用模糊提示，不暴露”你被拉黑”）
  6. 对方关闭了「允许加好友」

这些「先查后写」的检查只是为了友好提示，并发兜底靠数据库唯一索引。

5.2 接受申请为什么必须用事务

一次接受要做两件事：

  1. 把申请状态改成「已接受」
  2. 插入两条好友关系（A→B、B→A）

不用事务的后果：

  • 改了状态但插好友失败 → 申请显示已通过，但还不是好友（数据不一致）
  • 插了好友但状态没改 → 可以重复接受，重复插入

5.3 用「条件更新 + RowsAffected」抗并发

  • WHERE ... AND status=0 让「判断」和「修改」成为一个原子操作
  • 影响行数 = 0 → 被别人抢先处理 / 不是发给我的 / 不存在
  • 天然抗「双击」「重试」「并发接受」

5.4 软删除 + 唯一索引的坑

两个真实踩过的坑（都在代码里修了）：

坑 1：删除好友后重新加，INSERT 撞唯一索引

friendships 有 UNIQUE(user_id, friend_id)，删除只是把 status 改成 2，行还在。
再次加好友时直接 INSERT → 撞唯一索引失败。

解法：upsertFriendship() 先 Unscoped() 查（含软删行），存在就恢复 status=1，不存在才插入。

坑 2：重新发好友申请失败

friend_requests 有 UNIQUE(from_user_id, to_user_id)，同一对用户只能有一行。
第二次发申请直接 INSERT → 撞唯一索引。

解法：先查旧行，存在就复用（重置 status=0、更新 message），不存在才插入。

面试点：软删除 + 唯一索引天然冲突。要么复用旧行、要么把唯一索引加上删除标记列、要么对这类”开关型”数据用物理删除（如黑名单）。

七、注意点清单（本项目真实踩过的坑）

  1. GORM 的 First 返回 *gorm.DB，不是 (值, error)：用 .Error 取错误
  2. if err != nil 分支必须处理 err：不要 return nil（吞错误）
  3. GORM 零值陷阱：结构体零值字段会被忽略 → 部分更新用指针 / map / Select
  4. gorm.Model.ID 是 uint，JWT claims 是 uint64，注意转换
  5. 双指针：var u *User; DB.First(&u) 是 **User，应 var u User; DB.First(&u)
  6. c.Get("key") 的 key 必须和 c.Set 一致，用常量防手滑
  7. GetUint vs GetUint64：类型不匹配返回 0，不报错（极难查）
  8. c.Abort() 后要 return，否则当前函数继续执行
  9. soft delete + 唯一索引：重新创建会撞索引，要复用/恢复旧行
  10. N+1 查询：批量 ID 用 IN 一次查，别循环查

  1. 为什么用双 token？access 和 refresh 分别解决什么问题？

  3. JWT 有哪些安全风险？alg=none / 算法混淆怎么防？
  4. JWT 无状态，怎么实现”登出”和”撤销”？→ jti + Redis 白名单
  5. refresh rotation 是什么？为什么需要？并发刷新怎么办？
  6. 为什么用 GETDEL 而不是 Exists + Del？
  7. 为什么密码用 bcrypt 而不是 MD5/SHA256？cost 多少合适？
  8. 好友关系为什么存两行？代价是什么？
  9. 接受好友申请为什么必须用事务？
  10. 如何防止并发重复接受？→ 条件更新 + RowsAffected

九、最佳实践总结

实践 说明
分层单向依赖 router → service → model
service 用 context.Context 解耦框架、可测试、可迁移 gRPC
统一响应格式 {code,message,data}，handler 用共享包
常量代替魔法字符串 context key、状态值

事务尽量短 不在事务里做网络/IO

批量查询防 N+1 IN 一次查
DTO 分离 自己看 vs 别人看 vs 设置，别用一个 struct 到处返回

学习路线图：这个项目该怎么学

上图由项目手绘 SVG 说明，配合下文阅读效果更好。

本目录是 gochat 项目的学习文档中心。代码在 gochat/，文档在 gochat-study/。
阅读顺序：本文 → 各里程碑文档 → 面试集 / 场景集 → 对照代码。

一、项目定位

gochat 是一个「仿微信」的即时通讯后端，用来练并发编程、微服务拆分、消息队列。

技术栈：

层 技术
Web 框架 Gin
ORM GORM + MySQL 8
缓存 Redis
鉴权 JWT 双 token（access + refresh）
实时通信 gorilla/websocket
语音 Pion WebRTC（信令服务）
消息队列 RabbitMQ
微服务 gRPC + protobuf
语言 Go 1.27
