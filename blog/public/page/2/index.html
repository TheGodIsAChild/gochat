M5 语音通话

WebRTC 语音通话实现

一、WebRTC 是 P2P 的

服务器不传音视频——这是 WebRTC 相比服务器混流的最大优势：延迟低、带宽成本低。

二、建立连接的三个步骤

  1. 交换 SDP
    • A 生成 offer（支持的编解码、网络信息）
    • B 返回 answer
  2. 交换 ICE candidate
    • 双方收集可能的网络路径
  3. P2P 打洞 / 中继
    • 能直连就直连，失败用 TURN 中继

STUN / TURN / ICE

概念 作用
ICE 框架：收集候选 + 按优先级尝试连接
STUN 发现自己的公网 IP:Port（NAT 映射）
TURN 打洞失败时的中继服务器（有带宽成本）

三、服务器职责：信令状态机

状态迁移全部用条件更新：

连点接听、超时后接、已挂断再挂断，都会被拦住。

四、信令协议（WebSocket）

方向 type 说明
C→S call_invite 发起通话
C→S call_accept / call_reject / call_cancel / call_end 状态操作
C→S webrtc_offer / webrtc_answer / webrtc_ice 转发信令
S→C call_ack / call_incoming / call_accepted / call_rejected / call_canceled / call_ended 状态通知
S→C webrtc_offer / webrtc_answer / webrtc_ice 原样转发 + from_user_id

信令转发实现

服务器不解析 SDP，只加 from_user_id 原样转发——这就是信令服务器的本质。

M6-M7 分布式

微服务与消息队列

一、为什么要拆微服务

单体的问题：

痛点 单体 微服务
扩缩容 整包一起扩 按服务扩
故障隔离 一个模块 OOM 全挂 只挂一个
团队协作 一个仓库 按服务划分
部署 改一行全量发布 只发布改动的

代价：分布式复杂度（网络失败、一致性、服务发现、追踪）。

本项目先单体（M0–M5）跑通，M6 再拆——先体会痛点才知道为什么拆。

二、怎么拆：按领域，不按技术

本项目：

服务 职责 端口
user service 用户查询、批量查询 9001
chat service 发消息、拉历史 9002
gateway HTTP 入口 + 鉴权 + 限流 + 调 gRPC 8080

三、gRPC 核心知识

REST/JSON gRPC
传输 HTTP/1.1 HTTP/2（多路复用）
序列化 JSON protobuf（二进制、体积小）
契约 OpenAPI（可选） .proto 强契约
流式 弱 支持四种流

结论：对外 REST，内部服务间 gRPC。

本项目因环境没有 protoc，用 gRPC 的自定义 JSON codec 实现。
传输层仍是真 gRPC（HTTP/2、超时、状态码），换 protobuf 只需替换 codec 和生成代码，
架构不变——这说明微服务核心是「服务边界 + 契约」，不是序列化格式。

四、gateway 模式

gateway 负责：协议转换、统一鉴权、限流、聚合。
内部服务不直接对外，鉴权在入口做。

五、微服务带来的 5 个新问题

  1. 服务发现：怎么知道服务地址？（配置/Consul/Etcd/K8s）
  2. 超时重试：网络会失败，必须设超时，重试要幂等
  3. 熔断：下游持续失败时快速失败，防雪崩
  4. 链路追踪：跨服务请求要用 trace_id 串起来
  5. 数据一致性：跨服务不能用一个事务 → MQ/Saga/TCC

六、RabbitMQ：为什么需要

场景 不用 MQ 用 MQ
发消息后推送 请求里同步查成员+逐个推送 写 outbox，worker 异步推
群消息 200 人 请求耗时随人数增长 快速返回，后台慢慢推
流量高峰 直接打满 队列削峰
跨服务一致性 无法本地事务 最终一致性

七、核心：本地消息表（Transactional Outbox）

问题：落库和发 MQ 无法原子

  • 先落库后发 MQ：发 MQ 失败 → 消息丢失
  • 先发 MQ 后落库：落库失败 → 推了不存在的消息

解法：把「发 MQ」变成「写数据库」

关键洞察：写数据库是事务性的，发 MQ 不是。所以先记在数据库里，由后台可靠补发。

至少一次投递 → 消费幂等

worker 发 MQ 成功但标记失败 → 下次重复发。
消费方必须幂等（去重表/唯一索引/消息 id）。

本项目消费动作是「推送给在线用户」，重复推影响小；如果是加积分就必须严格去重。

八、可靠性设置

三项结合 = 至少一次。

九、降级设计

外部依赖要设计降级路径，不能因为 MQ 挂了整个聊天不可用。

十、踩过的坑

  • amqp.Table 的 value 不支持 uint，要转 int64
  • 事件契约要用中立的 struct，避免上下游循环依赖

仿微信前端与面试准备

一、前端技术选型

为了演示所有后端功能，实现了一个仿微信三栏布局的单页应用：

选型：原生 HTML/CSS/JS，由 Go 服务直接托管（r.Static）。
理由：零构建、零依赖、和后端同源（不用处理 CORS），演示最稳。

二、前端覆盖的功能

模块 功能
认证 登录/注册/登出、双 token 无感刷新（单飞）
会话 会话列表、未读数、在线状态
聊天 历史分页（滚轮上翻）、WebSocket 实时收发、已读标记
通讯录 好友列表、新朋友申请（接受/拒绝）、搜索加好友、备注、删除、拉黑
群聊 建群、群详情、成员列表、拉人、踢人、改资料、退群、解散
通话 通话记录、WebRTC 语音通话（呼叫/接听/拒绝/挂断/静音）
设置 资料修改、隐私开关、黑名单、退出登录

三、无感刷新的前端实现

单飞（single-flight）：并发 401 只发一次刷新请求，其他请求共享同一个 Promise。
否则 rotation 会让旧 refresh 被重复使用，触发服务端复用检测 → 用户被强制下线。

四、WebSocket 客户端要点

  1. token 走 query（浏览器 WS 不能带 header）
  2. 心跳 ping（25s），服务端 60s 无 pong 会踢连接
  3. 断线自动重连（指数退避，上限 15s）
  4. 事件分发：WS.on(type, handler)

五、WebRTC 通话（浏览器端）

  • localhost 是安全上下文 → HTTP 也能采集麦克风
  • 本机两窗口演示不需要 STUN（host candidate 直连）
  • 跨网演示需要 STUN/TURN

2. 挑 2–3 个亮点深入（不要全讲）

亮点 A：双 token 无感刷新（M1）

“access token 2 小时、refresh token 30 天。refresh 的 jti 存 Redis 白名单，登出就能撤销。
刷新时用 GETDEL 原子消费旧 jti，配合 rotation 防止 refresh 被重复使用。
如果旧 jti 不存在，判定为盗用，撤销该用户所有 refresh——这就是复用检测。”

亮点 B：消息幂等（M2）

“客户端为每条消息生成 client_msg_id，数据库有 UNIQUE(sender_id, client_msg_id)。
先查后插，并发插入撞唯一索引时捕获 gorm.ErrDuplicatedKey 再查一次返回。
这样无论重试多少次，库里只有一条消息。”

亮点 C：WebSocket 架构（M2）

“每个连接一个读 goroutine + 一个写 goroutine，因为 gorilla/websocket 不允许并发写。
Hub 用 RWMutex 管理 userID → 多连接（支持多端登录）。
心跳 ping/pong 清理僵尸连接，慢消费者有界队列满了就断开，避免拖垮推送方。”

亮点 D：接受好友申请事务（M1）

“接受申请要改状态 + 插两条好友关系，必须在一个事务里。
用条件更新 WHERE status=0 + RowsAffected 判断，天然抗并发重复接受。
还踩过软删除+唯一索引的坑：删除后再加好友会撞索引，所以用 Unscoped 查旧行然后恢复。”

亮点 E：Outbox 模式（M7）

“落库和发 MQ 无法原子。我在业务事务里同时写一条 outbox 记录，后台 worker 轮询发 MQ、标记已发送。
这样 MQ 挂了也不丢消息，消费方做幂等即可。MQ 不可用时降级为同步推送。”

场景集：30 个业务场景怎么实现

从项目里提炼的关键业务场景：问题 → 处理方案 → 代码位置 → 关键点。
用途：面试讲项目时按场景展开，或排查/扩展功能时对照。

M1 · 认证与好友

场景 1：用户注册

问题：注册要保证「用户名唯一」，并同时创建默认设置。

方案：

  1. 先查用户名是否已存在（友好提示）
  2. bcrypt 加密密码
  3. 事务：插入 users + user_settings

代码：internal/service/user_service/register_service.go

关键点：

  • 查重不是安全边界，唯一索引才是并发兜底
  • 密码永远不存明文，PasswordHash 字段 json:"-" 防泄露
  • 用户和设置必须成对出现 → 事务

场景 2：用户登录（签发双 token）

问题：登录成功要发 access + refresh 两个 token，并让 refresh 可撤销。

方案：

  1. 按 username 查用户，查不到 → 统一提示”用户名或密码错误”（防枚举）
  2. bcrypt 校验密码
  3. 检查账号禁用状态
  4. 签 access（2h，type=access）
  5. 签 refresh（30d，type=refresh，带 jti）
  6. SET refresh:{uid}:{jti} 1 EX 30d 存 Redis
  7. 更新 last_login_at（非关键，失败不影响登录）

代码：internal/service/user_service/login_service.go

关键点：

  • 不暴露”用户是否存在”
  • Redis TTL 必须与 refresh 的 exp 对齐
  • SaveRefresh 失败要整体失败（否则用户能登录但永远刷新不了）

场景 3：access token 过期 → 无感刷新

问题：access 2 小时过期，用户不能被踢下线。

方案（客户端拦截器驱动）：

  1. 请求返回 401
  2. 客户端用 refresh token 调 /token/refresh
  3. 服务端：验签 → type=refresh → GETDEL 消费旧 jti → rotation 签发新 token 对 → 存新 jti
  4. 客户端用新 access 重试原请求

代码：internal/service/user_service/refresh_service.go

关键点：

  • GETDEL 原子消费，防并发双签发
  • rotation：每次刷新换新 refresh，旧作废
  • 旧 jti 不存在 → 复用检测 → 撤销该用户全部 refresh

场景 4：并发刷新（5 个请求同时 401）

问题：客户端同时发多个 refresh，rotation 会让第二个请求用旧 token → 触发复用检测 → 用户被强制下线。

方案：

  1. 客户端 single-flight：刷新进行中，其他请求等待同一结果（治本）
  2. 服务端 GETDEL 防双签发
  3. 宽限期：消费 jti 时打一个 60s 的 used:{jti} 标记，宽限期内的重复请求不触发撤销
  4. （进阶）缓存「旧 jti → 新 token 对」实现幂等刷新

代码：internal/service/user_service/refresh_service.go（简化版）

关键点：

  • 这是双 token + rotation 的经典坑
  • 面试可以讲：problem → 为什么误判 → 三层解法

场景 5：登出

问题：JWT 无状态，怎么让 refresh 立即失效？

方案：客户端带 refresh token 调用 /logout，服务端解析出 jti 后 DEL refresh:{uid}:{jti}。
登出是幂等的（删不存在的 key 也算成功）。

一、Go 语言基础

⭐ 1. context.Context 是干什么的？

简答：用来在调用链上传递「取消信号、超时、请求范围的值」。
本项目里所有可能慢的操作（Redis、DB、下游调用）第一个参数都是 ctx，客户端断开时 c.Request.Context() 被取消，下游操作自动中止，避免资源浪费。

代码：internal/service/user_service/login_service.go（Login(ctx, ...)）、internal/auth/token_store.go

⭐ 2. *gin.Context 和 context.Context 有什么区别？为什么 service 用后者？

简答：

  • *gin.Context 是 HTTP 框架上下文（请求/响应/参数绑定/JSON 输出），只在 handler 层有意义。
  • context.Context 是标准库的通用上下文，用于取消/超时/传值。
  • service 用 context.Context 是为了解耦框架：M6 拆 gRPC 时 gRPC 里只有 context.Context，service 不用改；也方便单测。
  • 衔接方式：handler 里 c.Request.Context()。

代码：internal/router/user_router/user_api.go（传 c.Request.Context()）

⭐ 3. Go 的并发安全：哪些东西并发读写会出问题？

简答：

  • global.DB（GORM）和 global.Redis（go-redis）内部并发安全。
  • 普通 map 并发读写会直接 panic（fatal error: concurrent map read and map write）。
  • 业务层的「先查后写」不是原子的，需要唯一索引/事务/锁。

代码：M2 的 WebSocket 连接管理会用到 sync.Map / sync.RWMutex。

二、JWT 与认证

⭐⭐ 4. 为什么用双 token（access + refresh）？

简答：

  • access token 短命（2h），每个请求携带，泄露窗口小。
  • refresh token 长命（30d），只用于换新 access，且存在服务端（Redis）可撤销。
  • 用户只要 30 天内用过，refresh 自动续期 → 无感不掉登录。
  • 单 token 无法同时满足「安全」和「长期登录」。

代码：internal/auth/jwt.go、internal/service/user_service/login_service.go

⭐⭐ 5. JWT 的 payload 是加密的吗？能放什么？

简答：不是加密，只是 base64 编码，任何人都能解码。
signature（签名）只保证「没被篡改」，不保证「保密」。
所以只能放身份标识（user_id、username），绝不能放密码、身份证等敏感信息。

代码：internal/auth/jwt.go（Claims 只有 UserID/Username/Type）

⭐⭐ 6. JWT 有哪些安全风险？

简答：

  1. 算法混淆：alg=none 或 HS256↔RS256 混用 → 防法：校验 t.Method.(*jwt.SigningMethodHMAC)。
  2. payload 泄露：明文可读 → 不放敏感信息。
  3. 无法撤销：签出去就收不回 → 用 jti + 服务端白名单。
  4. 过期不短：泄露窗口大 → access 设短、refresh 长但可撤销。
  5. 密钥硬编码：→ 从配置读取。

代码：internal/auth/jwt.go 的 Parse() 里的算法校验

⭐⭐ 7. JWT 是无状态的，怎么实现登出/撤销？

简答：签发时给 refresh token 塞一个唯一 jti，并把 refresh:{userID}:{jti} 存 Redis（白名单）。
登出 = 删除该 jti；校验 = 查 Redis 是否还存在。
这样保留了 JWT 的无状态优势，又获得了「可撤销」能力。

代码：internal/auth/token_store.go、internal/router/user_router/user_api.go 的 Logout

⭐⭐ 8. refresh rotation 是什么？并发刷新怎么办？

简答：

  • rotation：每次刷新都签发新的 refresh，旧的作废。这样被盗的 refresh 只能用一次。
  • 并发刷新：多个请求同时用同一个 refresh → 只有第一个成功（GETDEL 原子消费），其余会触发「复用检测」→ 撤销全部。
  • 解决：① 客户端 single-flight（只发一次刷新，其他请求等待复用结果）；② 服务端用 GETDEL 防双签发 + 短 TTL 消费标记做宽限期；③ 更完善的是缓存「旧 jti → 新 token 对」实现幂等刷新。

代码：internal/service/user_service/refresh_service.go、internal/auth/token_store.go

⭐ 9. 为什么用 GETDEL 而不是 Exists + Del？

简答：Exists + Del 是两条命令，中间有时间窗口，并发下两个请求都可能通过检查然后都签发新 token，rotation 就失效了。
GETDEL 是 Redis 的原子命令（取+删一步完成），只有一个请求能拿到值。

⭐ 10. 为什么密码用 bcrypt 而不是 MD5/SHA256？

简答：

  • MD5/SHA256 是快速哈希，GPU 暴力破解极快；且相同密码哈希相同（彩虹表）。
  • bcrypt 故意慢（cost=10 约 50~100ms）+ 内置随机 salt：同一密码每次哈希都不同，破解成本极高。
  • 校验用 CompareHashAndPassword，从哈希里取出 salt 再算。

代码：internal/auth/password_util.go

⭐⭐ 12. GORM 部分更新的零值陷阱是什么？

简答：用结构体做 Updates 时，零值字段（""、0、false）会被 GORM 忽略。
后果：

  • 用户只想改昵称，传了 {nickname:"x"}，其余字段是零值 → 但如果你 Updates(req)，那些字段其实不会被更新（这算幸运）；
  • 更危险的是：想显式把某字段改成 0/空，GORM 会忽略，改不动。

解法（三选一）：

  1. 请求结构体用指针（*string、*bool）：nil=没传，非 nil=传了
  2. 用 map[string]any 组装，map 里 false/0/“” 不会被跳过
  3. 用 Select("field1","field2") 明确指定要更新的列

代码：internal/service/user_service/user_update_service.go

⭐ 13. 软删除和唯一索引为什么会冲突？怎么解？

简答：
软删除只是写 deleted_at/改 status，行还在，唯一索引依然生效。
所以「删除后重新创建同一条记录」会撞唯一索引。

  • 复用旧行：查 Unscoped()（含软删行），存在就恢复
  • 或对”开关型”数据用物理删除（如黑名单的拉黑/取消）
  • 或把删除标记列加进唯一索引（但恢复时要处理）

⭐ 15. N+1 查询是什么？怎么优化？

简答：查 N 条记录后，又为每条记录各查一次关联数据 → 1 + N 次查询。

  • 优化：先收集所有 id，再 WHERE id IN (...) 一次性查（2 次查询）。

  4. 单机内存锁（sync.Mutex / sync.Map）——仅单实例
  5. 分布式锁（Redis / ZooKeeper）——多实例

七、WebSocket 与实时通信（M2）

⭐⭐ 28. WebSocket 和 HTTP 长轮询 / SSE 有什么区别？为什么 IM 用 WebSocket？

简答：

  • HTTP 长轮询：客户端发请求，服务端 hold 住直到有数据/超时 → 每次都要重新建连接，开销大、实时性差
  • SSE：服务端单向推送，客户端不能发（IM 需要双向）
  • WebSocket：全双工、单 TCP 连接、开销小 → IM 的标准选择

代码：internal/ws/

⭐⭐ 29. 为什么 WebSocket 要读写分离？

简答：gorilla/websocket 不允许并发写（会 panic）。
所以每个连接：

  • 一个 goroutine 专门读（ReadPump）
  • 一个 goroutine 专门写（WritePump）
  • 其他 goroutine 想发消息只能往 send channel 里塞

代码：internal/ws/client.go

⭐ 30. 心跳机制解决什么问题？

简答：TCP 连接可能”假死”（网线拔了、手机切网），双方都不知道连接已断。

  • 服务端定期发 ping，客户端回 pong
  • 服务端设置 readDeadline，超时没收到 pong 就断开
    这样能及时清理僵尸连接、释放资源。

代码：internal/ws/client.go 的 ReadPump / WritePump

⭐⭐ 31. 大量 WebSocket 连接怎么管理？多实例怎么办？

简答：

  • 单机：Hub 用 map[userID]map[*Client]struct{} + sync.RWMutex
  • 一个用户可能有多个连接（多端登录）
  • 多实例：内存 Hub 只能管本进程连接 → 需要 Redis 存在线状态、用 MQ 广播跨实例消息（M4/M6/M7）

代码：internal/ws/hub.go

⭐ 32. 慢消费者怎么处理？

简答：客户端很慢时，推送队列会堆积。如果用阻塞写，会拖垮推送方（给其他用户推消息的 goroutine）。
解法：

  • 有界队列 + non-blocking 入队
  • 队列满 → 断开这个慢连接
    这样保证一个慢客户端不影响其他人。

⭐⭐ 35. 消息怎么保证不重复？

简答：客户端为每条消息生成唯一 client_msg_id，数据库 UNIQUE(sender_id, client_msg_id)：

  • 先查已存在 → 直接返回（幂等）
  • 并发插入撞唯一索引 → 捕获 gorm.ErrDuplicatedKey → 再查返回
    无论重试多少次，库里只有一条。

⭐ 36. 消息乱序怎么办？

并发发消息时，数据库自增 ID 的顺序就是落库顺序，不会乱。

十一、WebRTC 与通话（M5）

⭐⭐ 54. WebRTC 的原理？为什么是 P2P？

简答：WebRTC 让两个浏览器直接建立 UDP 连接传音视频，不经过服务器。
建立过程需要「信令」交换 SDP 和 ICE candidate，服务器只做信令转发，不碰媒体流。
好处：延迟低、服务器带宽成本低。

代码：internal/service/call_service、internal/ws/client.go 的 handleRelay

⭐⭐ 55. 信令服务器的作用？

简答：帮双方交换「怎么连」的信息：

  • SDP（offer/answer）：编解码、媒体类型、网络信息
  • ICE candidate：双方可能的网络路径
    服务器不解析这些内容，原样转发即可。

⭐ 56. SDP / ICE / STUN / TURN 分别是什么？

简答：

  • SDP：会话描述（编解码、媒体、网络）
  • ICE：候选地址收集 + 尝试连接的框架
  • STUN：发现自己的公网 IP:Port（NAT 映射）
  • TURN：打洞失败时的中继服务器（有带宽成本）

⭐⭐ 57. 通话状态机怎么设计？如何防重复接听？

简答：状态：呼叫中1/已接通2/已拒绝3/已取消4/已结束5/未接6。
状态迁移用条件更新：WHERE id=? AND callee_id=? AND status=1，RowsAffected=0 即拒绝。
和「接受好友申请」同一个套路，天然抗并发。

代码：call_service.go 的 Accept

⭐ 58. 通话时长怎么算？

简答：接通时记 started_at，挂断时 duration = now - started_at（秒）。
由服务端计算，避免客户端篡改。

⭐⭐ 59. 为什么要拆微服务？单体有什么问题？

简答：单体问题：整包扩缩容、故障不隔离、团队协作冲突、改一行全量发布。

本项目先单体跑通 M0–M5，再在 M6 拆——先体会痛点再拆。

⭐⭐ 60. 微服务怎么拆？

简答：按领域边界拆（用户域/聊天域），不是按技术分层（controller/service/dao 各一个服务是反模式）。
拆完每个服务独立部署、独立扩缩容，通过 gRPC 通信，对外统一走 gateway。

⭐⭐ 61. gRPC 和 REST 的区别？为什么内部用 gRPC？

简答：

  • gRPC：HTTP/2 + protobuf + 强契约（.proto）+ 支持四种流，性能高
  • REST：HTTP/1.1 + JSON + 契约弱（OpenAPI 可选）
  • 内部服务间用 gRPC（性能/契约），对外用 REST（浏览器友好）

⭐ 62. gRPC 四种调用方式？

简答：Unary（一请求一响应）、Server streaming、Client streaming、Bidirectional streaming。

⭐⭐ 63. gateway 的作用？

简答：协议转换（HTTP↔gRPC）、统一鉴权、限流、聚合。
内部服务不直接对外，鉴权在 gateway 做，降低每个服务的重复工作。

⭐ 64. 微服务带来的新问题？

简答：服务发现、超时/重试、熔断、链路追踪、跨服务数据一致性。

⭐ 65. 本项目 gRPC 为什么用 JSON codec？

简答：本机没有 protoc/buf，所以用 gRPC 自定义 codec（传输层仍是真 gRPC）。
换 protobuf 只需替换 codec 和生成代码，架构不变——说明微服务核心是「服务边界 + 契约」，不是序列化格式。

十三、消息队列（M7）

⭐⭐ 66. 为什么需要消息队列？

简答：解耦、削峰、异步、最终一致性。
本项目：发消息不再同步查成员+逐个推送，而是写 outbox 后异步推送。

⭐⭐ 67. 本地消息表（Outbox）解决什么问题？

简答：「落库」和「发 MQ」无法原子。
做法：业务事务里同时写业务数据 + outbox 记录（原子）；后台 worker 轮询 outbox 发 MQ 并标记已发送。
保证：即使 MQ 暂时挂了，消息也不会丢（worker 重试）。

⭐⭐ 68. 如何保证消息不丢？

简答：持久化队列 + 持久化消息 + 手动 ack + 生产者确认（publisher confirm）。
本项目用了前三项。

⭐⭐ 69. 如何保证消息不重复？

简答：MQ 是「至少一次」投递，消费方必须幂等：去重表/唯一索引/消息 id。
本项目消费动作是「推送给在线用户」，重复推影响小；如果是加积分就必须严格去重。

⭐ 70. 消息积压怎么办？

简答：加消费者/扩容、优化消费逻辑、死信队列、限流上游。

⭐ 71. 最终一致性 vs 强一致？

简答：跨服务无法用本地事务。方案：2PC（强一致但重）、Saga（补偿）、TCC（三阶段）、本地消息表（最简单）。
本项目用本地消息表。

⭐ 72. MQ 挂了系统怎么办？

简答：降级。本项目：global.MQ.Enabled == false 时改回同步推送，功能不中断。

二、WebRTC 基本原理（面试必问）

2.1 WebRTC 是 P2P 的

服务器不传音视频——这正是 WebRTC 相比「服务器混流」方案的最大优势：延迟低、服务器带宽成本低。

2.2 建立连接的三步

  1. 交换 SDP（Session Description Protocol）
    • A 生成 offer（我支持什么编解码、我的网络信息）
    • B 返回 answer
  2. 交换 ICE candidate
    • 双方各自收集「我可能的网络路径」（公网 IP、NAT 映射、中继地址）
    • 通过信令服务器互相告知
  3. P2P 打洞 / 中继
    • 能直连就直连
    • 打洞失败就用 TURN 服务器中继

2.3 STUN / TURN / ICE

概念 作用
ICE 框架：收集候选地址 + 按优先级尝试连接
STUN 帮客户端发现自己的公网 IP:Port（NAT 映射）
TURN 打洞失败时的中继服务器（要带宽成本）

面试可以答：”WebRTC 用 ICE 收集候选，STUN 发现公网地址，打洞失败用 TURN 中继；
服务器只做信令，不碰音视频。”

现在的做法

三、限流（滑动窗口）

为什么需要

  • 登录接口：可被撞库（批量试密码）
  • 注册接口：可被批量注册垃圾账号
  • 搜索接口：可被批量扫用户

实现：内存滑动窗口

每次请求：

  1. 清理该 key 里超出窗口的旧记录（懒清理，不用后台 goroutine）
  2. 判断是否超限
  3. 未超限则记录本次

为什么用滑动窗口而不是固定窗口

固定窗口在边界会翻倍：

滑动窗口只统计「最近 60 秒」，边界平滑。

六、goroutine 泄漏排查

常见泄漏点

泄漏点 原因
启动 goroutine 后没人关 例如 for { <-ch } 但 ch 永远不关闭
阻塞在 channel 发送 消费者已退出，生产者阻塞
阻塞在网络 IO 连接没设超时
定时器没 Stop time.NewTicker 忘了 Stop()

本项目怎么防

  • WritePump 里 defer ticker.Stop()
  • Client.Close() 用 sync.Once 保证幂等
  • Enqueue 队列满 → 主动断开慢连接
  • 优雅退出时 CloseAll() 清空所有连接（每个连接的读写 goroutine 都会随 conn 关闭而退出）

十、注意点清单

  1. 优雅退出顺序：HTTP → WS → DB/Redis
  2. Shutdown 要设超时，否则可能永远等
  3. 限流单机内存，多实例要 Redis
  4. 滑动窗口优于固定窗口（边界突发）
  5. 限流 key 用 IP，但注意代理场景要取真实 IP（X-Forwarded-For）
  6. Hub 持锁时不做 IO，先复制数据
  7. 信号量控制并发：pushSem <- struct{}{} / <-pushSem
  8. -race 需要 cgo，Linux/macOS 开箱即用，Windows 要装 gcc
  9. 日志不打印密码/token
  10. 每个 goroutine 都要有退出路径（连接关闭、channel 关闭、ctx 取消）
