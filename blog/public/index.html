仿微信前端与面试准备

一、前端技术选型

为了演示所有后端功能，实现了一个仿微信三栏布局的单页应用：

选型：原生 HTML/CSS/JS，由 Go 服务直接托管（r.Static）。
理由：零构建、零依赖、和后端同源（不用处理 CORS），演示最稳。

二、前端覆盖的功能

模块 功能
认证 登录/注册/登出、双 token 无感刷新（单飞）
会话 会话列表、未读数、在线状态
聊天 历史分页（滚轮上翻）、WebSocket 实时收发、已读标记
通讯录 好友列表、新朋友申请（接受/拒绝）、搜索加好友、备注、删除、拉黑
群聊 建群、群详情、成员列表、拉人、踢人、改资料、退群、解散
通话 通话记录、WebRTC 语音通话（呼叫/接听/拒绝/挂断/静音）
设置 资料修改、隐私开关、黑名单、退出登录

三、无感刷新的前端实现

单飞（single-flight）：并发 401 只发一次刷新请求，其他请求共享同一个 Promise。
否则 rotation 会让旧 refresh 被重复使用，触发服务端复用检测 → 用户被强制下线。

四、WebSocket 客户端要点

  1. token 走 query（浏览器 WS 不能带 header）
  2. 心跳 ping（25s），服务端 60s 无 pong 会踢连接
  3. 断线自动重连（指数退避，上限 15s）
  4. 事件分发：WS.on(type, handler)

五、WebRTC 通话（浏览器端）

  • localhost 是安全上下文 → HTTP 也能采集麦克风
  • 本机两窗口演示不需要 STUN（host candidate 直连）
  • 跨网演示需要 STUN/TURN

六、怎么讲这个项目（面试话术）

开场 30 秒

“我用 Go 实现了一个仿微信的 IM 后端，支持单聊/群聊、WebSocket 实时消息、WebRTC 语音通话，
并完整走过『单体 → gRPC 微服务 → RabbitMQ 最终一致性』的演进。”

挑 2–3 个亮点深入

双 token 无感刷新：access 2h + refresh 30d，refresh jti 存 Redis 白名单，
GETDEL 原子消费 + rotation + 复用检测。

消息幂等：client_msg_id + 唯一索引，重试不会重复落库。

WebSocket 架构：读写双泵（gorilla 不能并发写）、Hub 用 RWMutex、
心跳清理僵尸连接、慢消费者有界队列断开。

接受好友申请：事务 + 条件更新（RowsAffected 抗并发）。

Outbox：业务事务里写事件，worker 异步发 MQ，保证不丢 + 最终一致。

被问难点

问题 答法
最难 WebSocket 并发管理 + 双 token 并发刷新
踩的坑 软删除+唯一索引冲突、GORM 零值陷阱、事务里误用 global.DB、amqp.Table 不支持 uint
怎么验证 每个接口 curl 端到端，WS 用 .NET ClientWebSocket 实测
重做 会话创建加唯一键、未读数用 Redis、WS 多实例用 Redis 广播

主动说改进方向（体现深度）

  • 会话创建并发去重（唯一键）
  • 未读数 Redis 计数替代 N 次 count
  • WS 多实例：Redis Pub/Sub 或 MQ 广播
  • 消息已读回执/撤回
  • 群通话 SFU/MCU
  • 链路追踪、监控、测试覆盖率

M6-M7 分布式

微服务与消息队列

一、为什么要拆微服务

单体的问题：

痛点 单体 微服务
扩缩容 整包一起扩 按服务扩
故障隔离 一个模块 OOM 全挂 只挂一个
团队协作 一个仓库 按服务划分
部署 改一行全量发布 只发布改动的

代价：分布式复杂度（网络失败、一致性、服务发现、追踪）。

本项目先单体（M0–M5）跑通，M6 再拆——先体会痛点才知道为什么拆。

二、怎么拆：按领域，不按技术

本项目：

服务 职责 端口
user service 用户查询、批量查询 9001
chat service 发消息、拉历史 9002
gateway HTTP 入口 + 鉴权 + 限流 + 调 gRPC 8080

三、gRPC 核心知识

REST/JSON gRPC
传输 HTTP/1.1 HTTP/2（多路复用）
序列化 JSON protobuf（二进制、体积小）
契约 OpenAPI（可选） .proto 强契约
流式 弱 支持四种流

结论：对外 REST，内部服务间 gRPC。

本项目因环境没有 protoc，用 gRPC 的自定义 JSON codec 实现。
传输层仍是真 gRPC（HTTP/2、超时、状态码），换 protobuf 只需替换 codec 和生成代码，
架构不变——这说明微服务核心是「服务边界 + 契约」，不是序列化格式。

四、gateway 模式

gateway 负责：协议转换、统一鉴权、限流、聚合。
内部服务不直接对外，鉴权在入口做。

五、微服务带来的 5 个新问题

  1. 服务发现：怎么知道服务地址？（配置/Consul/Etcd/K8s）
  2. 超时重试：网络会失败，必须设超时，重试要幂等
  3. 熔断：下游持续失败时快速失败，防雪崩
  4. 链路追踪：跨服务请求要用 trace_id 串起来
  5. 数据一致性：跨服务不能用一个事务 → MQ/Saga/TCC

六、RabbitMQ：为什么需要

场景 不用 MQ 用 MQ
发消息后推送 请求里同步查成员+逐个推送 写 outbox，worker 异步推
群消息 200 人 请求耗时随人数增长 快速返回，后台慢慢推
流量高峰 直接打满 队列削峰
跨服务一致性 无法本地事务 最终一致性

七、核心：本地消息表（Transactional Outbox）

问题：落库和发 MQ 无法原子

  • 先落库后发 MQ：发 MQ 失败 → 消息丢失
  • 先发 MQ 后落库：落库失败 → 推了不存在的消息

解法：把「发 MQ」变成「写数据库」

关键洞察：写数据库是事务性的，发 MQ 不是。所以先记在数据库里，由后台可靠补发。

至少一次投递 → 消费幂等

worker 发 MQ 成功但标记失败 → 下次重复发。
消费方必须幂等（去重表/唯一索引/消息 id）。

本项目消费动作是「推送给在线用户」，重复推影响小；如果是加积分就必须严格去重。

八、可靠性设置

三项结合 = 至少一次。

九、降级设计

外部依赖要设计降级路径，不能因为 MQ 挂了整个聊天不可用。

十、踩过的坑

  • amqp.Table 的 value 不支持 uint，要转 int64
  • 事件契约要用中立的 struct，避免上下游循环依赖

十一、面试点

  1. 为什么拆微服务？单体有什么问题？
  2. 微服务怎么拆？为什么不能按技术层拆？
  3. gRPC vs REST？为什么内部用 gRPC？
  4. gateway 的作用？鉴权为什么放 gateway？
  5. 微服务带来哪些新问题？
  6. 为什么需要消息队列？
  7. 本地消息表解决什么问题？怎么实现？

  9. 最终一致性 vs 强一致？2PC/Saga/TCC/Outbox 怎么选？

M5 语音通话

WebRTC 语音通话实现

一、WebRTC 是 P2P 的

服务器不传音视频——这是 WebRTC 相比服务器混流的最大优势：延迟低、带宽成本低。

二、建立连接的三个步骤

  1. 交换 SDP
    • A 生成 offer（支持的编解码、网络信息）
    • B 返回 answer
  2. 交换 ICE candidate
    • 双方收集可能的网络路径
  3. P2P 打洞 / 中继
    • 能直连就直连，失败用 TURN 中继

STUN / TURN / ICE

概念 作用
ICE 框架：收集候选 + 按优先级尝试连接
STUN 发现自己的公网 IP:Port（NAT 映射）
TURN 打洞失败时的中继服务器（有带宽成本）

三、服务器职责：信令状态机

状态迁移全部用条件更新：

连点接听、超时后接、已挂断再挂断，都会被拦住。

四、信令协议（WebSocket）

方向 type 说明
C→S call_invite 发起通话
C→S call_accept / call_reject / call_cancel / call_end 状态操作
C→S webrtc_offer / webrtc_answer / webrtc_ice 转发信令
S→C call_ack / call_incoming / call_accepted / call_rejected / call_canceled / call_ended 状态通知
S→C webrtc_offer / webrtc_answer / webrtc_ice 原样转发 + from_user_id

信令转发实现

服务器不解析 SDP，只加 from_user_id 原样转发——这就是信令服务器的本质。

五、完整呼叫流程

六、前端实现要点

  • getUserMedia({ audio: true }) 采集麦克风
  • RTCPeerConnection 建立连接
  • onicecandidate → 通过 WS 发给对方
  • ontrack → 把对方音频挂到 <audio> 播放
  • localhost 是安全上下文，所以本地 HTTP 也能采集麦克风
  • 本机两窗口演示可不用 STUN（host candidate 直连）；跨网需 STUN/TURN

M4 并发加固

并发加固与优雅退出

一、优雅退出

以前 r.Run() 直接阻塞，进程被 kill 时：

  • 处理中的请求被硬切断
  • WebSocket 没 Close 帧，客户端要等超时
  • DB/Redis 连接没释放

现在的做法：

顺序很重要：先停 HTTP（不再有新请求）→ 再关 WS → 最后关依赖。

二、限流：滑动窗口

为什么需要：登录接口可被撞库、注册可被刷、搜索可被扫用户。

为什么用滑动窗口

固定窗口在边界会翻倍：

滑动窗口只统计「最近 60 秒」，边界平滑。

实现要点

每次请求：清理过期 → 判断超限 → 记录。
懒清理（请求时清理），不用后台 goroutine。

局限

单机内存限流在多实例下会翻倍。生产用 Redis（INCR + EXPIRE 或 Lua 脚本）。

实测：连续登录 25 次 → 前 20 次 401，之后 429。

三、WebSocket 并发安全

持锁不做 IO，否则会放大锁竞争。

四、扇出并发控制

群成员 200 人，无脑起 200 个 goroutine 会有瞬时压力。
用带缓冲 channel 当信号量：

小会话（≤10 人）直接顺序推送。

五、goroutine 泄漏排查

泄漏点 原因
启动 goroutine 后没人关 for { <-ch } 但 ch 永不关闭
阻塞在 channel 发送 消费者已退出
阻塞在网络 IO 没设超时
定时器没 Stop time.NewTicker 忘了 Stop

排查：go test -race（需 cgo）、pprof goroutine 数量。

六、其他改进

  • InitBaseServices() 从 os.Exit(0) 改为返回 error（退出码 1，不跳过 defer）
  • 删掉启动日志里打印完整 Config（会泄露数据库密码/JWT secret）

M3 群聊

群聊设计与权限

一、复用会话抽象

M2 已经把「会话 + 成员 + 消息」抽象好了，所以群聊几乎是免费的：

  • 群聊 = type=2 的会话 + groups 表（群元信息）
  • 群消息发送/推送完全复用 M2 的 SendMessage / PushMessage

M3 新增的只是群的生命周期管理：建群、拉人、踢人、改资料、解散。

这就是好抽象的复利：M2 多花点心思，M3 直接受益。

二、groups 表设计

字段 说明
conversation_id 关联会话（唯一）
owner_id 群主
name / avatar 群名称/头像
announcement 群公告
member_count 冗余人数
max_members 上限（默认 200）
status 1 正常 / 2 已解散

为什么冗余 member_count

群列表要显示人数。不冗余的话每次都 COUNT(*)。
加人/踢人时用 gorm.Expr("member_count + ?") 原子自增，避免并发覆盖。

三、建群必须用事务

建群要做 4 件事：

  1. 创建会话（type=2）
  2. 创建 groups 行
  3. 插入群主（role=1）
  4. 插入其他成员

不做事务的后果：

  • 有会话没群 → 会话列表出现无名会话
  • 有群没群主 → 没人能管理
  • 有群没会话 → 群消息发不出去

四、权限模型

操作 谁可以
拉人进群 任何成员（类微信）
踢人 只有群主
退群 任何成员（群主不能直接退）
改群名/公告 只有群主
解散群 只有群主

五、并发问题

人数上限有竞态

两个请求同时拉人，可能都通过 member_count + n > max 的校验 → 超员。

解法：

  1. 事务里 SELECT ... FOR UPDATE 锁群行（悲观锁）
  2. Redis 分布式锁
  3. 接受轻微超员（产品上可容忍）

计数用原子表达式

不要「先读再写」，并发会丢更新。

六、解散群

保留数据：群消息、群记录保留，便于审计/回溯。
IM 的群和消息一般软删，个人数据（如黑名单）可以物理删。

M2 实时消息

实时消息与 WebSocket

一、会话 + 消息两层抽象

单聊和群聊共用一套表：

好处：消息表不用区分单聊/群聊，统一按 conversation_id 查。
M3 做群聊时只需要新增 groups 表，消息逻辑完全复用。

二、消息幂等（重点）

网络重试、用户连点、WS 重发都会导致同一条消息发多次。

方案：客户端生成 client_msg_id，数据库 UNIQUE(sender_id, client_msg_id)。

服务端：

  1. 先查是否已存在 → 存在直接返回（幂等）
  2. 不存在 → 插入
  3. 并发撞唯一索引 → 捕获 gorm.ErrDuplicatedKey → 再查返回

配套：GORM 开启 TranslateError: true，把 MySQL 的 Duplicate 错误翻译成哨兵错误。

三、分页：游标 > offset

四、WebSocket 架构

为什么读写分离

gorilla/websocket 不允许并发写。所以：

  • ReadPump：唯一从 socket 读
  • WritePump：唯一往 socket 写
  • 其他 goroutine 发消息 = 往 send channel 塞数据

心跳

作用：清理「网线拔了但 TCP 没断」的僵尸连接。

慢消费者隔离

一个慢客户端不能拖垮给其他人推送的 goroutine。

五、离线消息

不需要单独离线表：

  • 消息落库到 messages
  • 用户上线后拉历史 GET /conversations/:id/messages
  • conversation_members.last_read_message_id 算未读数

这就是「持久化 + 上线拉取 + 未读数」的标准做法。

六、WS 鉴权

浏览器 WebSocket API 不能自定义 header，所以 token 走 query：

服务端在升级连接之前校验，非法直接 401。

七、踩过的坑

  1. CheckOrigin 生产环境必须校验（CSWSH 跨站 WebSocket 劫持）
  2. WS 连接用 context.Background()，不能用 HTTP 请求的 ctx
  3. Enqueue 要做 non-blocking + recover（连接关闭后 channel 会关闭）
  4. Hub 持锁时不要做 IO，先复制连接列表再释放锁

M1 认证与好友

认证与好友：双 token 与事务

一、为什么用双 token

单 token 的矛盾：

  • 有效期长 → 体验好，但泄露风险大、无法撤销
  • 有效期短 → 安全，但频繁掉登录

双 token：

  • access token：2 小时，每个请求携带，泄露窗口小
  • refresh token：30 天，只用来换新 access，存服务端可撤销

用户只要 30 天内用过，refresh 自动续期 → 无感不掉登录。

二、无感刷新的完整流程

关键点 1：用 GETDEL 原子消费

Exists + Del 是两条命令，中间有时间窗口，并发下两个请求都可能通过 → 都签发新 token，
rotation 就失效了。GETDEL 是原子命令，只有一个请求能成功。

关键点 2：rotation + 复用检测

每次刷新都换新 refresh，旧的作废。
如果旧 jti 不存在却仍被使用 → 可能被盗用 → 撤销该用户所有 refresh（强制下线）。

关键点 3：并发刷新怎么办

5 个请求同时 401 会触发 5 次刷新，rotation 会让第 2~5 次用旧 token → 被判定盗用。

解法：

  1. 客户端 single-flight：刷新进行中，其他请求等待同一个结果
  2. 服务端 GETDEL 防双签发
  3. 宽限期：消费标记短 TTL，区分正常重试和盗用

三、JWT 的安全要点

其他要点：

  • payload 是 base64 不是加密，只放 user_id/username，绝不放密码
  • secret 从配置读，不硬编码
  • access 短命 + refresh 可撤销

四、好友关系：双向两行

A、B 成为好友后插 (A,B) 和 (B,A) 两行。

  • 查「我的好友」只需 WHERE user_id=?
  • 每行可独立存备注/分组/星标
  • 代价：写入要写两行 → 必须用事务

五、接受好友申请：事务 + 条件更新

WHERE status=0 让「判断 + 修改」成为原子操作，天然抗并发重复接受。

六、踩过的坑

坑 1：软删除 + 唯一索引

删除好友只是 status=2，行还在。重新加好友时 INSERT 会撞唯一索引。
解法：Unscoped() 查旧行，存在就恢复 status=1。

坑 2：GORM 零值陷阱

改资料时只传昵称，其余字段是零值。用结构体 Updates 可能清空字段。
解法：请求用指针 / 用 map 组装 / Select 指定字段。

坑 3：先查后写的竞态

注册查重后插入，并发下两个请求都可能通过。
唯一索引是最后防线，业务层查重只是为了友好提示。

七、面试点

  1. 为什么用双 token？access 和 refresh 各解决什么问题？
  2. JWT payload 加密吗？能放什么？
  3. JWT 安全风险有哪些？怎么防算法混淆？
  4. 无状态 JWT 怎么登出？→ jti + Redis 白名单
  5. 并发刷新怎么处理？
  6. 好友关系为什么存两行？
  7. 接受好友申请为什么必须事务？
  8. 如何防止并发重复接受？
  9. 软删除和唯一索引冲突怎么解？

项目介绍：从零实现一个仿微信 IM 后端

为什么做这个项目

我想系统练习三件事：并发编程、微服务拆分、消息队列。普通的 CRUD 项目练不到这些，
于是决定做一个「仿微信」的即时通讯后端：

  • 有长连接（WebSocket）→ 练并发
  • 有多个业务域（用户/好友/聊天/群/通话）→ 练拆分
  • 有异步推送需求 → 练消息队列

技术栈

层 技术
Web 框架 Gin
ORM GORM + MySQL 8
缓存 Redis
鉴权 JWT 双 token
实时通信 gorilla/websocket
语音 WebRTC（信令服务）
微服务 gRPC
消息队列 RabbitMQ
前端 原生 HTML/CSS/JS（仿微信三栏）

架构演进：先单体，再微服务

为什么先单体：只有先体会单体的痛点（扩缩容、故障隔离、部署耦合），才知道为什么要拆。
