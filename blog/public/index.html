这是一篇「课程说明书」。花 10 分钟读完，能帮你少走很多弯路。

一、这门课面向谁

如果你满足以下条件，这篇博客就是为你写的：

  • ✅ 会 Go 基本语法（变量、函数、struct、interface、goroutine 的写法见过）
  • ✅ 懂计算机基础（进程/线程、HTTP、数据库是什么、SQL 会写一点）
  • ❌ 没做过完整项目（不知道分层怎么分、项目怎么组织）
  • ❌ 没用过 Gin / GORM / Redis / WebSocket / gRPC / RabbitMQ

不需要你提前会这些框架——文章会从「它是什么、为什么用它」讲起。

二、学完你能得到什么

一个能跑、能讲、能改的完整后端项目：

能力 具体表现
能跑 一条命令启动，浏览器打开就是仿微信界面
能讲 面试时能说清每个模块「解决什么问题、怎么解决、有什么坑」
能改 看懂任意一个文件的代码，能自己加功能（如消息撤回）

三、先建立全局印象

看图先记住三件事：

  1. 客户端只和 Gateway（:8080）说话
  2. 内部服务（user :9001 / chat :9002）用 gRPC 通信
  3. 消息推送是异步的：落库 → outbox → RabbitMQ → 消费者 → WebSocket

现在看不懂没关系，读完 M1–M7 再回来看，会有「哦——原来如此」的感觉。

五、读代码的三条铁律

铁律 1：沿「一条请求」走，不要按目录读

不要按 model → service → router 的顺序读。正确做法：

打开一个接口（如注册），从路由出发，跟着参数一路往下走，直到数据落库、响应返回。

这样你能看到「层与层之间怎么传数据」，比按目录读高效 10 倍。

铁律 2：先看「注释里的三种标记」

项目代码里大量使用这三种标记，看到就停下来读：

  • 【思路】 —— 为什么这么设计
  • 【注意点】 —— 容易踩的坑
  • 【面试点】 —— 面试会问什么

铁律 3：每个里程碑回答三个问题

读完后，合上电脑，问自己：

  1. 这步解决什么问题？（不讲代码，讲需求）
  2. 怎么解决的？（讲设计，不逐行背）
  3. 有什么坑？（能说出 2–3 个）

答得出来 = 真懂了；答不出来 = 回去补。

环境准备与项目启动（逐行讲解）

目标：搞懂「从一条命令到服务能响应」，这中间发生了什么。
读完你能理解 main.go、config.yaml、core/ 三者的关系。

一、先看项目怎么启动

go run . 会找当前目录的 package main，也就是 main.go。

二、config.yaml：配置为什么单独放文件

为什么不硬编码在代码里？

  • 开发/测试/生产环境配置不同，改配置不用改代码
  • 密码、密钥不应该进 git（生产用环境变量/配置中心）
  • 运维可以直接改配置重启，不用重新编译

三、internal/config：配置的 Go 结构体

YAML 是文本，Go 需要结构体来接。internal/config/mysql_config.go：

逐行解释：

  • `yaml:"host"` 是 struct tag，告诉 YAML 库：YAML 里的 host 对应这个字段
  • DB_DSN() 是方法（值接收者），把配置拼成 DSN
  • parseTime=True：让 MySQL 的 DATETIME 自动解析成 Go 的 time.Time（否则拿到的是字符串）
  • loc=Local：时区用本地时区

注意点：type Mysql struct{} 只放「数据定义」，不放「读取逻辑」——读取逻辑在 core/ 里。
这是用户最初就要求的分工：定义与读取分离。

四、core/init_config.go：读取配置的三步

逐行：

  • flag.StringVar(指针, 参数名, 默认值, 说明) —— 注意第 3 个参数是默认值，不是说明文字（这里踩过坑！）
  • -db 参数决定要不要执行 AutoMigrate（建表）
  • 解析结果存到 global.ConfigPath（全局变量）

逐行：

  • os.ReadFile 把整个文件读成 []byte
  • yaml.Unmarshal(bytes, &global.Config) —— 第二个参数必须传指针，否则解析结果写不进去
  • %w 是 Go 的错误包装语法，保留原始错误链（errors.Is 能判断）

逐行：

  • MySQL/Redis 是必需依赖：失败就返回 error，main 里 log.Fatal 退出
  • RabbitMQ 是可选依赖：失败只打日志，应用继续跑（消息改为同步推送）——这就是「降级设计」

五、db.LoadMysql：GORM 连接数据库

core/db/init_mysql.go：

逐行：

  • gorm.Open(mysql.Open(dsn), ...) —— 注意第一个参数是 gorm.Dialector，不是 dsn 字符串（这里踩过坑）
  • DisableForeignKeyConstraintWhenMigrating：迁移时不建物理外键，约束交给应用层
  • TranslateError：MySQL 的 Duplicate entry 会变成 gorm.ErrDuplicatedKey，业务代码能用 errors.Is 判断
  • 连接池：不设置的话默认可能无限开连接，DB 会被打爆

六、main.go：把所有东西串起来

为什么用 http.Server 而不是 r.Run()？

r.Run() 是阻塞的，进程被 kill 时处理中的请求会被硬切断。
用 http.Server + 信号监听，可以做到「停止接收新请求 → 等待处理中的请求完成 → 释放资源」。

七、/health：最简单的接口

internal/router/health/health_api.go：

逐行：

  • r.GET(路径, handler) 注册一个 GET 路由
  • c *gin.Context 是 gin 的请求上下文（拿参数、写响应都用它）
  • gin.H 就是 map[string]any 的简写
  • 为什么要有健康检查？ 负载均衡/K8s 用它判断服务是否存活

三、第 1 站：路由怎么注册的

internal/router/router.go：

internal/router/user_router/user_api.go 里：

逐行理解：

  • r.Group("/api/v1") 创建一个路由组，组内路径自动加前缀
  • r.Group("/api/v1", middleware.Auth()) 第二个参数是中间件，组内所有路由都会先执行它
  • 为什么要分组？ 把「需要登录」和「不需要登录」的接口分开，避免漏挂鉴权（最常见的安全事故）

四、第 2 站：handler 逐行

请求体结构体：

逐行理解：

  • json:"username"：JSON 字段名
  • binding:"required,min=3,max=32"：gin 内置的参数校验
    • required 必填
    • min/max 长度范围
    • 校验失败时 ShouldBindJSON 返回 error
  • c.ShouldBindJSON(&req)：把请求体 JSON 解析到结构体并校验
  • return 非常重要：出错必须 return，否则会继续往下执行

响应为什么统一格式

internal/router/resp/resp.go：

统一成 {code, message, data}，前端只需一套解析逻辑。

五、第 3 站：service 逐行

internal/service/user_service/register_service.go：

逐行理解：

  • Model(&User{}) 指定操作哪张表；Where 条件；Count(&count) 计数
  • ? 是占位符，防 SQL 注入（千万不要字符串拼接）
  • .Error —— GORM 的链式调用返回 *gorm.DB，错误在 .Error 字段
  • auth.Hash 用 bcrypt 加密：同一密码每次结果不同（随机 salt）
  • global.DB.Transaction(func(tx) error {...})：函数返回 error 就自动回滚
  • 为什么用户和设置要同事务？ 它们 1:1 必须成对出现，否则出现「有用户没设置」的脏数据
  • tx.Create(user) 之后 user.ID 会被 GORM 回填（自增主键）

六、第 4 站：model

internal/model/user_model/user_model.go：

逐行理解：

  • 嵌入 model.Model（内部是 gorm.Model）→ 自动获得 ID/CreatedAt/UpdatedAt/DeletedAt
  • uniqueIndex：建唯一索引（并发注册的最后防线）
  • json:"-"：序列化时忽略（密码哈希绝不出现在响应里）
  • TableName()：显式指定表名（否则默认是 users 单数化，容易猜错）

七、为什么这样分层

层 职责 不该做什么
handler 解析请求、参数校验、写响应 不写业务逻辑
service 业务规则、事务、调 model 不 import gin
model 描述表结构 不掺业务逻辑

好处：

  1. 可测试：service 是纯 Go 函数，单测不用起 HTTP 服务
  2. 可迁移：M6 拆 gRPC 时，service 完全不用改（*gin.Context 只存在 handler 层）
  3. 可复用：HTTP 接口和 gRPC 接口可以调同一个 service

踩坑集：24 个真实坑（含原因与解法）

这些都是本项目真实踩过的坑（编译报错、逻辑 bug、线上隐患）。
遇到问题先来这里查一眼，能省很多时间。

A. Go 语言坑

1. flag.StringVar 参数顺序

2. Go 不支持从 struct 解构

3. 空 .go 文件缺 package

每个 .go 文件第一行必须是 package xxx。

4. if err != nil 分支把错误吞了

检查习惯：问自己「这个 err 最后去哪了」。

5. os.Exit(0) 掩盖故障

应该 log.Fatalf（退出码 1）或返回 error。

B. GORM 坑

6. First/Find/Create 返回 *gorm.DB

7. gorm.Open 第一个参数要 Dialector

8. 零值陷阱：部分更新把字段清空

解法：请求结构体用指针 / 用 map[string]any / 用 Select 指定列。

9. 双指针

10. 软删除 + 唯一索引冲突

删除好友只是 status=2（或写 deleted_at），行还在 → 重新创建会撞唯一索引。
解法：Unscoped() 查旧行，存在就恢复。

11. 同一对用户只能有一条好友申请

UNIQUE(from_user_id, to_user_id) 导致「删除好友后重新申请」失败。
解法：先查旧行，存在就复用（重置 status=0）。

C. 认证 / 中间件坑

12. context key 不一致

解法：定义常量 middleware.CtxUserID，两边都用。

13. GetUint vs GetUint64

中间件存的是 uint64，用 GetUint 类型断言失败 → 返回 0，不报错。

14. c.Abort() 后必须 return

Abort 只是标记「后续别执行」，当前函数会继续跑。不 return 会继续执行后面的逻辑。

15. JWT 不校验签名算法

不校验 t.Method.(*jwt.SigningMethodHMAC) 会有 alg=none / HS256↔RS256 混淆攻击。

D. 数据库 / 性能坑

16. LIKE '%x%' 不走索引

B+ 树只能前缀匹配。数据量大时全表扫描。
解法：前缀匹配 x%、全文索引、或 ES。

17. N+1 查询

列表里每条记录都去查一次关联表 → 1+N 次查询。
解法：收集 id → WHERE id IN (...) 一次查（2 次查询）。

18. 事务里混用 global.DB

判断标准：事务函数里出现 global.DB 就是 bug。

19. 未读数 N 次 count

会话多时列表要 count N 次。生产用 Redis 计数器优化。

E. WebSocket 坑

20. gorilla/websocket 不能并发写

多个 goroutine 同时写同一个连接会 panic。
解法：读写分离，所有写操作交给 WritePump（通过 channel）。

21. WS 用错 context

WS 连接生命周期远长于 HTTP 请求。

F. 前端坑

22. [hidden] 被 CSS display:flex 覆盖

结果：登录页/通话遮罩一直挡住界面。
解法：[hidden] { display: none !important; }

23. 函数写了但没绑定事件

switchPanel() 定义了，但导航按钮没 addEventListener → 点了没反应。
排查方法：F12 Console 加日志，确认函数是否被调用。

G. 工具 / 环境坑

24. PowerShell 5.1 读 UTF-8 无 BOM 的 .ps1 中文乱码

症状：Missing closing '}' 之类莫名语法错误。
解法：脚本保存为 UTF-8 with BOM。

  2. 定位到文件和行号，打开那一行前后 20 行

M1 认证与好友

认证与好友：双 token 与事务

一、为什么用双 token

单 token 的矛盾：

  • 有效期长 → 体验好，但泄露风险大、无法撤销
  • 有效期短 → 安全，但频繁掉登录

双 token：

  • access token：2 小时，每个请求携带，泄露窗口小
  • refresh token：30 天，只用来换新 access，存服务端可撤销

用户只要 30 天内用过，refresh 自动续期 → 无感不掉登录。

二、无感刷新的完整流程

关键点 1：用 GETDEL 原子消费

Exists + Del 是两条命令，中间有时间窗口，并发下两个请求都可能通过 → 都签发新 token，
rotation 就失效了。GETDEL 是原子命令，只有一个请求能成功。

关键点 2：rotation + 复用检测

每次刷新都换新 refresh，旧的作废。
如果旧 jti 不存在却仍被使用 → 可能被盗用 → 撤销该用户所有 refresh（强制下线）。

关键点 3：并发刷新怎么办

5 个请求同时 401 会触发 5 次刷新，rotation 会让第 2~5 次用旧 token → 被判定盗用。

解法：

  1. 客户端 single-flight：刷新进行中，其他请求等待同一个结果
  2. 服务端 GETDEL 防双签发
  3. 宽限期：消费标记短 TTL，区分正常重试和盗用

三、JWT 的安全要点

其他要点：

  • payload 是 base64 不是加密，只放 user_id/username，绝不放密码
  • secret 从配置读，不硬编码
  • access 短命 + refresh 可撤销

四、好友关系：双向两行

A、B 成为好友后插 (A,B) 和 (B,A) 两行。

  • 查「我的好友」只需 WHERE user_id=?
  • 每行可独立存备注/分组/星标
  • 代价：写入要写两行 → 必须用事务

五、接受好友申请：事务 + 条件更新

WHERE status=0 让「判断 + 修改」成为原子操作，天然抗并发重复接受。

六、踩过的坑

坑 1：软删除 + 唯一索引

删除好友只是 status=2，行还在。重新加好友时 INSERT 会撞唯一索引。
解法：Unscoped() 查旧行，存在就恢复 status=1。

坑 2：GORM 零值陷阱

改资料时只传昵称，其余字段是零值。用结构体 Updates 可能清空字段。
解法：请求用指针 / 用 map 组装 / Select 指定字段。

坑 3：先查后写的竞态

注册查重后插入，并发下两个请求都可能通过。
唯一索引是最后防线，业务层查重只是为了友好提示。

七、面试点

  1. 为什么用双 token？access 和 refresh 各解决什么问题？
  2. JWT payload 加密吗？能放什么？
  3. JWT 安全风险有哪些？怎么防算法混淆？
  4. 无状态 JWT 怎么登出？→ jti + Redis 白名单
  5. 并发刷新怎么处理？
  6. 好友关系为什么存两行？
  7. 接受好友申请为什么必须事务？
  8. 如何防止并发重复接受？
  9. 软删除和唯一索引冲突怎么解？

M2 实时消息

实时消息与 WebSocket

一、会话 + 消息两层抽象

单聊和群聊共用一套表：

好处：消息表不用区分单聊/群聊，统一按 conversation_id 查。
M3 做群聊时只需要新增 groups 表，消息逻辑完全复用。

二、消息幂等（重点）

网络重试、用户连点、WS 重发都会导致同一条消息发多次。

方案：客户端生成 client_msg_id，数据库 UNIQUE(sender_id, client_msg_id)。

服务端：

  1. 先查是否已存在 → 存在直接返回（幂等）
  2. 不存在 → 插入
  3. 并发撞唯一索引 → 捕获 gorm.ErrDuplicatedKey → 再查返回

配套：GORM 开启 TranslateError: true，把 MySQL 的 Duplicate 错误翻译成哨兵错误。

三、分页：游标 > offset

四、WebSocket 架构

为什么读写分离

gorilla/websocket 不允许并发写。所以：

  • ReadPump：唯一从 socket 读
  • WritePump：唯一往 socket 写
  • 其他 goroutine 发消息 = 往 send channel 塞数据

心跳

作用：清理「网线拔了但 TCP 没断」的僵尸连接。

慢消费者隔离

一个慢客户端不能拖垮给其他人推送的 goroutine。

五、离线消息

不需要单独离线表：

  • 消息落库到 messages
  • 用户上线后拉历史 GET /conversations/:id/messages
  • conversation_members.last_read_message_id 算未读数

这就是「持久化 + 上线拉取 + 未读数」的标准做法。

六、WS 鉴权

浏览器 WebSocket API 不能自定义 header，所以 token 走 query：

服务端在升级连接之前校验，非法直接 401。

七、踩过的坑

  1. CheckOrigin 生产环境必须校验（CSWSH 跨站 WebSocket 劫持）
  2. WS 连接用 context.Background()，不能用 HTTP 请求的 ctx
  3. Enqueue 要做 non-blocking + recover（连接关闭后 channel 会关闭）
  4. Hub 持锁时不要做 IO，先复制连接列表再释放锁

M3 群聊

群聊设计与权限

一、复用会话抽象

M2 已经把「会话 + 成员 + 消息」抽象好了，所以群聊几乎是免费的：

  • 群聊 = type=2 的会话 + groups 表（群元信息）
  • 群消息发送/推送完全复用 M2 的 SendMessage / PushMessage

M3 新增的只是群的生命周期管理：建群、拉人、踢人、改资料、解散。

这就是好抽象的复利：M2 多花点心思，M3 直接受益。

二、groups 表设计

字段 说明
conversation_id 关联会话（唯一）
owner_id 群主
name / avatar 群名称/头像
announcement 群公告
member_count 冗余人数
max_members 上限（默认 200）
status 1 正常 / 2 已解散

为什么冗余 member_count

群列表要显示人数。不冗余的话每次都 COUNT(*)。
加人/踢人时用 gorm.Expr("member_count + ?") 原子自增，避免并发覆盖。

三、建群必须用事务

建群要做 4 件事：

  1. 创建会话（type=2）
  2. 创建 groups 行
  3. 插入群主（role=1）
  4. 插入其他成员

不做事务的后果：

  • 有会话没群 → 会话列表出现无名会话
  • 有群没群主 → 没人能管理
  • 有群没会话 → 群消息发不出去

四、权限模型

操作 谁可以
拉人进群 任何成员（类微信）
踢人 只有群主
退群 任何成员（群主不能直接退）
改群名/公告 只有群主
解散群 只有群主

五、并发问题

人数上限有竞态

两个请求同时拉人，可能都通过 member_count + n > max 的校验 → 超员。

解法：

  1. 事务里 SELECT ... FOR UPDATE 锁群行（悲观锁）
  2. Redis 分布式锁
  3. 接受轻微超员（产品上可容忍）

计数用原子表达式

不要「先读再写」，并发会丢更新。

六、解散群

保留数据：群消息、群记录保留，便于审计/回溯。
IM 的群和消息一般软删，个人数据（如黑名单）可以物理删。

  6. 群主退群怎么处理？（转让/解散）
  7. 群消息扇出到 200 人怎么优化？

M4 并发加固

并发加固与优雅退出

一、优雅退出

以前 r.Run() 直接阻塞，进程被 kill 时：

  • 处理中的请求被硬切断
  • WebSocket 没 Close 帧，客户端要等超时
  • DB/Redis 连接没释放

现在的做法：

顺序很重要：先停 HTTP（不再有新请求）→ 再关 WS → 最后关依赖。

二、限流：滑动窗口

为什么需要：登录接口可被撞库、注册可被刷、搜索可被扫用户。

为什么用滑动窗口

固定窗口在边界会翻倍：

滑动窗口只统计「最近 60 秒」，边界平滑。

实现要点

每次请求：清理过期 → 判断超限 → 记录。
懒清理（请求时清理），不用后台 goroutine。

局限

单机内存限流在多实例下会翻倍。生产用 Redis（INCR + EXPIRE 或 Lua 脚本）。

实测：连续登录 25 次 → 前 20 次 401，之后 429。

三、WebSocket 并发安全

持锁不做 IO，否则会放大锁竞争。

四、扇出并发控制

群成员 200 人，无脑起 200 个 goroutine 会有瞬时压力。
用带缓冲 channel 当信号量：

小会话（≤10 人）直接顺序推送。

五、goroutine 泄漏排查

泄漏点 原因
启动 goroutine 后没人关 for { <-ch } 但 ch 永不关闭
阻塞在 channel 发送 消费者已退出
阻塞在网络 IO 没设超时
定时器没 Stop time.NewTicker 忘了 Stop

排查：go test -race（需 cgo）、pprof goroutine 数量。

六、其他改进

  • InitBaseServices() 从 os.Exit(0) 改为返回 error（退出码 1，不跳过 defer）
  • 删掉启动日志里打印完整 Config（会泄露数据库密码/JWT secret）

  3. 单机限流 vs 分布式限流？

  8. 进程退出怎么保证数据不丢？
