二、优雅退出（Graceful Shutdown）

以前的问题

现在的做法

为什么顺序是「先 HTTP 后 WS 后 DB」

  • 先关 HTTP：不再接新请求，等在途请求处理完
  • 再关 WS：客户端立即收到 Close 帧，触发重连
  • 最后关 DB/Redis：保证前面的清理逻辑还能用数据库

面试点：优雅退出要做哪些事？顺序为什么重要？

三、限流（滑动窗口）

为什么需要

  • 登录接口：可被撞库（批量试密码）
  • 注册接口：可被批量注册垃圾账号
  • 搜索接口：可被批量扫用户

实现：内存滑动窗口

每次请求：

  1. 清理该 key 里超出窗口的旧记录（懒清理，不用后台 goroutine）
  2. 判断是否超限
  3. 未超限则记录本次

为什么用滑动窗口而不是固定窗口

固定窗口在边界会翻倍：

滑动窗口只统计「最近 60 秒」，边界平滑。

当前配置

接口 限制
/register、/login 20 次/分钟/IP
/users/search 30 次/分钟/IP
/token/refresh 不限（客户端正常刷新频率）

局限与后续

单机内存：多实例部署时每个实例独立计数，总量会翻倍。
生产解法：Redis（INCR + EXPIRE，或 Lua 脚本做滑动窗口）。M6 拆微服务时升级。

实测：连续登录 25 次 → 前 20 次 401，后 5 次 429。

五、消息扇出的并发控制

问题

群成员 200 人时，PushMessage 如果无脑起 200 个 goroutine：

  • goroutine 数量瞬间暴涨
  • 对 Hub 锁、网络造成瞬时压力

方案：信号量限制并发数

小会话（≤10 人）直接顺序推送，避免 goroutine 开销。

面试点：如何控制并发数？三种方式——

  • 带缓冲 channel 当信号量（本项目）
  • golang.org/x/sync/semaphore（加权信号量）
  • worker pool

六、goroutine 泄漏排查

常见泄漏点

泄漏点 原因
启动 goroutine 后没人关 例如 for { <-ch } 但 ch 永远不关闭
阻塞在 channel 发送 消费者已退出，生产者阻塞
阻塞在网络 IO 连接没设超时
定时器没 Stop time.NewTicker 忘了 Stop()

本项目怎么防

  • WritePump 里 defer ticker.Stop()
  • Client.Close() 用 sync.Once 保证幂等
  • Enqueue 队列满 → 主动断开慢连接
  • 优雅退出时 CloseAll() 清空所有连接（每个连接的读写 goroutine 都会随 conn 关闭而退出）

十、注意点清单

  1. 优雅退出顺序：HTTP → WS → DB/Redis
  2. Shutdown 要设超时，否则可能永远等
  3. 限流单机内存，多实例要 Redis
  4. 滑动窗口优于固定窗口（边界突发）
  5. 限流 key 用 IP，但注意代理场景要取真实 IP（X-Forwarded-For）
  6. Hub 持锁时不做 IO，先复制数据
  7. 信号量控制并发：pushSem <- struct{}{} / <-pushSem
  8. -race 需要 cgo，Linux/macOS 开箱即用，Windows 要装 gcc
  9. 日志不打印密码/token
  10. 每个 goroutine 都要有退出路径（连接关闭、channel 关闭、ctx 取消）
