面试集：72 道高频题（含简答与代码位置）

从项目代码提炼的面试题。每题包含：问题 → 简答 → 本项目代码位置。
建议练法：先自己答，再看简答，最后对照代码。
标记：⭐ 高频 / ⭐⭐ 必会

一、Go 语言基础

⭐ 1. context.Context 是干什么的？

简答：用来在调用链上传递「取消信号、超时、请求范围的值」。
本项目里所有可能慢的操作（Redis、DB、下游调用）第一个参数都是 ctx，客户端断开时 c.Request.Context() 被取消，下游操作自动中止，避免资源浪费。

代码：internal/service/user_service/login_service.go（Login(ctx, ...)）、internal/auth/token_store.go

⭐ 2. *gin.Context 和 context.Context 有什么区别？为什么 service 用后者？

简答：

  • *gin.Context 是 HTTP 框架上下文（请求/响应/参数绑定/JSON 输出），只在 handler 层有意义。
  • context.Context 是标准库的通用上下文，用于取消/超时/传值。
  • service 用 context.Context 是为了解耦框架：M6 拆 gRPC 时 gRPC 里只有 context.Context，service 不用改；也方便单测。
  • 衔接方式：handler 里 c.Request.Context()。

代码：internal/router/user_router/user_api.go（传 c.Request.Context()）

⭐ 3. Go 的并发安全：哪些东西并发读写会出问题？

简答：

  • global.DB（GORM）和 global.Redis（go-redis）内部并发安全。
  • 普通 map 并发读写会直接 panic（fatal error: concurrent map read and map write）。
  • 业务层的「先查后写」不是原子的，需要唯一索引/事务/锁。

代码：M2 的 WebSocket 连接管理会用到 sync.Map / sync.RWMutex。

二、JWT 与认证

⭐⭐ 4. 为什么用双 token（access + refresh）？

简答：

  • access token 短命（2h），每个请求携带，泄露窗口小。
  • refresh token 长命（30d），只用于换新 access，且存在服务端（Redis）可撤销。
  • 用户只要 30 天内用过，refresh 自动续期 → 无感不掉登录。
  • 单 token 无法同时满足「安全」和「长期登录」。

代码：internal/auth/jwt.go、internal/service/user_service/login_service.go

⭐⭐ 5. JWT 的 payload 是加密的吗？能放什么？

简答：不是加密，只是 base64 编码，任何人都能解码。
signature（签名）只保证「没被篡改」，不保证「保密」。
所以只能放身份标识（user_id、username），绝不能放密码、身份证等敏感信息。

代码：internal/auth/jwt.go（Claims 只有 UserID/Username/Type）

⭐⭐ 6. JWT 有哪些安全风险？

简答：

  1. 算法混淆：alg=none 或 HS256↔RS256 混用 → 防法：校验 t.Method.(*jwt.SigningMethodHMAC)。
  2. payload 泄露：明文可读 → 不放敏感信息。
  3. 无法撤销：签出去就收不回 → 用 jti + 服务端白名单。
  4. 过期不短：泄露窗口大 → access 设短、refresh 长但可撤销。
  5. 密钥硬编码：→ 从配置读取。

代码：internal/auth/jwt.go 的 Parse() 里的算法校验

⭐⭐ 7. JWT 是无状态的，怎么实现登出/撤销？

简答：签发时给 refresh token 塞一个唯一 jti，并把 refresh:{userID}:{jti} 存 Redis（白名单）。
登出 = 删除该 jti；校验 = 查 Redis 是否还存在。
这样保留了 JWT 的无状态优势，又获得了「可撤销」能力。

代码：internal/auth/token_store.go、internal/router/user_router/user_api.go 的 Logout

⭐⭐ 8. refresh rotation 是什么？并发刷新怎么办？

简答：

  • rotation：每次刷新都签发新的 refresh，旧的作废。这样被盗的 refresh 只能用一次。
  • 并发刷新：多个请求同时用同一个 refresh → 只有第一个成功（GETDEL 原子消费），其余会触发「复用检测」→ 撤销全部。
  • 解决：① 客户端 single-flight（只发一次刷新，其他请求等待复用结果）；② 服务端用 GETDEL 防双签发 + 短 TTL 消费标记做宽限期；③ 更完善的是缓存「旧 jti → 新 token 对」实现幂等刷新。

代码：internal/service/user_service/refresh_service.go、internal/auth/token_store.go

⭐ 9. 为什么用 GETDEL 而不是 Exists + Del？

简答：Exists + Del 是两条命令，中间有时间窗口，并发下两个请求都可能通过检查然后都签发新 token，rotation 就失效了。
GETDEL 是 Redis 的原子命令（取+删一步完成），只有一个请求能拿到值。

代码：internal/auth/token_store.go 的 ConsumeRefreshKey

⭐ 10. 为什么密码用 bcrypt 而不是 MD5/SHA256？

简答：

  • MD5/SHA256 是快速哈希，GPU 暴力破解极快；且相同密码哈希相同（彩虹表）。
  • bcrypt 故意慢（cost=10 约 50~100ms）+ 内置随机 salt：同一密码每次哈希都不同，破解成本极高。
  • 校验用 CompareHashAndPassword，从哈希里取出 salt 再算。

代码：internal/auth/password_util.go

⭐⭐ 12. GORM 部分更新的零值陷阱是什么？

简答：用结构体做 Updates 时，零值字段（""、0、false）会被 GORM 忽略。
后果：

  • 用户只想改昵称，传了 {nickname:"x"}，其余字段是零值 → 但如果你 Updates(req)，那些字段其实不会被更新（这算幸运）；
  • 更危险的是：想显式把某字段改成 0/空，GORM 会忽略，改不动。

解法（三选一）：

  1. 请求结构体用指针（*string、*bool）：nil=没传，非 nil=传了
  2. 用 map[string]any 组装，map 里 false/0/“” 不会被跳过
  3. 用 Select("field1","field2") 明确指定要更新的列

代码：internal/service/user_service/user_update_service.go

⭐ 13. 软删除和唯一索引为什么会冲突？怎么解？

简答：
软删除只是写 deleted_at/改 status，行还在，唯一索引依然生效。
所以「删除后重新创建同一条记录」会撞唯一索引。

解法：

  • 复用旧行：查 Unscoped()（含软删行），存在就恢复
  • 或对”开关型”数据用物理删除（如黑名单的拉黑/取消）
  • 或把删除标记列加进唯一索引（但恢复时要处理）

代码：internal/service/friend_service/friend_service.go 的 upsertFriendship、RemoveBlacklist、SendRequest

⭐ 14. 注册时的「先查后写」并发安全吗？

简答：不安全。两个请求可能同时通过查重，然后都执行插入（TOCTOU 竞态）。
真正的兜底是数据库的唯一索引：只有一个能插成功，另一个报 Duplicate。
业务层的查重只是为了给用户友好提示（”用户名已存在”），不是安全边界。

代码：internal/service/user_service/register_service.go

⭐ 15. N+1 查询是什么？怎么优化？

简答：查 N 条记录后，又为每条记录各查一次关联数据 → 1 + N 次查询。

  • 本项目例子：好友申请列表，如果每条申请都去查一次申请人信息，就是 N+1。
  • 优化：先收集所有 id，再 WHERE id IN (...) 一次性查（2 次查询）。
  • 其他手段：JOIN、GORM 预加载 Preload。

代码：internal/service/friend_service/friend_service.go 的 ListIncomingRequests、ListFriends

⭐ 16. LIKE '%x%' 为什么用不上索引？

简答：B+ 树索引只能做前缀匹配。%x 前面的 % 表示”前面可以是任意内容”，索引无法定位起点，只能全表扫描。
优化：改成前缀匹配 x%、用全文索引、或上 ES。

代码：internal/service/user_service/user_search_service.go

四、事务与并发

⭐⭐ 17. 接受好友申请为什么必须用事务？

简答：一次接受要写两处：

  1. 改 friend_requests.status = 已接受
  2. 插两条 friendships（A→B、B→A）

不用事务：改了状态但插好友失败 → 申请显示已通过但还不是好友（数据不一致）。
事务保证「要么全成功，要么全回滚」。

代码：internal/service/friend_service/friend_service.go 的 AcceptRequest

⭐⭐ 18. 如何防止并发重复接受同一个好友申请？

简答：用条件更新 + RowsAffected：

WHERE status=0 让「判断」和「修改」成为一个原子操作，天然抗并发。

代码：同 AcceptRequest

⭐ 19. 事务里最容易犯什么错？

简答：

  1. 事务里混用 global.DB：global.DB.Create() 不在事务内，失败不回滚。必须全部用 tx。
  2. 事务太长：在事务里做 HTTP 调用/文件 IO，长时间持锁。
  3. 不检查 RowsAffected：条件更新没生效却当成成功。
  4. 忘记 return 错误：事务函数返回 nil 导致提交。

代码：AcceptRequest、DeleteFriend

⭐ 20. 什么时候该加锁，什么时候不用？

简答：优先级：

  1. 唯一索引 / 条件更新（最简单，首选）
  2. 事务（多表原子）
  3. Redis 原子命令（GETDEL / INCR / SETNX）
  4. 单机内存锁（sync.Mutex / sync.Map）——仅单实例
  5. 分布式锁（Redis / ZooKeeper）——多实例

原则：能用数据库的唯一约束/条件更新解决，就别引入锁。

五、Redis

⭐ 21. Redis 怎么删大量 key？为什么不能用 KEYS？

简答：

  • KEYS pattern 会一次性遍历所有 key，Redis 是单线程，数据量大时阻塞整个 Redis（线上事故）。
  • SCAN 用游标分批遍历（每次 100 个），不阻塞；缺点是可能重复/漏（需容忍）。

代码：internal/auth/token_store.go 的 DeleteAllRefreshJtiinRedis

⭐ 22. Redis 的 key 怎么设计？

简答：业务:对象:标识 结构，见本项目：

  • refresh:{userID}:{jti} —— refresh token 白名单
  • （M2 会用）online:{userID} —— 在线状态
  • （M4 会用）rate:{userID}:{window} —— 限流计数

要点：可读、可批量匹配、带 TTL 防内存泄漏。

六、API 设计与工程实践

⭐ 23. 为什么 public 路由和鉴权路由用两个 gin.Group？

简答：把「公开接口」和「需要登录的接口」分成两个组，鉴权组整组挂 middleware.Auth()。
好处：新增接口直接丢进组里，不会漏挂鉴权。漏挂鉴权是最常见的安全事故。

代码：internal/router/user_router/user_api.go、internal/router/friend_router/friend_api.go

⭐ 24. 为什么 c.Abort() 后必须 return？

简答：c.Abort() 只是标记「后续中间件/handler 别执行」，当前函数仍会继续往下跑。
如果不 return，后面的代码会继续执行（可能又写了响应、或继续调业务逻辑），造成漏洞。

代码：internal/middleware/auth.go

⭐ 25. 为什么 gin context 的 key 要用常量？

简答：中间件 c.Set("userId", ...) 和 handler c.Get("userId") 必须用同一个字符串。
手写字符串写错一个字母不会报错，只会永远拿到零值——极难排查。
定义成常量（middleware.CtxUserID）让编译器帮忙检查。

代码：internal/middleware/auth.go、internal/router/friend_router/friend_api.go

⭐ 26. 注册时为什么要在事务里同时创建 user_settings？

简答：用户和设置是 1:1，必须成对出现。不加事务：用户建成功、设置建失败 → 数据不一致。
global.DB.Transaction(func(tx *gorm.DB) error {...}) 里任一步返回 error → 自动回滚。

代码：internal/service/user_service/register_service.go

⭐ 27. 为什么「用户不存在」和「密码错误」返回同样的提示？

简答：防用户枚举攻击。如果提示”用户不存在”，攻击者能批量试出哪些用户名注册过。
统一返回”用户名或密码错误”，攻击者无法区分。

代码：internal/service/user_service/login_service.go

七、WebSocket 与实时通信（M2）

⭐⭐ 28. WebSocket 和 HTTP 长轮询 / SSE 有什么区别？为什么 IM 用 WebSocket？

简答：

  • HTTP 长轮询：客户端发请求，服务端 hold 住直到有数据/超时 → 每次都要重新建连接，开销大、实时性差
  • SSE：服务端单向推送，客户端不能发（IM 需要双向）
  • WebSocket：全双工、单 TCP 连接、开销小 → IM 的标准选择

代码：internal/ws/

⭐⭐ 29. 为什么 WebSocket 要读写分离？

简答：gorilla/websocket 不允许并发写（会 panic）。
所以每个连接：

  • 一个 goroutine 专门读（ReadPump）
  • 一个 goroutine 专门写（WritePump）
  • 其他 goroutine 想发消息只能往 send channel 里塞

代码：internal/ws/client.go

⭐ 30. 心跳机制解决什么问题？

简答：TCP 连接可能”假死”（网线拔了、手机切网），双方都不知道连接已断。

  • 服务端定期发 ping，客户端回 pong
  • 服务端设置 readDeadline，超时没收到 pong 就断开
    这样能及时清理僵尸连接、释放资源。

代码：internal/ws/client.go 的 ReadPump / WritePump

⭐⭐ 31. 大量 WebSocket 连接怎么管理？多实例怎么办？

简答：

  • 单机：Hub 用 map[userID]map[*Client]struct{} + sync.RWMutex
  • 一个用户可能有多个连接（多端登录）
  • 多实例：内存 Hub 只能管本进程连接 → 需要 Redis 存在线状态、用 MQ 广播跨实例消息（M4/M6/M7）

代码：internal/ws/hub.go

⭐ 32. 慢消费者怎么处理？

简答：客户端很慢时，推送队列会堆积。如果用阻塞写，会拖垮推送方（给其他用户推消息的 goroutine）。
解法：

  • 有界队列 + non-blocking 入队
  • 队列满 → 断开这个慢连接
    这样保证一个慢客户端不影响其他人。

代码：internal/ws/client.go 的 Enqueue

⭐ 33. WS 怎么鉴权？

简答：浏览器 WebSocket API 不能自定义请求头，所以 token 放 query：ws://host/ws?token=xxx。
服务端在升级连接之前校验 token，非法直接 401（不浪费连接）。
非浏览器客户端也可兼容 Authorization: Bearer。

代码：internal/ws/handler.go

⭐ 34. WebSocket 的 CheckOrigin 为什么要校验？

简答：不校验的话，任意网站都能从用户浏览器连你的 WebSocket（CSWSH，跨站 WebSocket 劫持），
配合浏览器里已登录的 Cookie 就能冒充用户。生产环境必须校验 Origin。

八、消息系统（M2）

⭐⭐ 35. 消息怎么保证不重复？

简答：客户端为每条消息生成唯一 client_msg_id，数据库 UNIQUE(sender_id, client_msg_id)：

  • 先查已存在 → 直接返回（幂等）
  • 并发插入撞唯一索引 → 捕获 gorm.ErrDuplicatedKey → 再查返回
    无论重试多少次，库里只有一条。

代码：internal/service/chat_service/message_service.go 的 SendMessage

⭐ 36. 消息乱序怎么办？

简答：服务端用自增 ID 作为消息顺序依据（单库）。客户端收到后按 ID 排序/去重。
并发发消息时，数据库自增 ID 的顺序就是落库顺序，不会乱。
分库分表时要用雪花算法保证全局有序。

⭐⭐ 37. 离线消息怎么实现？

简答：不需要单独离线队列。消息落库 + 上线拉历史 + 未读数：

  • messages 表持久化
  • 上线后 GET /conversations/:id/messages 拉历史
  • conversation_members.last_read_message_id 算未读

代码：ListMessages、ListConversations

⭐ 38. 游标分页 vs offset 分页？

简答：

  • offset：LIMIT 20 OFFSET 1000 → 数据库要跳过前 1000 行，越翻越慢；新数据插入还会错位
  • 游标：WHERE id < 上一页最后一条 → 走索引、性能稳定、不错位
    IM 消息历史必须用游标分页。

代码：ListMessages 的 before_id

⭐ 39. 未读数怎么算？怎么优化？

简答：

  • 简单版：COUNT(*) WHERE conversation_id=? AND id > last_read AND sender != 我
  • 问题：会话多时是 N 次 count
  • 优化：Redis 计数器（每收一条 INCR，已读时重置）、或定时汇总

代码：ListConversations

⭐ 40. 单聊会话怎么保证”两个人只有一个会话”？

简答：conversation_members 自连接：同一个 conversation 下同时存在两个 user。
并发创建可能产生重复会话 → M4 用唯一键（如 single_key='min:max'）或分布式锁解决。

代码：CreateOrGetSingleConversation

九、群聊（M3）

⭐⭐ 41. 群聊为什么复用「会话 + 消息」模型？

简答：群聊 = Type=2 的会话 + groups 表（群元信息）。

  • 消息表不需要区分单聊/群聊，统一按 conversation_id 查
  • 群消息发送/推送完全复用 M2 的 SendMessage / PushMessage
  • M3 只需写「群的生命周期管理」（建群/拉人/踢人/解散）

代码：internal/model/group_model/group_model.go、group_service

⭐⭐ 42. 建群为什么必须用事务？

简答：建群要写 4 处：会话、群、群主成员、其他成员。
不做事务会出现「有会话没群」「有群没群主」等脏数据。
global.DB.Transaction(func(tx *gorm.DB) error {...}) 里任一步失败整体回滚。

代码：CreateGroup

⭐ 43. 群成员人数怎么高效统计？

简答：在 groups 表冗余 member_count，加人/踢人时同步更新。
更新用 gorm.Expr("member_count + ?") 原子自增，避免「先读再写」的并发覆盖。

代码：AddMembers、RemoveMember

⭐⭐ 44. 并发拉人怎么防止超员？

简答：member_count + n > max_members 的校验有竞态（两个请求可能同时通过）。
解法：

  1. 事务里 SELECT ... FOR UPDATE 锁定群行（悲观锁）
  2. Redis 分布式锁
  3. 接受轻微超员（产品上可容忍）

代码：AddMembers（M3 用原子计数，上限校验仍有竞态，M4 加固）

⭐ 45. 群主退群怎么处理？

简答：群主不能直接退——否则群无人管理。
要么转让群主，要么先解散群。M3 简化：群主退群被拒绝，提示先解散。

代码：RemoveMember

⭐ 46. 群解散后数据怎么处理？

简答：软删除（groups.status=2 + 软删会话），保留消息和群记录便于审计/追溯。
不要物理删除。

代码：DissolveGroup

⭐ 47. 群消息扇出到 200 人怎么优化？

简答：

  • 现在：同步循环推送 200 次
  • 优化：goroutine 池并行推送、或 MQ 异步投递、或按在线用户分批
  • 注意慢消费者隔离（M2 的 Enqueue 已做）

十、并发与稳定性（M4）

⭐⭐ 48. 什么是优雅退出？要做哪些事？

简答：

  1. srv.Shutdown(ctx)：停止接收新请求，等待在途请求完成（带超时）
  2. 断开所有 WebSocket（Hub.CloseAll()），让客户端立即感知
  3. 释放 DB/Redis 连接
    顺序很重要：先停 HTTP（不再有新请求）→ 再关 WS → 最后关依赖。

代码：main.go、internal/ws/hub.go 的 CloseAll

⭐⭐ 49. 限流怎么做？固定窗口 vs 滑动窗口？

简答：

  • 固定窗口：每分钟计数，边界会翻倍突发
  • 滑动窗口：只统计「最近 60 秒」，边界平滑（本项目）
  • 令牌桶：允许突发到桶容量，长期按速率
  • 漏桶：恒定速率

本项目：内存 map + 时间列表 + 懒清理。单机；多实例要用 Redis。

代码：internal/middleware/ratelimit.go

⭐ 50. 如何控制并发数？

简答：带缓冲 channel 当信号量：

或用 golang.org/x/sync/semaphore、worker pool。

代码：internal/ws/push.go（群消息扇出限并发 16）

⭐ 51. 如何检测数据竞争？

简答：go test -race（需要 cgo + gcc）。原理是编译时插桩，记录内存访问的读写集合，
发现「并发读写同一地址且没有同步」就报告。
Linux/macOS 开箱即用，Windows 要装 MinGW/TDM-GCC。

⭐ 52. goroutine 泄漏怎么排查？

简答：

  • 常见泄漏：阻塞在 channel、网络 IO 没超时、ticker 没 Stop、启动 goroutine 后没人关
  • 排查：pprof goroutine 数量、runtime.NumGoroutine()
  • 预防：每个 goroutine 必须有退出路径（conn 关闭 / channel 关闭 / ctx 取消）

⭐ 53. 为什么锁里面不能做 IO？

简答：持锁做网络/IO 会阻塞其他 goroutine 获取锁，放大锁竞争，严重时整个服务卡住。
正确做法：持锁只做「读/复制数据」，释放锁后再做 IO。
SendToUser 就是先复制连接列表再释放锁。

十一、WebRTC 与通话（M5）

⭐⭐ 54. WebRTC 的原理？为什么是 P2P？

简答：WebRTC 让两个浏览器直接建立 UDP 连接传音视频，不经过服务器。
建立过程需要「信令」交换 SDP 和 ICE candidate，服务器只做信令转发，不碰媒体流。
好处：延迟低、服务器带宽成本低。

代码：internal/service/call_service、internal/ws/client.go 的 handleRelay

⭐⭐ 55. 信令服务器的作用？

简答：帮双方交换「怎么连」的信息：

  • SDP（offer/answer）：编解码、媒体类型、网络信息
  • ICE candidate：双方可能的网络路径
    服务器不解析这些内容，原样转发即可。

⭐ 56. SDP / ICE / STUN / TURN 分别是什么？

简答：

  • SDP：会话描述（编解码、媒体、网络）
  • ICE：候选地址收集 + 尝试连接的框架
  • STUN：发现自己的公网 IP:Port（NAT 映射）
  • TURN：打洞失败时的中继服务器（有带宽成本）

⭐⭐ 57. 通话状态机怎么设计？如何防重复接听？

简答：状态：呼叫中1/已接通2/已拒绝3/已取消4/已结束5/未接6。
状态迁移用条件更新：WHERE id=? AND callee_id=? AND status=1，RowsAffected=0 即拒绝。
和「接受好友申请」同一个套路，天然抗并发。

代码：call_service.go 的 Accept

⭐ 58. 通话时长怎么算？

简答：接通时记 started_at，挂断时 duration = now - started_at（秒）。
由服务端计算，避免客户端篡改。

十二、微服务与 gRPC（M6）

⭐⭐ 59. 为什么要拆微服务？单体有什么问题？

简答：单体问题：整包扩缩容、故障不隔离、团队协作冲突、改一行全量发布。
代价：分布式复杂度（网络失败、一致性、服务发现、追踪）。
本项目先单体跑通 M0–M5，再在 M6 拆——先体会痛点再拆。

⭐⭐ 60. 微服务怎么拆？

简答：按领域边界拆（用户域/聊天域），不是按技术分层（controller/service/dao 各一个服务是反模式）。
拆完每个服务独立部署、独立扩缩容，通过 gRPC 通信，对外统一走 gateway。

⭐⭐ 61. gRPC 和 REST 的区别？为什么内部用 gRPC？

简答：

  • gRPC：HTTP/2 + protobuf + 强契约（.proto）+ 支持四种流，性能高
  • REST：HTTP/1.1 + JSON + 契约弱（OpenAPI 可选）
  • 内部服务间用 gRPC（性能/契约），对外用 REST（浏览器友好）

⭐ 62. gRPC 四种调用方式？

简答：Unary（一请求一响应）、Server streaming、Client streaming、Bidirectional streaming。

⭐⭐ 63. gateway 的作用？

简答：协议转换（HTTP↔gRPC）、统一鉴权、限流、聚合。
内部服务不直接对外，鉴权在 gateway 做，降低每个服务的重复工作。

⭐ 64. 微服务带来的新问题？

简答：服务发现、超时/重试、熔断、链路追踪、跨服务数据一致性。

⭐ 65. 本项目 gRPC 为什么用 JSON codec？

简答：本机没有 protoc/buf，所以用 gRPC 自定义 codec（传输层仍是真 gRPC）。
换 protobuf 只需替换 codec 和生成代码，架构不变——说明微服务核心是「服务边界 + 契约」，不是序列化格式。

十三、消息队列（M7）

⭐⭐ 66. 为什么需要消息队列？

简答：解耦、削峰、异步、最终一致性。
本项目：发消息不再同步查成员+逐个推送，而是写 outbox 后异步推送。

⭐⭐ 67. 本地消息表（Outbox）解决什么问题？

简答：「落库」和「发 MQ」无法原子。
做法：业务事务里同时写业务数据 + outbox 记录（原子）；后台 worker 轮询 outbox 发 MQ 并标记已发送。
保证：即使 MQ 暂时挂了，消息也不会丢（worker 重试）。

⭐⭐ 68. 如何保证消息不丢？

简答：持久化队列 + 持久化消息 + 手动 ack + 生产者确认（publisher confirm）。
本项目用了前三项。

⭐⭐ 69. 如何保证消息不重复？

简答：MQ 是「至少一次」投递，消费方必须幂等：去重表/唯一索引/消息 id。
本项目消费动作是「推送给在线用户」，重复推影响小；如果是加积分就必须严格去重。

⭐ 70. 消息积压怎么办？

简答：加消费者/扩容、优化消费逻辑、死信队列、限流上游。

⭐ 71. 最终一致性 vs 强一致？

简答：跨服务无法用本地事务。方案：2PC（强一致但重）、Saga（补偿）、TCC（三阶段）、本地消息表（最简单）。
本项目用本地消息表。

⭐ 72. MQ 挂了系统怎么办？

简答：降级。本项目：global.MQ.Enabled == false 时改回同步推送，功能不中断。

十四、结语

以上 72 题覆盖了 gochat 从认证、好友、单聊、群聊、并发、WebRTC、微服务到消息队列的全部核心知识点。
建议：先能讲清楚每个模块「解决什么问题、怎么解决、有什么坑」，再背细节。
