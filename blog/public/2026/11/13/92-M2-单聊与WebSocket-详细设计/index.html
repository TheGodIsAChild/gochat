二、数据模型：会话 + 消息 + 成员

2.1 为什么单聊和群聊共用一张会话表

  • 单聊：Type=1，两个成员
  • 群聊：Type=2，多个成员（M3 复用同一套表）

好处：消息表不需要区分单聊/群聊，统一按 conversation_id 查。

2.2 为什么会话冗余最后消息

conversations.last_message_id / last_message_at

如果会话列表要展示”最后一条消息”，每次都去 messages 按 conversation_id 查最新一条，数据量大时很慢。
把最后消息信息冗余到会话行 → 列表查询变成一次简单查询（空间换时间）。

2.3 未读数怎么算

conversation_members.last_read_message_id 记录”我读到哪了”。

标记已读 = 更新 last_read_message_id（只前进不后退）。

比单独建 message_reads 表简单，M2 先用这个方案。

三、消息幂等（重点）

问题

网络重试、用户连点、WS 重发都会导致同一条逻辑消息被发送多次。

方案：客户端生成唯一 client_msg_id

服务端处理：

  1. 先查 (sender_id, client_msg_id) 是否已存在 → 存在直接返回（重复请求返回同一条）
  2. 不存在 → 插入
  3. 并发下两个请求同时插入 → 唯一索引让第二个报 Duplicate
  4. 捕获 gorm.ErrDuplicatedKey → 再查一次返回已有消息

结果：无论客户端重试多少次，数据库里只有一条消息。

配套：TranslateError: true

GORM 配置里开启 TranslateError，把 MySQL 的 Duplicate entry 错误翻译成 gorm.ErrDuplicatedKey，
这样业务代码用 errors.Is(err, gorm.ErrDuplicatedKey) 判断，不用匹配错误字符串。

四、分页：为什么用游标不用 offset

返回时把倒序结果翻转成正序，前端直接渲染。

五、WebSocket 架构（M2 最核心）

5.1 三个角色

5.2 为什么读写分离

gorilla/websocket 不允许并发写。如果多个 goroutine 同时写同一个连接会 panic。
所以：

  • ReadPump：唯一从 socket 读的 goroutine
  • WritePump：唯一往 socket 写的 goroutine
  • 其他 goroutine 想发消息 = 往 Client.send channel 里塞数据

5.3 Hub 的并发安全

  • Hub 被「连接建立/断开」和「消息推送」多个 goroutine 同时访问 → 必须加锁
  • 读写锁：读多写少，比 Mutex 性能好
  • SendToUser 里先把连接列表复制出来，再释放锁发送，避免持锁做 IO

5.4 心跳机制

作用：清理「网线拔了但 TCP 没断」的僵尸连接。

5.5 慢消费者隔离

如果客户端很慢，send channel 满了，直接阻塞会拖垮推送方（可能是给其他用户推消息的 goroutine）。
用 non-blocking 写 + 断开慢连接，保证一个慢客户端不影响其他人。

这是消息系统「慢消费者」问题的通用解法（Kafka/RabbitMQ 里也有类似思路）。

5.6 推送路径统一

HTTP 发消息 和 WS 发消息，最终都要「推送给会话所有在线成员」。
所以抽出 ws.PushMessage(convID, item)：

  • HTTP handler 发完消息调用
  • WS 的 handleText 发完消息也调用

为什么放 ws 包而不是 service：service 不应该依赖 WebSocket（M6 拆 gRPC 时没有 WS）。

六、鉴权：WS 怎么带 token

浏览器 WebSocket API 不能自定义请求头（不能带 Authorization）。
所以：

服务端在升级连接之前先校验 token，非法直接 401，不浪费连接资源。
（同时兼容非浏览器客户端的 Authorization: Bearer。）

七、在线状态与离线消息

在线状态

  • Hub 里 IsOnline(userID) 判断是否在线
  • 接口：GET /api/v1/online?ids=1,2,3 → {"online_ids":[1]}

M2 是单机内存；M4/M6 多实例要改成 Redis（每个实例写入在线用户 + TTL 续期）。

离线消息

不需要单独的表：

  • 消息已经落库到 messages
  • 用户上线后通过 GET /conversations/:id/messages 拉历史
  • 通过 unread 计数知道有多少没读

这就是”离线消息”的标准做法：持久化 + 上线拉取 + 未读数。

九、注意点清单

  1. gorilla/websocket 不能并发写 → 写操作只在 WritePump
  2. WS 的 ctx 用 context.Background()：连接生命周期远长于 HTTP 请求
  3. Hub 持锁时不要做 IO/channel 操作 → 先复制连接列表再发
  4. 慢消费者要断开，不能阻塞推送方
  5. WS 鉴权在 Upgrade 之前，别升级完再校验
  6. CheckOrigin 生产环境必须校验，否则有 CSWSH 跨站 WebSocket 劫持
  7. 消息 ID 用自增：单库单表够用；分库分表时要用雪花算法/号段
  8. 未读数是 N 次 count，会话多时要优化（Redis 计数）
  9. 游标分页不要用 offset
  10. client_msg_id 必须由客户端生成，服务端不能自己造（否则重试无法幂等）

十、面试点（M2）

  1. WebSocket 和 HTTP 长轮询/SSE 有什么区别？为什么 IM 用 WebSocket？
  2. 为什么 WebSocket 要读写分离？gorilla/websocket 并发写会怎样？
  3. 心跳机制解决什么问题？ping/pong 怎么做？
  4. 如何管理大量 WebSocket 连接？Hub 怎么设计？多实例怎么办？
  5. 消息怎么保证不重复？（client_msg_id + 唯一索引）
  6. 消息乱序怎么办？（服务端 ID 递增 + 客户端按 ID 排序）
  7. 离线消息怎么实现？（持久化 + 上线拉取 + 未读数）
  8. 游标分页 vs offset 分页？
  9. 慢消费者怎么处理？（有界队列 + 断开）
  10. WS 怎么鉴权？（query token，因为浏览器 WS 不能带 header）
  11. 未读数怎么高效计算？（last_read_message_id vs Redis 计数）

十一、下一步（M3 群聊）

M3 会复用 M2 的「会话 + 消息 + 成员」模型，只需：

  • 建 groups 表（群信息）
  • 建群：创建 conversation(Type=2) + 群主成员
  • 加群 / 退群 / 踢人
  • 群消息：发送时推送给所有成员（M2 的 PushMessage 已经支持！）
  • 群里成员多时要注意扇出性能（M4 并发专题）
