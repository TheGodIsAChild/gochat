场景集：30 个业务场景怎么实现

从项目里提炼的关键业务场景：问题 → 处理方案 → 代码位置 → 关键点。
用途：面试讲项目时按场景展开，或排查/扩展功能时对照。

M1 · 认证与好友

场景 1：用户注册

问题：注册要保证「用户名唯一」，并同时创建默认设置。

方案：

  1. 先查用户名是否已存在（友好提示）
  2. bcrypt 加密密码
  3. 事务：插入 users + user_settings

代码：internal/service/user_service/register_service.go

关键点：

  • 查重不是安全边界，唯一索引才是并发兜底
  • 密码永远不存明文，PasswordHash 字段 json:"-" 防泄露
  • 用户和设置必须成对出现 → 事务

场景 2：用户登录（签发双 token）

问题：登录成功要发 access + refresh 两个 token，并让 refresh 可撤销。

方案：

  1. 按 username 查用户，查不到 → 统一提示”用户名或密码错误”（防枚举）
  2. bcrypt 校验密码
  3. 检查账号禁用状态
  4. 签 access（2h，type=access）
  5. 签 refresh（30d，type=refresh，带 jti）
  6. SET refresh:{uid}:{jti} 1 EX 30d 存 Redis
  7. 更新 last_login_at（非关键，失败不影响登录）

代码：internal/service/user_service/login_service.go

关键点：

  • 不暴露”用户是否存在”
  • Redis TTL 必须与 refresh 的 exp 对齐
  • SaveRefresh 失败要整体失败（否则用户能登录但永远刷新不了）

场景 3：access token 过期 → 无感刷新

问题：access 2 小时过期，用户不能被踢下线。

方案（客户端拦截器驱动）：

  1. 请求返回 401
  2. 客户端用 refresh token 调 /token/refresh
  3. 服务端：验签 → type=refresh → GETDEL 消费旧 jti → rotation 签发新 token 对 → 存新 jti
  4. 客户端用新 access 重试原请求

代码：internal/service/user_service/refresh_service.go

关键点：

  • GETDEL 原子消费，防并发双签发
  • rotation：每次刷新换新 refresh，旧作废
  • 旧 jti 不存在 → 复用检测 → 撤销该用户全部 refresh

场景 4：并发刷新（5 个请求同时 401）

问题：客户端同时发多个 refresh，rotation 会让第二个请求用旧 token → 触发复用检测 → 用户被强制下线。

方案：

  1. 客户端 single-flight：刷新进行中，其他请求等待同一结果（治本）
  2. 服务端 GETDEL 防双签发
  3. 宽限期：消费 jti 时打一个 60s 的 used:{jti} 标记，宽限期内的重复请求不触发撤销
  4. （进阶）缓存「旧 jti → 新 token 对」实现幂等刷新

代码：internal/service/user_service/refresh_service.go（简化版）

关键点：

  • 这是双 token + rotation 的经典坑
  • 面试可以讲：problem → 为什么误判 → 三层解法

场景 5：登出

问题：JWT 无状态，怎么让 refresh 立即失效？

方案：客户端带 refresh token 调用 /logout，服务端解析出 jti 后 DEL refresh:{uid}:{jti}。
登出是幂等的（删不存在的 key 也算成功）。

代码：internal/service/user_service/logout_service.go

场景 6：发好友申请

问题：要拦住各种非法加好友。

方案（6 条规则）：

  1. 不能加自己
  2. 目标用户必须存在
  3. 不能已是好友
  4. 不能重复发待处理申请（已拒绝可重发）
  5. 对方拉黑了我 → 拒绝（模糊提示）
  6. 对方关闭「允许加好友」

落库时：有旧申请行就复用（重置为待处理），没有才插入（避开唯一索引）。

代码：internal/service/friend_service/friend_service.go 的 SendRequest

关键点：

  • 先查后写有竞态，唯一索引兜底
  • 唯一索引 + 复用旧行 = 同一对用户永远只有一行申请记录

场景 7：接受好友申请（事务 + 抗并发）

问题：接受申请要「改状态 + 插两条好友关系」，且要防重复接受。

方案：

代码：internal/service/friend_service/friend_service.go 的 AcceptRequest

关键点：

  • 条件更新让「判断+修改」原子化
  • 双向两行必须同事务
  • 软删除后重新加好友要复用旧行（upsertFriendship）

场景 8：删除好友后重新加回

问题：删除好友是软删（status=2），重新加好友会撞唯一索引。

方案：

  1. 发申请时：复用旧的 friend_requests 行（重置 status=0）
  2. 接受时：upsertFriendship 用 Unscoped() 查到旧行，恢复 status=1 和 deleted_at=null

代码：SendRequest、upsertFriendship

关键点：

  • 实测：重新加回后 friendship_id 不变，说明是恢复不是重复插入
  • 面试点：软删除 + 唯一索引的组合坑

场景 9：拉黑 / 取消拉黑

问题：拉黑要幂等；取消后还能重新拉黑。

方案：

  • 拉黑：INSERT ... ON CONFLICT DO NOTHING（clause.OnConflict{DoNothing:true}）→ 重复拉黑不报错
  • 取消：物理删除（Unscoped().Delete）→ 否则软删行会挡住下次拉黑

代码：internal/service/friend_service/friend_service.go 的 AddBlacklist、RemoveBlacklist

关键点：

  • “开关型”数据用物理删除更简单
  • OnConflict DoNothing 是幂等写入门槛最低的做法

场景 10：修改资料（部分更新）

问题：用户只改昵称，不能把头像/签名清空。

方案：

  • 请求结构体用指针：Nickname *string → nil 表示没传
  • 服务层用 map[string]any 组装要更新的字段
  • Updates(map) 不会忽略 false/0/""

代码：internal/service/user_service/user_update_service.go

关键点：

  • GORM 零值陷阱
  • 指针 / map / Select 三种解法

场景 11：好友列表 / 申请列表（避免 N+1）

问题：列表要展示对方的昵称/头像，但不能每条查一次。

方案：

  1. 查关系表拿到一批 friend_id / from_user_id
  2. 收集 id → WHERE id IN (...) 一次查 users
  3. 内存里 map 关联组装

代码：ListFriends、ListIncomingRequests（friend_service.go）

关键点：

  • 2 次查询 vs 1+N 次
  • 慢查询日志 / ORM 日志可以发现 N+1

场景 12：用户搜索

问题：加好友前要先找到人。

方案：(username LIKE %kw% OR nickname LIKE %kw%) AND id <> self LIMIT 20
只返回公开字段（id/username/nickname/avatar/gender）。

代码：internal/service/user_service/user_search_service.go、SearchUsers handler

关键点：

  • 排除自己、限制条数
  • LIKE '%x%' 不走索引（面试点）
  • 线上要限流防批量扫用户

M2 · 单聊与实时消息

场景 13：创建单聊会话

问题：A、B 之间只能有一个单聊会话；双方谁先点开都要落到同一个 conversation。

方案：

  1. conversation_members 自连接查「同一个 conversation 下同时存在这两个 user」
  2. 存在 → 直接返回；不存在 → 事务创建 conversation + 两个成员

代码：internal/service/chat_service/conversation_service.go 的 CreateOrGetSingleConversation

关键点：

  • 单聊/群聊共用 conversations 表，所以不能用「存两个 user_id」的方式判断
  • 并发创建可能产生重复会话（M4 用唯一键/分布式锁解决）

场景 14：发送消息（幂等）

问题：网络重试/连点会导致同一条消息被发多次。

方案：

  1. 客户端生成 client_msg_id
  2. 先查 (sender_id, client_msg_id) → 存在直接返回
  3. 不存在 → 事务：插消息 + 更新会话 last_message_id/at
  4. 并发插入撞唯一索引 → 捕获 gorm.ErrDuplicatedKey → 再查返回

代码：internal/service/chat_service/message_service.go 的 SendMessage

关键点：

  • UNIQUE(sender_id, client_msg_id) 是幂等的根基
  • TranslateError: true 让 Duplicate 错误可用 errors.Is 判断
  • 消息 + 会话冗余字段必须同事务

场景 15：拉取历史消息（分页）

问题：消息多，不能一次全拉；翻页不能错位。

方案：游标分页 WHERE conversation_id=? AND id < before_id ORDER BY id DESC LIMIT n，
返回时翻转成正序。

代码：ListMessages

关键点：

  • 不用 offset（越翻越慢、新消息导致错位）
  • 先校验成员身份，防越权

场景 16：WebSocket 实时推送

问题：消息要实时到达在线用户。

方案：

  1. 客户端连 ws://host/ws?token=<access>，服务端校验 token 后升级
  2. 注册到 Hub（userID → 多个连接）
  3. 发消息成功后，ws.PushMessage 查会话成员 → 逐个 SendToUser
  4. 不在线的成员无需处理（消息已落库，上线拉历史）

代码：internal/ws/hub.go、client.go、push.go、handler.go

关键点：

  • 读写下分离（gorilla 不能并发写）
  • 心跳清理僵尸连接
  • 慢消费者有界队列 + 断开
  • HTTP 发消息和 WS 发消息共用同一个 PushMessage

场景 17：在线状态查询

问题：前端要显示好友是否在线。

方案：Hub 内存里 IsOnline(userID)；接口 GET /api/v1/online?ids=1,2。

代码：internal/ws/hub.go、chat_api.go 的 GetOnlineStatus

关键点：

  • M2 单机内存；多实例要用 Redis + TTL
  • 多端登录时「有任一连接在线」即算在线

场景 18：离线消息

问题：用户不在线时别人发的消息，上线后要能看到。

方案：消息落库（messages）+ 上线拉历史 + last_read_message_id 算未读。
不需要单独的离线消息表/队列。

代码：SendMessage、ListMessages、ListConversations

关键点：

  • “离线消息”本质是”持久化 + 拉取 + 未读数”
  • 未读数在会话列表里直接返回

M3 · 群聊

场景 19：建群

问题：建群要同时创建会话、群信息、成员，且不能出现半成品。

方案：事务里依次：

  1. 创建 conversations（Type=2）
  2. 创建 groups（关联 conversation_id，member_count=成员数）
  3. 插入群主（Role=1）和其他成员
  4. 校验用户存在、去重、人数上限

代码：internal/service/group_service/group_service.go 的 CreateGroup

关键点：

  • 群聊复用 M2 的会话/消息模型
  • 事务边界 = 建群这个完整业务动作

场景 20：拉人进群 / 踢人 / 退群

问题：成员变更要维护成员表 + 人数冗余，还要做权限控制。

方案：

  • 拉人：任何成员可拉；跳过已在群里的；校验上限；事务插成员 + member_count + n
  • 踢人：只有群主；事务删成员 + member_count - 1
  • 退群：自己退；群主不能直接退

代码：AddMembers、RemoveMember

关键点：

  • 计数用 gorm.Expr 原子操作
  • 权限校验：群主校验 + 成员校验都要做

场景 21：改群资料 / 解散群

问题：群资料和解散是敏感操作，只有群主能做。

方案：

  • 改群名/公告：校验 owner_id == operator，用 map 部分更新
  • 解散：status=2 + 软删会话

代码：UpdateGroup、DissolveGroup

关键点：

  • 软删除保留审计数据
  • 解散后 getGroupByID 会因 status 过滤返回「群不存在或已解散」

场景 22：群消息

问题：群消息要发给所有成员。

方案：完全复用 M2：

  • chatservice.SendMessage(convID, ...) 落库
  • ws.PushMessage(convID, item) 查群成员逐个推送

代码：chat_service + ws/push.go

关键点：

  • 群消息不需要新代码
  • 成员多时扇出放大 → M4 优化

M4 · 并发与稳定性

场景 23：优雅退出

问题：进程被 kill 时请求被硬切断、WS 连接没通知、DB 连接没释放。

方案：

  1. http.Server + signal.Notify(SIGINT,SIGTERM)
  2. 收到信号 → srv.Shutdown(10s 超时)
  3. ws.DefaultHub.CloseAll() 断开 WS
  4. core.CloseBaseServices() 释放 DB/Redis

代码：main.go

关键点：

  • 顺序：HTTP → WS → DB
  • Shutdown 必须带超时

场景 24：接口限流

问题：登录/注册/搜索可被批量刷。

方案：滑动窗口限流中间件（内存 map + 懒清理），按 IP 计数。

  • 登录/注册：20 次/分钟
  • 搜索：30 次/分钟

代码：internal/middleware/ratelimit.go

关键点：

  • 滑动窗口避免固定窗口的边界突发
  • 单机内存局限，多实例要 Redis

场景 25：群消息扇出

问题：200 人群一次消息要推 200 次，无脑起 goroutine 会瞬间膨胀。

方案：小会话顺序推送；大会话并发推送 + 信号量限制并发数（16）。

代码：internal/ws/push.go

关键点：

  • 信号量（带缓冲 channel）控制并发
  • 慢消费者隔离（有界队列 + 断开）

场景 26：并发安全的连接管理

问题：Hub 被多个 goroutine 并发读写。

方案：sync.RWMutex + 持锁只复制数据、释放后再 IO；单元测试并发验证。

代码：internal/ws/hub.go、hub_test.go

关键点：

  • 读写锁适合读多写少
  • -race 检测数据竞争（需 cgo）

M5 · 语音通话信令

场景 27：发起 / 接听 / 挂断通话

问题：双方要建立 WebRTC 连接，需要交换 SDP/ICE；同时要有通话状态和记录。

方案：

  1. 主叫 call_invite → 服务端建 call 记录（status=呼叫中）→ 推 call_incoming 给被叫
  2. 被叫 call_accept → 条件更新 status=已接通、记 started_at → 双方收到 call_accepted
  3. 双方通过 webrtc_offer/answer/ice 交换连接信息（服务端原样转发 + from_user_id）
  4. 任一方 call_end → 条件更新 status=已结束、算 duration → 对方收到 call_ended

代码：call_service.go、ws/client.go 的 handleCall*

关键点：

  • 服务器不传音视频，只转发信令
  • 状态迁移用条件更新防连点
  • 信令复用 M2 的 WebSocket 长连接

场景 28：查询通话记录

问题：用户要看到历史通话（谁打给谁、多久、什么状态）。

方案：GET /api/v1/calls 按时间倒序返回我的通话（作为主叫或被叫），用 CallItem DTO。

代码：call_service.ListHistory、call_router

关键点：

  • 越权校验：只有通话双方能看
  • DTO 避免暴露 GORM 内部字段

M6 · 微服务化

场景 29：HTTP gateway → gRPC 微服务

问题：单体里 service 直接调用；拆开后需要跨进程调用，还要统一鉴权入口。

方案：

  1. 按领域拆：user service(:9001)、chat service(:9002)
  2. gateway 保留 HTTP 入口，鉴权后通过 gRPC 调内部服务
  3. gRPC 用自定义 JSON codec（无 protoc 环境）
  4. 错误码映射：gRPC NotFound → HTTP 502（带原始信息）

代码：internal/grpcx/、internal/router/rpc_router/

关键点：

  • 按领域拆，不按技术层
  • gateway 做协议转换 + 鉴权 + 限流
  • 服务地址来自配置（生产用服务发现）

M7 · 消息队列与最终一致性

场景 30：消息异步投递（Outbox 模式）

问题：发消息要「落库 + 推送给所有在线成员」，同步做会让请求变慢，且 MQ 和 DB 无法原子。

方案：

  1. SendMessage 事务里：写 messages + 更新 conversations + 写 outbox(status=0)
  2. OutboxWorker 每 2s 轮询 status=0 → 发 RabbitMQ → 标 status=1（失败重试）
  3. Consumer 消费 → 解析事件 → ws.PushToConversation 推送
  4. MQ 不可用时降级为同步推送

代码：internal/outbox/、internal/mq/mq.go、message_service.go

关键点：

  • outbox 必须在业务事务内写
  • 至少一次投递 → 消费需幂等
  • MQ 要可降级
  • amqp.Table 不支持 uint（踩坑记录）
