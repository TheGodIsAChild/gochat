术语表：45 个必懂概念（小白友好）

读技术文章最痛苦的是：每个字都认识，连起来不知道在说什么。
这篇把项目里出现的所有术语，用「一句话 + 一个生活类比 + 项目里在哪」讲清楚。
建议先扫一遍，读文章时遇到不懂的词回来查。

一、认证与安全（8 个）

术语 一句话解释 生活类比 项目里在哪
认证 你是谁（登录） 进小区刷门禁卡 /login
鉴权 你能不能做这件事（权限） 门禁卡只能开你家门，不能开别人家 middleware.Auth()
JWT 一种「自带签名的身份凭证」，服务端不用存 演唱会门票：票面信息 + 防伪码，检票员看防伪码就知道真假 auth/jwt.go
access token 短期通行证，每次请求都带上 公司临时访客卡，2 小时失效 请求头 Authorization: Bearer
refresh token 长期凭证，只用来换新的 access 身份证：平时不带出门，卡片过期了拿它去换 /token/refresh
jti JWT 的唯一编号，用来在服务端做「黑名单」 门票编号，挂失时按编号作废 auth/token_store.go
bcrypt 一种密码哈希算法，加密慢且每次结果不同 把肉绞成肉馅：能验证是牛肉，但绞不回去 auth.Hash()
salt（盐） 加密时混入的随机值，让同密码结果不同 每份菜加不同的调味粉，别人无法批量对照 bcrypt 内部

小白最容易问：JWT 和 session 有什么区别？

JWT（本项目） Session
状态存哪 客户端（token 里） 服务端内存/Redis
服务端要存吗 不存（无状态） 要存
好处 多实例部署简单、不占服务端内存 能立刻踢人下线
坏处 天然无法撤销（所以要搞 refresh 白名单） 服务端有状态、扩容要共享存储

二、网络与实时通信（10 个）

术语 一句话解释 生活类比 项目里在哪
HTTP 「请求-响应」式协议，客户端问一次服务端答一次 寄快递：寄一次、等一次回执 所有 /api/v1/*
WebSocket 建立一次连接后双向持续通信 打电话：接通后双方随时能说话 /ws
握手 / 101 WebSocket 借用 HTTP 发一个「升级」请求，服务端返回 101 Switching Protocols 打电话前先说”喂，方便吗”，对方说”方便” ws/handler.go
心跳 ping/pong 定期互相发小包，证明”我还活着” 每隔几秒问一句”在吗”，没回应就挂断 ws/client.go 常量
轮询 客户端每隔 N 秒问一次”有新消息吗” 每隔 5 秒去门口看快递到没到 本项目不用
长轮询 请求挂住不返回，直到有新消息或超时 站在门口等，快递到了立刻告诉你 本项目不用
SSE 服务端单向推流的 HTTP 方案 广播电台：只能听，不能说 本项目不用
SDP 描述”我支持什么音视频格式、我的网络地址”的文本 两个人交换”我会说普通话、我住哪” WebRTC 呼叫时交换
ICE candidate 一个「可能的网络路径」，双方各收集一堆后逐个尝试 互相给对方一串电话号码，挨个拨，哪个通就用哪个 webrtc_ice 消息
STUN / TURN STUN 帮你查出自己的公网地址；TURN 打洞失败时做中转 STUN=问”我在外面看起来是什么地址”；TURN=打不通就找个中间人转话 本项目本地演示只走 host 直连

三、数据库（11 个）

术语 一句话解释 生活类比 项目里在哪
事务 一组操作「要么全成功，要么全回滚」 银行转账：扣钱和加钱必须一起成功 register_service.go
回滚 事务中途失败，把已做的操作撤销 转账失败，扣的钱退回来 Transaction(func(tx)...) 返回 error
索引 给某列建一个”目录”，查询不用全表扫描 书的目录：不用一页页翻 SHOW INDEX FROM messages
唯一索引 索引 + 不许重复 身份证号：全国唯一 uk_username
复合索引 多个列组合成一个索引 按「省+市」排序的电话簿 uk_conv_user(conversation_id, user_id)
最左前缀 复合索引只能从最左列开始用 电话簿按「省+市」排，只查”市”就查不了 idx_to_status(to_user_id, status)
软删除 不真删，只打一个”已删除”标记 员工离职：档案还在，只是标记”离职” status=2 / deleted_at
条件更新 把「判断」和「修改」写成一条 SQL，避免并发插队 抢票：只有余票>0 才扣（判断和扣减一步完成） WHERE status = 0 + RowsAffected
乐观锁 不加锁，靠”条件不满足就失败”来防冲突 抢座位：坐下前再确认一次空位 条件更新
悲观锁 直接锁住行，别人等着 进试衣间先锁门 SELECT ... FOR UPDATE（本项目未用）
N+1 查询 列表 1 次查询 + 每条记录各 1 次 = N+1 次 查 20 个订单，每个订单都单独跑一趟仓库 用 WHERE id IN (...) 批量查

小白最容易混：offset 分页 vs 游标分页

offset 分页 游标分页（本项目）
写法 LIMIT 20 OFFSET 1000 WHERE id < 5000 LIMIT 20
速度 越翻越慢（要跳过 1000 行） 恒定
新消息插入 会错位/重复 不受影响
类比 从第 1 页数到第 51 页 从折角那页继续读

四、并发（10 个）

术语 一句话解释 生活类比 项目里在哪
goroutine Go 的”轻量线程”，几 KB 就能起一个 一个员工可以同时干好几件事 每请求一个、每连接两个
channel goroutine 之间传数据的”管道” 传送带：一个往上放，一个往下取 send chan []byte
有缓冲 channel 管道带储物格，放满才阻塞 快递柜：有格子就放，满了才等 make(chan []byte, 64)
Mutex 一把锁，同一时刻只能一个人进 厕所门锁 保护 map
RWMutex 读写锁：读可以多人同时，写只能一个 图书馆：很多人可以同时看书，但上架时要清场 Hub.mu
数据竞争 两个 goroutine 同时读写同一变量，结果不确定 两个人同时改同一份文档，谁覆盖谁看运气 go test -race 检测
死锁 双方各持一把锁等对方释放，永远等下去 两个人过独木桥，互不相让 锁里做 IO 容易触发
goroutine 泄漏 goroutine 永远阻塞，内存一直涨 员工卡在等一个永远不来的电话 缺超时/缺退出路径
信号量 限制”同时最多 N 个”的计数器 停车场：车位满了就在门口等 pushSem chan struct{}
扇出（fanout） 一条消息发给多个接收者 群发短信 群消息推给 200 人

小白最容易问：为什么说「锁里不能做 IO」？

想象你拿着厕所钥匙（锁），却在里面排队等外卖（IO）。外面所有人都进不来，队伍越排越长。
正确做法：锁只用来”改一下名单”（内存操作），改完立刻释放，然后再去做耗时的推送。

五、架构与工程（12 个）

术语 一句话解释 生活类比 项目里在哪
分层 代码按职责分成 handler / service / model 餐厅：服务员只点单，厨师只做菜，采购只进货 全项目
中间件 在请求到达业务前统一做一件事（鉴权/限流/日志） 进公司先过安检 middleware/
gateway（网关） 对外的统一入口，内部服务不直接暴露 公司前台：所有访客都先到前台 :8080
gRPC 服务之间高性能的二进制 RPC 协议 内部专线电话：快、格式固定 internal/grpcx/
微服务 按业务拆成多个独立服务 大公司拆成多个部门，各管一摊 user / chat 服务
消息队列（MQ） 把「要做的事」放进队列，异步处理 点外卖：下单后不用站在窗口等，做好了通知你 RabbitMQ
Outbox（本地消息表） 把「要发 MQ」先写进数据库，后台再可靠补发 先把待办写在便利贴上，再一条条执行 outbox_messages
最终一致性 不要求立刻一致，但一段时间后一定会一致 转账短信可能晚 3 秒到，但一定会到 MQ 异步推送
幂等 同一个操作执行多次，结果和执行一次相同 电梯按钮：按 1 次和按 5 次，电梯都只来一次 client_msg_id
降级 某个依赖挂了，用更差但可用的方式顶上 电梯坏了，走楼梯（慢但能到） MQ 挂了走同步推送
限流 限制单位时间内的请求数 景区限流：每小时只放 500 人 RateLimit(20, time.Minute)
熔断 下游持续失败时，直接快速失败，不再重试 电话一直打不通，就先不发消息了，过会儿再试 本项目未做
慢消费者/背压 消费者处理不过来时，不能把生产者拖死 传送带末端的人太慢，不能卡住整条线 Enqueue 队列满就断开

六、六大核心概念只用一句话说清

面试时如果紧张，先记住这 6 句：

  1. JWT：自带签名的身份凭证，服务端不用存，所以「登出」要靠 refresh 白名单实现。
  2. 双 token：access 短命负责安全，refresh 长命负责体验，靠无感刷新兼得。
  3. 幂等：用 client_msg_id + 唯一索引，重发不会产生两条消息。
  4. WebSocket 读写分离：gorilla 不允许并发写，所以所有写都交给一个专门的 goroutine。
  5. 唯一索引是并发最后防线：「先查后插」有并发窗口，数据库约束才是真的。
  6. Outbox：落库和发 MQ 无法一个事务完成，所以先写数据库，后台再补发。
