接到需求怎么动手：标准开发流程 9 步

新手最常问：「我知道语法，但拿到需求不知道从哪下手。」
本文给一套可复用的 9 步流程，并用「消息撤回」这个真实需求完整走一遍。

一、9 步流程总览

顺序很重要：先想清楚「数据长什么样、接口长什么样」，再写代码。
反过来（先写 handler）会导致反复返工。

二、第 1 步：读懂需求（问出隐藏约束）

需求：「用户能撤回自己发的消息，2 分钟内。」

要追问的隐藏问题：

问题 影响
撤回后对方还能看到吗？ 显示「已撤回」提示 vs 直接消失
超过 2 分钟怎么办？ 返回什么错误
群主能撤回别人消息吗？ 权限模型
撤回要不要记审计？ 是否软删
撤回后未读数要不要减？ 数据一致性

经验：需求里没写清楚的，就是将来要返工的地方。

五、第 4 步：定接口

接口设计三问：

  1. 资源是什么？（message）→ URL 用名词
  2. 动作是什么？（撤回）→ 用 POST + 子路径
  3. 失败怎么区分？（业务错误 vs 系统错误）→ 统一 code + message

六、第 5 步：写 service（核心）

这段代码体现的 5 个开发思路：

  1. 先查后判：先拿到数据，再校验权限/时间
  2. 错误分层：业务错误用 errors.New，系统错误用 %w 包装
  3. 幂等：条件更新而不是「先查 status 再 update」
  4. 软删：改状态不删数据（IM 要可追溯）
  5. 副作用异步化：通知走 MQ，不阻塞返回

七、第 6 步：写 handler

handler 只做三件事：取参数 → 调 service → 写响应。不做业务判断。

八、第 7 步：接路由 + 配置权限

priv 组已经挂了 middleware.Auth()，所以自动要求登录。

检查清单：

  • 路由放在公开组还是鉴权组？
  • 需不需要额外限流？
  • 前端有没有对应按钮？

九、第 8 步：自测

自测要覆盖：正常路径、权限拒绝、幂等重试、边界（时间窗口）。

十、第 9 步：补文档 + 提交

  • 更新接口文档（README 的 API 表）
  • 如果是重要功能，写一段设计说明
  • git commit -m "feat(chat): 消息撤回（2 分钟窗口 + 权限校验 + 幂等）"

十一、这套流程的通用性

需求 复用这套流程的方式
消息已读回执 表用 last_read_message_id（已有）→ 新接口 → 推送
群公告 groups 表加字段 → 改群信息接口扩展
好友分组 friend_groups 表已有 → 接口 + 前端
消息搜索 新查询 + 索引/ES，不用改写入链路
拉黑后禁止发消息 在 SendMessage 里加一层校验

核心：先看「数据模型支不支持」，再看「接口怎么设计」，最后写代码。

十二、新手最容易犯的 5 个错

错误 后果
不追问需求直接写 返工
先写代码后想数据模型 改表改到崩溃
业务逻辑塞 handler 无法复用/测试
只测正常路径 上线被边界情况打脸
不做幂等 用户连点产生脏数据

十三、面试问法

  1. 接到一个需求你的开发流程是什么？
  2. 怎么判断要不要加表/加字段？
  3. 接口设计要考虑哪些方面？
  4. 你怎么保证接口幂等？
  5. 你怎么自测？只测正常路径吗？
  6. 需求不明确时你会怎么办？
