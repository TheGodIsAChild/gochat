数据库表设计：12 张表逐张讲清楚

表设计不是「把字段列出来」，而是用数据库的约束表达业务规则。
本文逐张表讲：为什么有这张表、每个字段干嘛、索引为什么这么建，并附上项目真实的 GORM 模型代码。

一、设计表之前先想清楚 3 件事

1. 这张表描述的是什么「东西」

一个表 = 一类实体。如果你想不出「它描述什么」，大概率是表拆错了。

2. 哪些规则必须由数据库保证

规则 用数据库保证（强） 只用代码保证（弱）
用户名唯一 UNIQUE 索引 先查后插（有并发窗口）
消息不重复 UNIQUE(sender_id, client_msg_id) 查重（并发会漏）
好友关系成对 事务 分两次插入（可能只成功一半）

结论：唯一性、成对性，能交给数据库就交给数据库。

3. 哪些场景要读得快

列表页（会话列表、好友列表）是最高频的查询，需要专门为它设计索引或冗余字段。

三、逐域拆解

3.1 用户域

users

字段 类型 说明
id BIGINT PK 自增
username VARCHAR(32) UNIQUE 登录名
phone / email 可空 + UNIQUE 多个 NULL 不冲突
password_hash VARCHAR(255) bcrypt 哈希，绝不明文
nickname / avatar / signature / region 资料
status TINYINT 0 正常 / 1 禁用
deleted_at DATETIME NULL GORM 软删除

设计点 1：phone/email 为什么可空

如果设成 NOT NULL，所有不填手机号的用户都存 '' → 撞唯一索引。

MySQL 的唯一索引对 NULL 的处理是：多个 NULL 允许共存。所以用「可空 + 唯一」既能保证有值时唯一，又允许多人不填。

对应 Go 代码里用指针：

指针的 nil 表示「没填」，"" 表示「填了空字符串」——语义不同。

设计点 2：password_hash 的 JSON tag 是 json:"-"

json:"-" 让这个字段永远不会被序列化到响应里。这是最简单的防泄露手段。

设计点 3：为什么单独一张 user_settings

设置字段多（隐私开关、通知开关…）、只有设置页用、改动频繁。塞进 users 会让主表越来越宽，而主表是最高频查询的表。

为什么不建一张 message_reads 表：

方案 存储 查询
每条消息一条已读记录 消息数 × 成员数（爆炸） 复杂
last_read_message_id 每成员一行 一次比较

群聊 200 人、10 万条消息，前者是 2000 万行，后者是 200 行。差距巨大。

索引设计：

  • uk_conv_user(conversation_id, user_id) 唯一 → 防同一会话重复加成员
  • idx_user(user_id) → 查「我的所有会话」

5.3 messages：消息表

设计要点 1：ClientMsgID + 唯一索引 = 幂等

网络重试、用户连点都会导致同一条消息发多次。客户端生成唯一 ID，服务端 UNIQUE(sender_id, client_msg_id) 兜底：

  • 第一次插入成功
  • 重复插入报 Duplicate → 查出已有消息直接返回（幂等）

设计要点 2：Type 用 tinyint 不用 enum

设计要点 3：Content 用 text

文本可能很长；图片/语音/文件消息存 URL 或 JSON 元信息，text 也放得下（最大 64KB）。

5.4 消息分页：为什么用游标不用 offset

方式 SQL 问题
offset LIMIT 20 OFFSET 1000 要扫描并跳过 1000 行，越翻越慢；新消息插入会错位
游标 id < last_id 走主键索引，恒定速度；不受新消息影响

为什么 id < last_id 能走索引：idx_msg_conv(conversation_id) 的叶子节点存主键，而主键有序 → 范围扫描 + 反向取即可。

九、索引为什么这么建：反向推导

索引 支撑的查询 不加会怎样
users.uk_username 登录 WHERE username = ? 每次登录全表扫
users.uk_phone 手机登录 同上
friendships.idx_user 好友列表 WHERE user_id = ? 全表扫
friendships.uk_user_friend 防重复 + 判断是否好友 可能重复好友
conversation_members.idx_user 「我的会话」 全表扫
conversation_members.uk_conv_user 防重复加成员 成员重复
messages.idx_msg_conv 拉历史 全表扫
messages.uk_sender_client 幂等 消息重复
friend_requests.idx_to_status 申请列表 全表扫

一个反例：不该建索引的情况

索引不是越多越好：每个索引都会拖慢写入（INSERT 要维护所有索引）、占用磁盘。

十、常见表设计错误

错误 后果 正确做法
不用唯一索引，只靠代码查重 并发下产生重复数据 加 UNIQUE
软删除 + 唯一索引不处理 删除后无法重建 复用旧行 / 物理删除
用 status 同时表达「业务状态」和「删除」 查询条件混乱 业务状态 + deleted_at 分开
不冗余计数/最后消息 列表页 N 次查询 冗余 + 原子更新
手机号 NOT NULL 多用户不填会冲突 可空 + 唯一
大字段放热点索引 索引膨胀 大字段单独表或 text
所有字符串用 VARCHAR(255) 索引/存储浪费 按实际长度设

十一、如果以后要加功能，表怎么改

新需求 改法 要不要新表
消息撤回 用已有的 messages.status = 2 不用改
消息已读回执（精确到人） 新建 message_reads 表 要
好友分组 用已有的 friend_groups 不用改
群公告已读 新建 group_announcement_reads 要
用户注销 用 users.deleted_at 软删 不用改
消息搜索 加全文索引或接 ES 不用改

设计得好不好，看加功能时改不改表。本项目刻意预留了 status/type 字段，就是为了这个。
