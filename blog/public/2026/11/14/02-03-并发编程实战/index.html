并发编程实战：项目里的 7 个并发场景

并发是这个项目最重要的技术含量。
本文不讲语法，只讲项目里真实存在的 7 个并发点：为什么需要并发、用了什么手段、为什么不用别的手段。
所有代码都来自 internal/ws/ 和 internal/service/，可直接对照源码。

一、先复习：Go 并发的 4 个工具

工具 解决什么 什么时候用
goroutine 让任务并行执行 IO 密集（网络、数据库）、需要后台处理
channel goroutine 之间传数据 / 排队 生产者-消费者、任务队列
sync.Mutex/RWMutex 保护共享内存 多个 goroutine 读写同一份数据
context 取消、超时、传值 所有可能阻塞的调用

一句话原则

能用 channel 传数据，就别共享内存；必须共享内存，才加锁。
能用数据库的原子操作（唯一索引/条件更新）解决，就不要加锁。

二、场景 1：HTTP 请求天然并发（gin 已经帮你做了）

gin 每收到一个请求就开一个 goroutine 执行 handler。所以「100 个用户同时注册」对 gin 来说是 100 个 goroutine 并行跑 Register。

你不需要写任何并发代码，但必须知道共享了什么。

陷阱：普通 map 并发读写会直接 panic

Go 的 map 不是并发安全的。要么加锁，要么用 sync.Map，要么（更好）用 Redis。

本项目里 global.DB、global.Redis 都是并发安全的（内部有连接池和锁），可以放心在多 goroutine 里用。

为什么用 RWMutex 而不是 Mutex

操作 频率
推送消息（读 clients） 非常频繁
连接建立/断开（写 clients） 相对少

读多写少 → 用读写锁，多个读可以并发，只有写才互斥。

注意 defer h.mu.Unlock()：即使中间 panic 也能解锁。如果手写 h.mu.Unlock() 放在函数末尾，中间 return 就会死锁。

推送：先复制，再解锁（关键技巧）

为什么必须这样写：

如果持着读锁去 c.Enqueue(payload)，而 Enqueue 里可能触发 c.Close()（关闭连接）→ Close 里可能要拿写锁 → 死锁（读锁还没释放，写锁拿不到）。

即使不死锁，持锁做 IO 也会把所有其他 goroutine 卡住。

这是并发编程最重要的习惯：锁只保护内存访问，不保护任何可能阻塞的操作。

gorilla/websocket 的文档明确写着：一个连接同时只允许一个 goroutine 写。
如果两个 goroutine 同时 WriteMessage，会 panic：

所以设计成：

  • 写操作 只有 WritePump 能做
  • 其他 goroutine 想发消息 → 往 send channel 塞数据 → WritePump 取出来写

这是「共享资源单 goroutine 独占 + channel 排队」的经典模式。

WritePump 还负责心跳

两个 select 分支：一个是「有消息要发」，一个是「到点发心跳」。这就是写 goroutine 的全部工作。

SetWriteDeadline 很重要：如果客户端网络卡住，WriteMessage 会一直阻塞，没有超时就会永久占用一个 goroutine（goroutine 泄漏）。

五、场景 4：慢消费者隔离（真实代码）

问题：如果某个客户端网络很慢（或故意不读），它的 send 队列会一直满。推送方如果阻塞等待，所有人都会被它拖死。

逐行解释

  • defer recover()：连接已经被关闭时，send channel 也关闭了，再往里写会 panic send on closed channel。这里兜住
  • select { case c.send <- payload: ... default: ... } —— non-blocking 写：
    • 队列有空间 → 入队
    • 队列满 → 走 default → 断开这个连接
  • 为什么是「断开」而不是「丢弃消息」：WebSocket 是有序的，丢一条后面就乱了。断开让客户端重连、重新拉历史，语义更干净

这就是「慢消费者隔离」：一个慢客户端不能影响其他 999 个用户。

八、场景 7：优雅退出（信号 + context）

顺序为什么重要

  • 先停 HTTP：不再有新请求进来
  • 再关 WS：客户端立刻感知并重连（不断开的话客户端会「假在线」）
  • 最后关依赖：如果先关 DB，正在处理的请求会报错

每个后台 goroutine 都要有退出路径

没有退出路径的 goroutine = 泄漏。

九、并发 bug 清单（都踩过）

bug 现象 原因 修复
数据竞争 偶发数据错乱 多 goroutine 读写同一变量 go test -race
goroutine 泄漏 内存/协程数持续涨 goroutine 阻塞在 channel/IO 上 加超时、加 ctx
死锁 程序卡死 锁顺序不一致 / 持锁做 IO 统一锁顺序、锁外做 IO
send on closed channel panic 连接关闭后仍推送 once 关闭 + recover
循环变量捕获 所有 goroutine 用同一个值 闭包捕获循环变量 显式传参
map 并发写 fatal error 直接崩 未加锁 mutex / sync.Map
