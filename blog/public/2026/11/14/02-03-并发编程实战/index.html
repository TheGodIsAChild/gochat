并发编程实战：项目里的 7 个并发场景

这个项目的并发点都在哪？每个点用了什么手段、为什么、怎么验证。
读完你应该能回答：「什么时候该加锁，什么时候不该加」。

一、先复习 Go 并发的 4 个工具

工具 用途 本项目用在哪
goroutine 并发执行 HTTP 请求（gin 自带）、WS 读写泵、扇出推送
channel goroutine 通信 / 队列 每个 WS 连接的发送队列
sync.Mutex / RWMutex 保护共享内存 Hub 连接表
context 取消 / 超时 所有 IO、优雅退出

核心原则：

能用 channel 传递数据 就别用共享内存；必须共享内存才加锁。
能用 数据库唯一索引/条件更新 解决的并发，就不要加锁。

二、场景 1：HTTP 并发（gin 天然并发）

但共享状态要注意：global.DB/global.Redis 是并发安全的（内部连接池），
而普通 map 并发读写会直接 panic。

三、场景 2：Hub 的读写锁

  • 注册/注销：Lock()（写）
  • 推送：RLock()（读），读多写少 → RWMutex 优于 Mutex

关键细节：持锁不做 IO

为什么：持锁调用 Enqueue（可能阻塞/关闭连接）会阻塞其他 goroutine 获取锁。

四、场景 3：每个连接的读/写双泵

为什么必须分开：gorilla/websocket 不允许并发写，并发写会 panic。
其他 goroutine 想发消息 → 只能往 send chan []byte 塞。

这里体现的原则：共享资源（socket）单 goroutine 独占，其他 goroutine 通过 channel 排队。

五、场景 4：慢消费者隔离

问题：如果客户端很慢，send 队列会满；如果用阻塞写 c.send <- payload，
推送方（可能正在给其他用户推消息）会被卡住。

解法：non-blocking 入队 + 断开慢连接 = 一个慢客户端不影响其他人。

六、场景 5：群消息扇出限并发

为什么：200 人的群无脑起 200 goroutine 会瞬时膨胀。
用带缓冲 channel 当信号量，把并发限制在 16。

小会话（≤10 人）直接顺序推，避免 goroutine 开销。

七、场景 6：并发控制交给数据库（最推荐）

很多并发问题不需要锁，数据库的原子操作就够了：

唯一索引兜底

条件更新 + RowsAffected

WHERE status=0 让「判断 + 修改」原子化，天然抗并发（双击、重试都安全）。

原子表达式

不要「先读再写」，并发会丢更新。

八、场景 7：优雅退出（信号 + context）

要点：每个后台 goroutine 都要有「退出路径」（ctx.Done / conn 关闭 / channel 关闭）。

九、并发常见 bug 清单

bug 现象 避免方式
数据竞争 偶发数据错乱 go test -race
goroutine 泄漏 内存/协程数持续涨 每个 goroutine 有退出条件
死锁 程序卡死 锁顺序一致、不嵌套锁
panic: send on closed channel 连接关闭后仍推送 sync.Once 关闭 + recover
闭包捕获循环变量 所有 goroutine 用同一个值 传参 go func(uid uint64){...}(uid)
map 并发读写 fatal error: concurrent map read and map write sync.Map 或加锁

闭包陷阱（Go 1.22 前常见）

十、怎么验证并发安全

本项目 hub_test.go 覆盖了：并发注册/推送/注销、多端在线、关闭全部连接、慢消费者不阻塞。
