面试自测 30 题（含参考答案）

前面所有文章都在讲知识，这篇是检验。
每题都有「参考答案 + 可能的追问」。先自己答，再对照——答不出来的回去看对应文章。

怎么用这篇

  1. 拿纸笔，把 30 题当成真实面试，口头答一遍（不要在心里默念）
  2. 答不出的题，点「详见」回到文章
  3. 全部能答后，再练追问部分——面试真正拉开差距的是追问

A. 认证与安全（5 题）

Q1. 为什么用两个 token，不用一个？

答：一个 token 无法同时满足安全和体验。有效期长 → 泄露风险大、无法撤销；有效期短 → 频繁掉登录。
双 token 把两件事分开：access 短命（2 小时）负责安全，refresh 长命（30 天）负责体验。
refresh 存在 Redis，可以随时撤销，所以「登出立即失效」也能实现。

追问：access 过期了用户会不会有感知？
不会。客户端拿到 401 后自动调 /token/refresh 换新 token，再重试原请求，用户无感。

详见 一次 HTTP 请求的完整链路

Q2. JWT 的 payload 是加密的吗？能放密码吗？

答：不是加密，只是 base64 编码，任何人拿到都能解码看到内容。签名只保证”没被篡改”，不保证”看不见”。
所以只能放非敏感信息（user_id、username、过期时间），绝不能放密码。

追问：那 JWT 有什么安全风险？
要校验签名算法（防 alg=none 伪造）；secret 不能硬编码；access 要短命。

Q3. 无状态的 JWT 怎么实现「登出」？

答：JWT 本身无法撤销，所以要引入有状态的辅助：登录时把 refresh 的 jti（唯一编号）写进 Redis 白名单，
登出时删掉这个 key。之后再用这个 refresh 刷新就会失败。
access 因为只有 2 小时，过期自然失效，不单独处理。

追问：为什么不用黑名单？ 黑名单要存所有作废 token，只增不减；白名单只存有效的，更省空间。

Q4. 并发刷新 token 会有什么问题？怎么解决？

答：5 个请求同时 401 会触发 5 次刷新。因为每次刷新都会换新 refresh（rotation），第 2~5 次用旧 token 就会失败，甚至被判定为「token 被盗」而强制下线。
解决：① 服务端用 GETDEL 原子消费，只有一个请求能成功；② 客户端单飞（single-flight），刷新进行中其他请求等待同一个结果。

追问：GETDEL 和 GET + DEL 有什么区别？ 前者是一条原子命令，后者中间有时间窗口，并发下两个请求都能通过。

Q5. 密码为什么用 bcrypt 而不是 MD5？

答：MD5/SHA 是快速哈希，可被彩虹表和 GPU 暴力破解，且同密码结果相同，一旦库泄露能批量撞库。
bcrypt 故意很慢 + 内置随机 salt，同密码每次结果不同，破解成本极高。

追问：salt 存在哪？ 存在哈希字符串里（$2a$10$...），不需要单独字段。

B. 数据库（6 题）

Q6. 好友关系为什么存两行？

答：A、B 成为好友插 (A,B) 和 (B,A) 两行。
好处：查「我的好友」只需 WHERE user_id = ?，能走索引；
如果只存一行，查询要 WHERE user_id = ? OR friend_id = ?，OR 用不上索引，数据量大就全表扫。
代价是写两行，必须用事务保证成对。

追问：为什么还要 status 字段？ 用于软删除，保留关系历史，重新加好友时复用旧行。

Q7. 未读数怎么算？为什么不建一张已读表？

答：在 conversation_members 表里存 last_read_message_id，未读数 = 该会话里 id > last_read_message_id 且 sender != 我 的消息数。
如果建「每条消息 × 每个成员」的已读表：200 人的群 × 10 万条消息 = 2000 万行，而当前方案只有 200 行。

追问：这个方案的缺点？ 只能知道”读到哪”，不能精确知道”谁读了哪条”；如果需要精确已读回执，就得加表。

Q8. 消息分页为什么用游标不用 offset？

答：LIMIT 20 OFFSET 1000 要扫描并跳过 1000 行，越翻越慢；而且期间有新消息插入会导致重复或漏。
游标用上一页最后一条的 id 作为锚点：WHERE conversation_id = ? AND id < ? ORDER BY id DESC LIMIT 20，
走主键索引，速度恒定，也不受新消息影响。

追问：那怎么跳页？ 游标分页不支持跳页，消息流场景也不需要。

Q9. 怎么保证消息不重复？

答：三层：
① 客户端生成 client_msg_id（唯一）；
② 数据库 UNIQUE(sender_id, client_msg_id) 兜底；
③ 插入撞唯一索引时捕获 gorm.ErrDuplicatedKey，查出已有消息直接返回（幂等）。

追问：为什么只靠”先查再插”不行？ 查和插之间有时间窗口，两个并发请求可能都查到”不存在”。

Q10. 接受好友申请为什么必须用事务？怎么防重复接受？

答：要改申请状态 + 插两条好友关系，这是 3 个写操作，中途失败会产生脏数据（比如有申请记录但没有好友关系）。
防重复：用条件更新 WHERE id = ? AND status = 0，看 RowsAffected。
第二次点「接受」时 RowsAffected = 0，直接报错，不会插重复好友。

追问：这和加锁有什么区别？ 不用加锁，把”判断”和”修改”合成一条原子 SQL，性能更好。

Q11. 软删除和唯一索引冲突怎么解决？

答：软删除只是改标记，行还在，唯一索引仍然占位。比如删除好友后重新加，会撞 UNIQUE(user_id, friend_id)。
解法：① 用 Unscoped() 查出旧行，存在就恢复（重置 status）；② 对于黑名单这种不需要历史的，直接物理删除。

追问：为什么黑名单要物理删？ 因为拉黑/取消拉黑会反复发生，软删的行会一直挡着唯一索引。

C. 并发（6 题）

Q12. WebSocket 为什么必须读写分离？

答：gorilla/websocket 明确不允许并发写，两个 goroutine 同时写会 panic（concurrent write to websocket connection）。
所以设计成：ReadPump 唯一负责读，WritePump 唯一负责写，其他 goroutine 想发消息只能往 send channel 塞。

追问：为什么不加锁解决？ 加锁也能避免并发写，但写 socket 可能阻塞，持锁会拖住所有发送方；channel 方式把”发送”和”实际写”解耦了。

Q13. 心跳解决什么问题？为什么 ping 间隔要小于超时时间？

答：TCP 连接可能”假死”（网线拔了、切网），双方都以为还连着，导致服务端一直往死连接推消息、goroutine 泄漏。
心跳让双方定期确认存活：服务端每 54 秒发 ping，60 秒收不到 pong 就断开。
ping 间隔 < 超时（54 < 60）是为了留网络抖动余量，否则正常连接会被误杀。

详见 WebSocket 全解

Q14. 慢消费者怎么处理？

答：每个连接有一个缓冲 channel。推送时用 select { case ch <- data: default: 关闭连接 }——队列满了就断开这个连接。
这样做得原因：如果阻塞等待，一个慢客户端会拖死给它推送的 goroutine，进而影响其他用户。
选择断开而不是丢消息，是因为 WebSocket 是有序的，丢一条后面就乱；断开后客户端重连、拉历史更干净。

详见 并发编程实战

Q15. 为什么说「锁里不能做 IO」？举个项目里的例子。

答：持锁做 IO（网络、channel 阻塞、数据库）会把锁持有时间放大到不可控，其他 goroutine 全部排队。
项目例子：Hub.SendToUser 先持读锁把连接列表复制一份，立刻 RUnlock，再在锁外逐个 Enqueue。
如果持锁调用 Enqueue，而 Enqueue 可能触发 Close()（要拿写锁），就会死锁。

详见 并发编程实战

Q16. 怎么控制并发数？项目里哪里用到了？

答：用「带缓冲 channel 当信号量」：sem := make(chan struct{}, N)，起 goroutine 前 sem <- struct{}{}，goroutine 结束时 <-sem。
项目里群消息扇出就是：小群（≤10 人）顺序推送，大群并发推送但限制同时最多 16 个。

追问：为什么不用 worker pool？ 也可以，本质一样；这里成员数是动态的，用信号量更简单。

Q17. goroutine 泄漏常见原因？怎么排查？

答：常见原因：① goroutine 阻塞在 channel 上（消费者已退出）；② 网络/数据库调用没有超时；③ 定时器没 Stop；④ 没有退出路径的死循环。
排查：pprof 看 goroutine 数量（/debug/pprof/goroutine），对比不同时间点；代码审查每个 go func 是否有退出条件。

追问：怎么预防？ 所有可能阻塞的调用都带 context 超时；后台 goroutine 用 ctx.Done() 做退出信号。

D. WebSocket 与实时（6 题）

Q18. WebSocket 和 HTTP 长轮询、SSE 的区别？

答：

  • HTTP 短轮询：客户端定时问，实时性差、连接开销大
  • 长轮询：请求挂住等消息，实时性较好，但每条消息要重建连接
  • SSE：单连接服务端单向推流，只能下行
  • WebSocket：单连接全双工，双方随时发

IM 需要服务端主动推 + 客户端主动发，只有 WebSocket 同时满足。

Q19. WebSocket 握手过程说一下。

答：客户端发一个普通 HTTP 请求，带 Upgrade: websocket、Connection: Upgrade、Sec-WebSocket-Key；
服务端校验后返回 101 Switching Protocols 和 Sec-WebSocket-Accept（Key + 固定 GUID 的 SHA1）。
之后同一条 TCP 连接上开始传 WebSocket 帧，不再走 HTTP。

追问：Sec-WebSocket-Key 有什么用？ 防止中间代理误把普通 HTTP 请求当成升级请求。

Q20. 浏览器 WebSocket 不能带自定义 header，怎么鉴权？

答：把 token 放在 query 参数里：ws://host/ws?token=xxx。
服务端在升级连接之前解析并校验 token，非法直接返回 401，不建立连接。

追问：这样有什么安全隐患？ token 会出现在 Nginx 日志、浏览器历史。生产更推荐先 HTTP 换一个一次性 ticket，再用 ticket 连 WS。

Q21. 断线重连怎么做？为什么要指数退避？

答：监听 onclose，用 setTimeout 延迟重连，延迟按 1s→2s→4s→8s→15s 递增封顶。
指数退避是为了防”惊群”：服务端重启时所有客户端同时用 1 秒间隔重连，会把刚起来的服务再次打挂。
重连后要：重新注册连接、拉断线期间的消息、刷新在线状态。

详见 WebSocket 全解

Q22. wss 和 ws 的区别？Nginx 怎么配？

答：wss 是 WebSocket over TLS，加密传输，生产必须用（否则 HTTPS 页面会被浏览器拦为混合内容）。
Nginx 反代关键三行：proxy_http_version 1.1、proxy_set_header Upgrade $http_upgrade、proxy_set_header Connection "upgrade"；
另外要把 proxy_read_timeout 调大（默认 60s 会把长连接断开）。

Q23. 多实例部署时，怎么给不在本机的用户推消息？

答：单机 Hub 只管理本进程连接。多实例方案：
① Redis Pub/Sub：每个实例订阅频道，收到广播后推本机在线用户；
② MQ 扇出：消息发到 RabbitMQ，所有实例消费后各推本机用户（本项目 M7 用的这个思路）；
③ 一致性哈希：按 userID 固定路由到某实例。
在线状态也要从内存改成 Redis + TTL。

E. 架构、MQ 与工程（7 题）

Q24. 你的项目怎么分层？为什么这么分？

答：三层：handler（解析请求、写响应）→ service（业务逻辑、事务）→ model/DB（数据访问）。
好处：① service 不依赖 gin，M6 拆 gRPC 时复用；② service 是纯函数，容易单测；③ 换框架只改 handler。

追问：怎么判断分层被破坏了？ service 里出现 import gin 或 *gin.Context，就说明业务和 HTTP 框架绑死了。

Q25. 为什么先写单体，后来才拆微服务？

答：先体会单体的痛点才知道为什么要拆：扩缩容粒度粗（聊天流量大但用户服务也得跟着扩）、故障不隔离、部署耦合。
拆分按业务领域（user / chat），不按技术层。拆完带来新问题：服务发现、超时重试、熔断、链路追踪、跨服务数据一致性。

Q26. 为什么内部用 gRPC，对外用 HTTP？

答：对外 HTTP 因为浏览器、调试工具、第三方都友好；内部 gRPC 因为强契约、二进制体积小、HTTP/2 多路复用、支持流式。
另外内部服务只允许 gateway 调用，鉴权统一在网关做。

Q27. 为什么消息要经过 MQ 异步推送？直接推不行吗？

答：直接推的问题：请求里要查会话成员 + 逐个推送，群消息 200 人时请求变慢；推送失败没有重试。
走 MQ 后：请求快速返回（只落库 + 写 outbox）；worker 异步发 MQ；消费失败可以重试；还能削峰。

追问：延迟会变大吗？ 会（本项目 outbox worker 每 2 秒轮询），但 IM 场景可接受。

Q28. Outbox 模式解决什么问题？怎么实现的？

答：解决”落库和发 MQ 无法原子”：先落库再发 MQ，发失败会丢消息；先发 MQ 再落库，落库失败会推不存在的消息。
实现：业务事务里同时写 messages 和 outbox_messages(status=0)（同一事务，原子）；后台 worker 轮询 status=0，发 MQ 成功后标记 status=1。

追问：worker 发完 MQ 但标记失败会怎样？ 下次会重发 → 至少一次投递 → 消费方必须幂等。

Q29. 某个依赖挂了怎么办？举例说明降级。

答：区分必需依赖和可选依赖。MySQL/Redis 挂了必须报错（fail-fast）；RabbitMQ 挂了打日志并降级为同步推送（fail-soft）。
降级的核心是”用更差但可用的方式继续服务”，而不是直接报错。

追问：为什么 MQ 可以降级？ 因为消息已经落库了，推送只是”通知”，同步推也能达到效果，只是慢一点。

Q30. 你项目里最难的三个点是什么？怎么解决的？

答（选你最有把握的三个）：
① WebSocket 并发管理：读写分离 + RWMutex + 慢消费者隔离；
② 双 token 并发刷新：GETDEL 原子消费 + 客户端单飞；
③ Outbox 最终一致性：本地消息表 + worker 重试 + 消费幂等。

答题技巧：每个点都说「问题是什么 → 试过什么方案 → 最终怎么选 → 效果如何」，不要说”我用了 X 技术”就完了。
