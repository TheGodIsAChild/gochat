M3 详细设计：群聊（建群事务 / 权限 / 人数统计）

对应提交：M3: groups model + group service + group routes + conversation list group info

一、里程碑目标

  • 群信息模型（groups）
  • 建群（事务：会话 + 群 + 成员）
  • 拉人进群 / 踢人 / 退群
  • 改群名、群公告（群主权限）
  • 解散群
  • 群消息（复用 M2 的发送与推送）

验收（已实测）：

场景 结果
建群（群主 + 2 成员） 200，member_count=3
我的群列表（群主/成员都能看） 200
群详情 200
群消息发送 + 成员拉历史 200
群主踢人 200
被踢后访问群 400「你不是该群成员」
非群主改群名 400「只有群主可以修改群资料」
群主改群名 200
会话列表带群信息 200（group_name/member_count）
解散群 200，之后查群 400

二、核心设计：复用会话抽象

为什么群聊几乎不用新写消息逻辑

M2 已经建立了：

所以群聊 = Type=2 的会话 + groups 表（群元信息）。

  • 群消息发送：直接复用 chatservice.SendMessage（它只认 conversation_id）
  • 群消息推送：直接复用 ws.PushMessage（它查会话所有成员并逐个推送）

M3 新增的只有「群的生命周期管理」：建群、拉人、踢人、改资料、解散。

这就是好的抽象的价值：M2 多花一点心思设计会话+成员+消息，M3 就几乎免费。

三、数据模型

groups 表

字段 说明
conversation_id 关联会话（唯一）
owner_id 群主
name 群名称
avatar 群头像
announcement 群公告
member_count 冗余人数（列表展示）
max_members 人数上限（默认 200）
status 1 正常 / 2 已解散

为什么 member_count 要冗余

群列表/群详情要显示”多少人”。如果不冗余，每次都要 COUNT(*) FROM conversation_members WHERE conversation_id=?。
加人/踢人时同步更新 member_count（用 gorm.Expr("member_count + ?") 原子自增，避免并发覆盖）。

四、建群：为什么必须是事务

建群要做 4 件事：

  1. 创建 conversations（Type=2）
  2. 创建 groups（关联 conversation_id）
  3. 插入群主到 conversation_members（Role=1）
  4. 插入其他成员

任何一步失败，不做事务就会产生脏数据：

  • 有会话没群 → 会话列表出现一个没有名字的会话
  • 有群没会话 → 群消息发不出去
  • 有群没群主 → 群没人能管理

面试点：事务边界 = 一个完整业务语义。建群是一个业务动作，必须原子。

五、成员管理的权限规则

操作 谁可以
拉人进群 任何群成员（类微信）
踢人 只有群主
退群 任何成员（群主不能直接退）
改群名/公告 只有群主
解散群 只有群主

权限校验的统一套路：

群主不能直接退群

如果群主退了，群就没人管了。正确做法：

  • 转让群主（M3 简化未做，M4 可加）
  • 或者先解散群

六、人数上限与并发

上限校验

并发安全

两个请求同时拉人，可能都通过上限校验 → 超员。
M3 用 gorm.Expr 原子自增保证计数不丢，但上限校验仍有竞态。

彻底解决（M4）：

  • 事务里 SELECT ... FOR UPDATE 锁群行
  • 或用 Redis 分布式锁
  • 或不严格限制（超一点可接受）

面试点：乐观 vs 悲观。计数用原子表达式是乐观；上限校验加行锁是悲观。

七、踢人/退群：为什么要事务

踢人要：

  1. 删除 conversation_members 里的一行
  2. member_count - 1

不是事务的话，删了成员但人数没减 → 群人数显示错误。

八、解散群

为什么保留数据：群消息、群记录保留，便于审计/追溯。

软删除 vs 物理删除：IM 的群、消息一般软删（合规/回溯），个人数据可以用物理删（如黑名单）。

九、群消息：复用 M2

群消息的发送和推送完全复用 M2：

唯一要担心的：群成员多时（比如 200 人），一次消息要推 200 次。

  • M3 是同步循环推
  • M4 会讨论「扇出放大」问题（可以用 goroutine 池、MQ 异步）

十、代码导读

文件 作用 重点
internal/model/group_model/group_model.go 群模型 关联 conversation、member_count 冗余
internal/service/group_service/group_service.go 群业务 建群事务、权限校验、原子计数
internal/router/group_router/group_api.go 群接口 7 个接口
internal/service/chat_service/conversation_service.go 会话列表 群信息富化（Type=2 带 group_name）

十一、注意点清单

  1. 建群必须事务（会话+群+成员）
  2. 群主校验和成员校验都要做：先确认群存在 → 再确认操作人身份
  3. member_count 用 gorm.Expr 原子自增/自减，不要先读再写
  4. 踢人/退群也要事务（删成员 + 减计数）
  5. 群主不能直接退群，要先解散或转让
  6. 被踢的人要立即失去访问权限：每个群接口都做 isMember 校验
  7. 解散群保留数据（软删会话），不要物理删
  8. 群消息扇出：成员多时推送量大，M4 优化
  9. 拉人上限有竞态：并发加人可能超员，需行锁或接受轻微超员

十二、面试点（M3）

  1. 群聊为什么复用「会话 + 消息」模型？有什么好处？
  2. 建群为什么必须用事务？不做会出现什么脏数据？
  3. 群成员人数怎么高效统计？为什么冗余 member_count？
  4. 并发加人怎么防止超员？（行锁 / 原子计数 / 可接受超员）
  5. 群权限模型怎么设计？（群主/管理员/成员）
  6. 群主退群怎么处理？（转让 / 解散）
  7. 群解散后数据怎么处理？（软删保留 vs 物理删除）
  8. 群消息扇出到 200 人怎么优化？（goroutine 池 / MQ / 分批）
  9. 单聊和群聊共用会话表有什么坑？
  10. 群成员列表需要缓存吗？为什么？

十三、下一步（M4 并发加固）

M4 会针对前三个里程碑的并发/稳定性问题做加固：

  • WebSocket 连接管理的并发测试（-race）
  • goroutine 泄漏排查
  • 优雅退出（关闭时等待/断开连接）
  • 消息扇出优化（goroutine 池）
  • 限流（登录/搜索）
  • 幂等强化
  • 压测脚本
