> 「我觉得没问题」不是验证。本文讲：怎么写测试、怎么跑、出 bug 怎么定位。
> 目标：让你在没有 QA 的情况下也能对代码有信心。

## 一、测试金字塔

```
        ▲  E2E（端到端）      少、慢、贵
       ╱ ╲
      ╱   ╲  集成测试        中
     ╱     ╲
    ╱───────╲ 单元测试       多、快、便宜
```

| 层 | 测什么 | 本项目 |
|---|---|---|
| 单元测试 | 纯函数、service 逻辑 | `hub_test.go`（并发） |
| 集成测试 | HTTP 接口 + 真实依赖 | curl 冒烟脚本 |
| E2E | 浏览器全流程 | 手动（两窗口演示） |

## 二、表驱动测试（Go 最常用写法）

```go
func TestParseToken(t *testing.T) {
    cases := []struct {
        name    string
        token   string
        wantErr bool
    }{
        {"正常 access", validAccess, false},
        {"过期", expiredToken, true},
        {"错误签名", badSigToken, true},
        {"类型不对", refreshAsAccess, true},
        {"空串", "", true},
    }

    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) {
            _, err := auth.Parse(c.token)
            if (err != nil) != c.wantErr {
                t.Fatalf("wantErr=%v, got err=%v", c.wantErr, err)
            }
        })
    }
}
```

**为什么用表驱动**：加用例只是加一行数据，不用复制测试函数。

## 三、并发测试（本项目 hub_test.go）

```go
func TestHubConcurrency(t *testing.T) {
    h := NewHub()
    var wg sync.WaitGroup

    // 200 个 goroutine 同时注册
    for i := 0; i < 200; i++ {
        wg.Add(1)
        go func(uid uint64) {
            defer wg.Done()
            c := newTestClient(uid)
            h.Register(c)
            h.SendToUser(uid, []byte("hi"))   // 同时推送
            h.Unregister(c)                    // 同时注销
        }(uint64(i))
    }
    wg.Wait()

    if got := h.Count(); got != 0 {
        t.Fatalf("连接未清理干净: %d", got)
    }
}
```

**跑法**：

```bash
go test ./internal/ws/ -race -count=1 -v
```

| 参数 | 作用 |
|---|---|
| `-race` | 数据竞争检测（需 cgo + gcc） |
| `-count=1` | 禁用缓存，强制重跑 |
| `-v` | 显示每个用例 |
| `-cover` | 显示覆盖率 |

> **本项目的真实限制**：Windows 本机没有 gcc，`-race` 跑不了。
> 这说明「测试能力受环境限制」——生产 CI 上必须开 `-race`。

## 四、HTTP 接口测试（httptest）

```go
func TestRegisterAPI(t *testing.T) {
    gin.SetMode(gin.TestMode)
    r := gin.New()
    r.POST("/api/v1/register", userapi.Register)

    body := `{"username":"testuser","password":"123456","nickname":"测试"}`
    req := httptest.NewRequest("POST", "/api/v1/register", strings.NewReader(body))
    req.Header.Set("Content-Type", "application/json")
    w := httptest.NewRecorder()

    r.ServeHTTP(w, req)

    if w.Code != 200 {
        t.Fatalf("期望 200，实际 %d: %s", w.Code, w.Body.String())
    }
}
```

**注意**：service 里用了 `global.DB`，所以这类测试需要真实/内存数据库（或改成注入）。

> 这也是「依赖注入」的价值：注入 DB 后单测可以直接用 sqlite/mock。

## 五、集成 / 冒烟测试（本项目做法）

对于有真实依赖（MySQL/Redis/MQ）的项目，最实用的是**脚本化冒烟**：

```powershell
# 1. 注册
curl -X POST $U/register -d '{"username":"alice",...}'
# 2. 登录拿 token
$TOKEN = (curl -X POST $U/login ...).data.access_token
# 3. 调业务接口
curl -X POST $U/friends/requests -H "Authorization: Bearer $TOKEN" -d '{"to_user_id":2}'
# 4. 断言状态码和关键字段
```

本项目的 `scripts/seed-demo.ps1` 就是这种思路：**用 API 把业务流程跑一遍**。

**优点**：真实、直观、能发现集成问题（如 JSON 字段名不一致、鉴权失败）。
**缺点**：慢、依赖环境、不好并行。

## 六、覆盖率

```bash
go test ./... -cover
go test ./... -coverprofile=cover.out
go tool cover -html=cover.out
```

| 覆盖率 | 意义 |
|---|---|
| 30% | 基本没测 |
| 60% | 及格 |
| 80%+ | 良好（核心逻辑） |

**注意**：覆盖率是「有没有跑到」，不是「测得对不对」。
100% 覆盖也可能全是「只调用不断言」的假测试。

## 七、调试手段工具箱

| 场景 | 工具 |
|---|---|
| 看请求/响应 | `curl -v`、浏览器 DevTools Network |
| 看变量 | `log.Printf` / `fmt.Printf`（加唯一前缀方便过滤） |
| 断点调试 | Delve（`dlv debug`）+ VS Code 配置 |
| 看 CPU/内存/goroutine | `net/http/pprof` |
| 看 SQL | GORM Logger（`db.Debug()`） |
| 看 Redis 数据 | `redis-cli` / `MONITOR` |
| 看 MQ 消息 | RabbitMQ 管理台 15672 |
| 看 WebSocket 帧 | 浏览器 DevTools WS 面板 / `wscat` |

### pprof 接入（临时排查）

```go
import _ "net/http/pprof"

go func() {
    log.Println(http.ListenAndServe("127.0.0.1:6060", nil))
}()
```

```bash
go tool pprof http://127.0.0.1:6060/debug/pprof/goroutine   # goroutine 泄漏
go tool pprof http://127.0.0.1:6060/debug/pprof/heap       # 内存
go tool pprof http://127.0.0.1:6060/debug/pprof/profile    # CPU 30s
```

**注意**：pprof 端口只能内网/本机访问，不要暴露到公网。

## 八、bug 定位流程（实战）

```
1. 复现：能稳定复现吗？→ 不能就先加日志
2. 缩小范围：前端问题还是后端？→ 看 Network / 看服务端日志
3. 定位层次：HTTP 进来了吗？→ 日志有没有打到 handler
4. 看数据：参数对不对？→ 打印入参
5. 看 SQL：执行了什么？→ GORM Debug / 慢查询日志
6. 二分：注释一半代码，问题还在吗？
7. 最小复现：写 20 行小程序重现
```

**经验**：80% 的 bug 是「参数不对」或「数据状态不符合预期」。
先打印入参和关键状态，比盯着代码看快得多。

## 九、本项目踩过的测试坑

| 坑 | 教训 |
|---|---|
| 测试 URL 写错（`/friends/settings` vs `/users/settings`） | 以为接口 404 是 bug |
| WS 测试中读到了之前推送的残留帧 | 测试要隔离，用独立会话 |
| 主叫/被叫方向搞反 | 明确谁收什么事件 |
| `-race` 需要 cgo，环境没有 gcc | 测试能力依赖环境，CI 要配好 |

## 十、上线前的检查清单

- [ ] `go build ./...` 通过
- [ ] `go vet ./...` 无警告
- [ ] `go test ./...` 通过
- [ ] 核心接口 curl 冒烟通过
- [ ] 降级路径验证（停掉 MQ 再试）
- [ ] 日志里没有密码/token
- [ ] 优雅退出正常（Ctrl+C 观察日志）
