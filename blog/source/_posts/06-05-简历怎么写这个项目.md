> 学完了，但简历上怎么写？写得太朴素没人问，写得太夸张会被追问到崩。
> 本文给 3 个可直接改的版本，以及**面试官会顺着哪句话追问**。

## 一、写简历的 3 条铁律

### 铁律 1：写「问题 + 方案 + 结果」，不写「用了什么技术」

| ❌ 差 | ✅ 好 |
|---|---|
| 使用 Gin、GORM、Redis、RabbitMQ 开发了 IM 系统 | 消息重复发送问题：用客户端消息 ID + 唯一索引实现幂等，重复率从重试场景 100% 降到 0 |

**为什么**：技术栈人人都会写，面试官想看的是**你解决了什么问题**。

### 铁律 2：只写你能扛住 3 层追问的点

写了「高并发」就要能被问：QPS 多少？瓶颈在哪？怎么压测的？
**没做过压测就别写高并发**。

### 铁律 3：数字要真实且具体

| ❌ 模糊 | ✅ 具体 |
|---|---|
| 支持大量用户 | 单机维护 1 万+ WebSocket 长连接（测试值） |
| 提升了性能 | 消息列表查询从 120ms 降到 8ms（加了复合索引 + 游标分页） |

> 如果没测过，就写**设计方案**，不要编数字。编数字是面试大忌。

## 二、版本 A：校招 / 转行（1–2 个月项目）

适合：没有工作经验的应届生、培训班转行。

```
gochat · 仿微信即时通讯后端（个人项目）
技术栈：Go / Gin / GORM / MySQL / Redis / WebSocket / RabbitMQ / gRPC

· 独立设计并实现用户、好友、单聊、群聊、语音通话 5 大模块，共 60+ 文件、约 4500 行 Go 代码
· 认证：实现 access + refresh 双 token 机制，refresh 存 Redis 白名单支持登出撤销；
  用 GETDEL 原子消费 + 客户端单飞解决并发刷新导致的 token 失效问题
· 消息：基于客户端消息 ID + 唯一索引实现幂等，避免网络重试产生重复消息；
  历史消息采用游标分页替代 offset，避免深翻页变慢
· 实时：实现 WebSocket 长连接管理（读写分离双 goroutine、心跳保活、指数退避重连），
  用 non-blocking 入队隔离慢消费者，避免单个慢连接拖垮推送
· 一致性：引入本地消息表（Outbox）+ RabbitMQ 实现异步推送，
  MQ 不可用时降级为同步推送，保证功能可用
· 微服务：将单体按领域拆分为 user / chat 两个 gRPC 服务 + HTTP 网关
```

**面试官会从哪句追问**：

| 简历里的词 | 可能的追问 |
|---|---|
| 双 token | 为什么不用单 token？refresh 怎么撤销？ |
| GETDEL | 和 GET + DEL 有什么区别？ |
| 幂等 | 为什么不用"先查后插"？唯一索引冲突怎么处理？ |
| 游标分页 | 为什么不支持跳页？ |
| 慢消费者 | 为什么断开而不是丢消息？ |
| Outbox | 怎么保证不丢？重复投递怎么办？ |

## 三、版本 B：社招 / 有经验（强调设计能力）

适合：1–3 年经验，想展示架构思维。

```
gochat · 即时通讯系统（个人项目，从 0 到 1）

背景：为系统练习并发编程、微服务拆分与消息中间件，独立实现一个仿微信 IM 后端。

· 架构演进：先以单体完成 M0–M5（认证/好友/聊天/群聊/WebRTC 信令），
  再按业务领域拆分为 gRPC 微服务 + 网关，service 层不依赖 Web 框架，拆分时零改动复用
· 数据模型：设计 12 张表，采用「会话 + 消息」两层抽象统一单聊与群聊；
  未读数用 last_read_message_id 方案，相比逐条已读表减少 4 个数量级存储
· 并发控制：WebSocket Hub 用 RWMutex 保护，持锁仅做内存复制、IO 全部移到锁外；
  群消息扇出用信号量限制 16 并发，避免瞬时 goroutine 暴涨
· 一致性：业务事务内写 Outbox 表，后台 worker 轮询投递 MQ，
  消费端幂等处理，实现消息推送的最终一致性；MQ 故障时自动降级同步推送
· 可观测性：实现优雅退出（信号 → 停 HTTP → 关长连接 → 停 gRPC → 释放依赖）、
  滑动窗口限流、统一错误包装与日志分级
```

**优势**：这份描述体现「先单体后拆」的演进思路，面试官会觉得你想过为什么拆。

## 四、版本 C：只留 3 条（简历空间紧张）

```
gochat · 仿微信 IM 后端（Go / Gin / MySQL / Redis / WebSocket / RabbitMQ）
· 双 token 无感刷新：refresh 白名单 + GETDEL 原子消费，解决并发刷新失效问题
· 消息幂等与分页：client_msg_id + 唯一索引防重复；游标分页替代 offset
· 异步推送：Outbox + RabbitMQ 最终一致性，MQ 故障降级同步推送
```

**适合**：项目只是简历里的一条，不需要展开。三条各对应一个可深挖的技术点。

## 五、技术栈怎么排序

**原则**：把最想被问的放前面。

```
✅ Go / WebSocket / Redis / MySQL / RabbitMQ / gRPC / Gin / GORM
❌ HTML / CSS / JavaScript / Go ...
```

- Go 放第一（岗位相关）
- WebSocket、Redis、MQ 这些「有技术含量」的放前面
- 前端只写一句「附带仿微信前端用于演示」，不要展开

## 六、避免踩雷的 5 个写法

| ❌ 别写 | 原因 |
|---|---|
| 高并发、高可用、分布式 | 太抽象，一问就露馅；除非你能说清 QPS 和方案 |
| 精通 Go / 精通 MySQL | "精通"会被问到底层；写"熟悉"更安全 |
| 使用 XX 技术实现了 YY | 只有技术没有业务价值，像流水账 |
| 日活 10 万 / 百万级数据 | 个人项目编这个，一问测试方法就崩 |
| 团队协作、敏捷开发 | 个人项目没有团队，写了很假 |

## 七、面试前 10 分钟的自查

- [ ] 简历里每一个技术名词，我都能说出**为什么用它、不用会怎样**
- [ ] 每一个数字，我都能说出**怎么测出来的**（或者删掉数字）
- [ ] 能画出项目的**架构图**（3 分钟，白板）
- [ ] 能讲清**一条消息从发送到接收**的完整链路
- [ ] 准备好**3 个难点**：问题→试过的方案→最终选择→效果
- [ ] 准备好**2 个不足**：比如"单机限流，多实例要换 Redis"（主动说不足显得真实）

## 八、被问「这个项目是你一个人做的吗」

诚实回答：

> 是的，个人项目，目的是系统练习并发、微服务和消息队列。
> 后端和前端都是我自己写的，UI 参考了微信的布局。

**不要**含糊其辞或暗示是团队项目——一问细节就崩。

## 九、如果面试官说「这个项目太简单了」

不要慌，把话题引到深度：

> 功能确实不复杂，但我重点练的是工程问题：
> 比如消息幂等怎么做、WebSocket 怎么管理连接和心跳、MQ 挂了怎么降级。
> 这些点单看都不难，但要做得可靠需要考虑很多边界。

**核心思路**：项目的价值不在功能数量，在**你有没有想过边界和异常**。
