> 表设计不是「把字段列出来」，而是**用数据库的约束表达业务规则**。
> 本文逐张表讲：为什么有这张表、每个字段干嘛、索引为什么这么建，并附上项目真实的 GORM 模型代码。

## 一、设计表之前先想清楚 3 件事

### 1. 这张表描述的是什么「东西」

一个表 = 一类实体。如果你想不出「它描述什么」，大概率是表拆错了。

### 2. 哪些规则必须由数据库保证

| 规则 | 用数据库保证（强） | 只用代码保证（弱） |
|---|---|---|
| 用户名唯一 | `UNIQUE` 索引 | 先查后插（有并发窗口） |
| 消息不重复 | `UNIQUE(sender_id, client_msg_id)` | 查重（并发会漏） |
| 好友关系成对 | 事务 | 分两次插入（可能只成功一半） |

**结论**：**唯一性、成对性，能交给数据库就交给数据库。**

### 3. 哪些场景要读得快

列表页（会话列表、好友列表）是最高频的查询，需要**专门为它设计索引或冗余字段**。

## 三、逐域拆解

### 3.1 用户域

#### users

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | 自增 |
| username | VARCHAR(32) **UNIQUE** | 登录名 |
| phone / email | 可空 + UNIQUE | 多个 NULL 不冲突 |
| password_hash | VARCHAR(255) | **bcrypt 哈希，绝不明文** |
| nickname / avatar / signature / region | | 资料 |
| status | TINYINT | 0 正常 / 1 禁用 |
| deleted_at | DATETIME NULL | GORM 软删除 |

**设计点 1：`phone`/`email` 为什么可空**

如果设成 `NOT NULL`，所有不填手机号的用户都存 `''` → 撞唯一索引。

MySQL 的唯一索引对 NULL 的处理是：**多个 NULL 允许共存**。所以用「可空 + 唯一」既能保证有值时唯一，又允许多人不填。

对应 Go 代码里用指针：

```go
Phone *string `gorm:"type:varchar(20);uniqueIndex" json:"phone,omitempty"`
```

指针的 `nil` 表示「没填」，`""` 表示「填了空字符串」——语义不同。

**设计点 2：`password_hash` 的 JSON tag 是 `json:"-"`**

```go
PasswordHash string `gorm:"type:varchar(255);not null" json:"-"`
```

`json:"-"` 让这个字段**永远不会被序列化到响应里**。这是最简单的防泄露手段。

**设计点 3：为什么单独一张 `user_settings`**

设置字段多（隐私开关、通知开关…）、只有设置页用、改动频繁。塞进 `users` 会让主表越来越宽，而主表是最高频查询的表。

#### user_settings（1:1）

| 字段 | 说明 |
|---|---|
| user_id **UNIQUE** | 一人一条 |
| allow_search_by_phone | 允许通过手机号被搜到 |
| allow_friend_request | 允许被加好友 |
| need_verify | 加好友需要验证 |
| show_read_receipt | 显示已读回执 |

## 四、好友域

### 4.1 friendships：为什么存双向两行

A 和 B 成为好友后，插两条记录：

```
(A, B)
(B, A)
```

**为什么不存一行 + OR 查询**：

```sql
-- 一行方案：查「我的好友」
WHERE user_id = 1 OR friend_id = 1     -- ❌ OR 用不上索引，数据量大直接全表扫
```

```sql
-- 两行方案
WHERE user_id = 1                       -- ✅ 走 idx_user，快
```

**代价**：写要写两条 → **必须用事务**，否则可能只成功一条，产生「单向好友」。

真实模型：

```go
type Friendship struct {
    model.Model
    UserID    uint   `gorm:"not null;uniqueIndex:uk_user_friend;index:idx_user" json:"user_id"`
    FriendID  uint   `gorm:"not null;uniqueIndex:uk_user_friend" json:"friend_id"`
    Remark    string `gorm:"type:varchar(32);not null;default:''" json:"remark"`
    GroupID   uint   `gorm:"not null;default:0" json:"group_id"`
    IsStarred int8   `gorm:"type:tinyint;not null;default:0" json:"is_starred"`
    Status    int8   `gorm:"type:tinyint;not null;default:1" json:"status"` // 1正常 2已删除
}

func (Friendship) TableName() string { return "friendships" }
```

**逐行解释**：

- `uniqueIndex:uk_user_friend` 作用在**两个字段上** → 生成复合唯一索引 `UNIQUE(user_id, friend_id)`
- `index:idx_user` 只作用在 `UserID` 上 → 查「我的好友」用
- `Remark` 是**我这一侧**的备注：A 给 B 改备注，不影响 B 那边的记录
- `Status` 是软删除标记（1 正常 / 2 已删）

### 4.2 friend_requests

```sql
UNIQUE (from_user_id, to_user_id)     -- 同一对用户只能有一条申请记录
INDEX  (to_user_id, status)           -- 「我收到的待处理申请」
```

**这里有个坑**：唯一索引导致「删除好友后重新申请」会冲突（旧申请记录还在）。

解法：**复用旧行**——查到旧记录就把 `status` 重置为 0，而不是插入新行。

### 4.3 blacklist

```sql
UNIQUE (user_id, blocked_user_id)
```

**注意**：取消拉黑用**物理删除**（`Unscoped().Delete`），不能用软删除。否则软删的行还占着唯一索引，下次再拉黑会冲突。

> **这是软删除 + 唯一索引的经典冲突**，面试常问。

## 五、聊天域（核心）

### 5.1 conversations：单聊和群聊共用一张表

```go
type Conversation struct {
    model.Model
    Type          int8       `gorm:"type:tinyint;not null;default:1;index" json:"type"` // 1单聊 2群聊
    GroupID       uint       `gorm:"not null;default:0" json:"group_id"`
    LastMessageID uint       `gorm:"not null;default:0" json:"last_message_id"`
    LastMessageAt *time.Time `json:"last_message_at,omitempty"`
}
```

**设计要点 1：单聊/群聊共用**

| 类型 | Type | 成员数 | GroupID |
|---|---|---|---|
| 单聊 | 1 | 2 | 0 |
| 群聊 | 2 | N | groups.id |

好处：**消息表不用区分单聊/群聊**，统一按 `conversation_id` 查。这是 IM 的通用做法：**会话 + 消息** 两层抽象。

**设计要点 2：为什么冗余 `LastMessageID` / `LastMessageAt`**

会话列表要显示「最后一条消息 + 时间」。如果不冗余：

```sql
-- 每个会话都要子查询一次 → N 次查询
SELECT m.* FROM messages m
WHERE m.conversation_id = ? ORDER BY m.id DESC LIMIT 1
```

冗余之后，会话列表一次查询搞定：

```sql
SELECT * FROM conversations WHERE id IN (我的会话) ORDER BY last_message_at DESC
```

**空间换时间**的典型应用。

### 5.2 conversation_members：成员 + 已读位置

```go
type ConversationMember struct {
    model.Model
    ConversationID    uint `gorm:"not null;uniqueIndex:uk_conv_user" json:"conversation_id"`
    UserID            uint `gorm:"not null;uniqueIndex:uk_conv_user;index:idx_user" json:"user_id"`
    Role              int8 `gorm:"type:tinyint;not null;default:0" json:"role"` // 0成员 1群主
    Mute              int8 `gorm:"type:tinyint;not null;default:0" json:"mute"`
    LastReadMessageID uint `gorm:"not null;default:0" json:"last_read_message_id"`
}
```

**`LastReadMessageID` 是未读数的关键**：

```
未读数 = 会话里 id > LastReadMessageID 且 sender != 我 的消息数
```

**为什么不建一张 `message_reads` 表**：

| 方案 | 存储 | 查询 |
|---|---|---|
| 每条消息一条已读记录 | 消息数 × 成员数（爆炸） | 复杂 |
| **last_read_message_id** | 每成员一行 | 一次比较 |

群聊 200 人、10 万条消息，前者是 2000 万行，后者是 200 行。**差距巨大。**

**索引设计**：

- `uk_conv_user(conversation_id, user_id)` 唯一 → 防同一会话重复加成员
- `idx_user(user_id)` → 查「我的所有会话」

### 5.3 messages：消息表

```go
type Message struct {
    model.Model
    ConversationID uint   `gorm:"not null;index:idx_msg_conv" json:"conversation_id"`
    SenderID       uint   `gorm:"not null;index:idx_msg_sender" json:"sender_id"`
    ClientMsgID    string `gorm:"type:varchar(64);not null;uniqueIndex:uk_sender_client" json:"client_msg_id"`
    Type           int8   `gorm:"type:tinyint;not null;default:1" json:"type"` // 1文本 2图片 3语音 4文件
    Content        string `gorm:"type:text;not null" json:"content"`
    Status         int8   `gorm:"type:tinyint;not null;default:1" json:"status"` // 1正常 2撤回
}
```

**设计要点 1：`ClientMsgID` + 唯一索引 = 幂等**

网络重试、用户连点都会导致同一条消息发多次。客户端生成唯一 ID，服务端 `UNIQUE(sender_id, client_msg_id)` 兜底：

- 第一次插入成功
- 重复插入报 `Duplicate` → 查出已有消息直接返回（幂等）

**设计要点 2：`Type` 用 tinyint 不用 enum**

```sql
-- ❌ enum 加新类型要 ALTER TABLE，大表很痛
type ENUM('text','image','voice','file')

-- ✅ tinyint 加类型只改代码
type TINYINT
```

**设计要点 3：`Content` 用 text**

文本可能很长；图片/语音/文件消息存 URL 或 JSON 元信息，`text` 也放得下（最大 64KB）。

### 5.4 消息分页：为什么用游标不用 offset

```sql
-- 首屏
SELECT * FROM messages
WHERE conversation_id = 100
ORDER BY id DESC LIMIT 20;

-- 上翻加载更多（传上一页最旧的 id）
SELECT * FROM messages
WHERE conversation_id = 100 AND id < 5000
ORDER BY id DESC LIMIT 20;
```

| 方式 | SQL | 问题 |
|---|---|---|
| offset | `LIMIT 20 OFFSET 1000` | 要扫描并跳过 1000 行，越翻越慢；新消息插入会错位 |
| **游标** | `id < last_id` | 走主键索引，恒定速度；不受新消息影响 |

**为什么 `id < last_id` 能走索引**：`idx_msg_conv(conversation_id)` 的叶子节点存主键，而主键有序 → 范围扫描 + 反向取即可。

## 六、群聊域

### groups

```go
type Group struct {
    model.Model
    ConversationID uint   `gorm:"not null;uniqueIndex:uk_group_conv"`
    OwnerID        uint   `gorm:"not null;index"`
    Name           string `gorm:"type:varchar(64);not null"`
    Announcement   string `gorm:"type:varchar(512);not null;default:''"`
    MemberCount    int    `gorm:"not null;default:0"`
    MaxMembers     int    `gorm:"not null;default:200"`
    Status         int8   `gorm:"type:tinyint;not null;default:1"` // 1正常 2已解散
}
```

**设计要点 1：`ConversationID` 唯一** —— 一个群对应一个会话，1:1

**设计要点 2：为什么冗余 `MemberCount`**

群列表要显示人数。不冗余就每次 `COUNT(*)`：

```sql
SELECT COUNT(*) FROM conversation_members WHERE conversation_id = ?   -- 每次列表都执行
```

冗余后加人/踢人时原子更新：

```go
tx.Model(&Group{}).Where("id = ?", g.ID).
    Update("member_count", gorm.Expr("member_count + ?", len(addIDs)))
```

**注意**：必须用 `gorm.Expr` 原子自增，不能「先读再写」（并发会丢更新）。

### outbox_messages

| 字段 | 说明 |
|---|---|
| event_type | 事件类型（如 `message.created`） |
| payload | 事件内容 JSON |
| status | 0 待发送 / 1 已发送 |

## 九、索引为什么这么建：反向推导

| 索引 | 支撑的查询 | 不加会怎样 |
|---|---|---|
| `users.uk_username` | 登录 `WHERE username = ?` | 每次登录全表扫 |
| `users.uk_phone` | 手机登录 | 同上 |
| `friendships.idx_user` | 好友列表 `WHERE user_id = ?` | 全表扫 |
| `friendships.uk_user_friend` | 防重复 + 判断是否好友 | 可能重复好友 |
| `conversation_members.idx_user` | 「我的会话」 | 全表扫 |
| `conversation_members.uk_conv_user` | 防重复加成员 | 成员重复 |
| `messages.idx_msg_conv` | 拉历史 | 全表扫 |
| `messages.uk_sender_client` | 幂等 | 消息重复 |
| `friend_requests.idx_to_status` | 申请列表 | 全表扫 |

### 一个反例：不该建索引的情况

```sql
-- ❌ 性别只有 0/1，索引选择性极差，MySQL 可能直接不用它
CREATE INDEX idx_gender ON users(gender);
```

**索引不是越多越好**：每个索引都会拖慢写入（INSERT 要维护所有索引）、占用磁盘。

## 十、常见表设计错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 不用唯一索引，只靠代码查重 | 并发下产生重复数据 | 加 `UNIQUE` |
| 软删除 + 唯一索引不处理 | 删除后无法重建 | 复用旧行 / 物理删除 |
| 用 `status` 同时表达「业务状态」和「删除」 | 查询条件混乱 | 业务状态 + `deleted_at` 分开 |
| 不冗余计数/最后消息 | 列表页 N 次查询 | 冗余 + 原子更新 |
| 手机号 `NOT NULL` | 多用户不填会冲突 | 可空 + 唯一 |
| 大字段放热点索引 | 索引膨胀 | 大字段单独表或 text |
| 所有字符串用 `VARCHAR(255)` | 索引/存储浪费 | 按实际长度设 |

## 十一、如果以后要加功能，表怎么改

| 新需求 | 改法 | 要不要新表 |
|---|---|---|
| 消息撤回 | 用已有的 `messages.status = 2` | 不用改 |
| 消息已读回执（精确到人） | 新建 `message_reads` 表 | 要 |
| 好友分组 | 用已有的 `friend_groups` | 不用改 |
| 群公告已读 | 新建 `group_announcement_reads` | 要 |
| 用户注销 | 用 `users.deleted_at` 软删 | 不用改 |
| 消息搜索 | 加全文索引或接 ES | 不用改 |

**设计得好不好，看加功能时改不改表**。本项目刻意预留了 `status`/`type` 字段，就是为了这个。

## 十三、面试怎么答（背这 3 句）

**问：好友关系为什么存两行？**

> 因为查「我的好友」要能走索引。存两行后 `WHERE user_id = ?` 直接命中 `idx_user`；
> 只存一行就得 `WHERE user_id = ? OR friend_id = ?`，`OR` 用不上索引，数据量大就全表扫。
> 代价是写两条，所以必须用事务保证成对。

**问：未读数怎么算？为什么不用已读表？**

> 在 `conversation_members` 存 `last_read_message_id`，未读数 = `id > last_read_message_id AND sender != 我` 的消息数。
> 建已读表是「消息数 × 成员数」的量级（200 人 × 10 万条 = 2000 万行），当前方案只要 200 行。

**问：软删除和唯一索引冲突怎么解？**

> 软删只是改标记、行还在，唯一索引仍占位。解法两种：
> ① 用 `Unscoped()` 查旧行，存在就恢复（重置 status）；
> ② 不需要历史的数据（如黑名单）直接物理删除。
