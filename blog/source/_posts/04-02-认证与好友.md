## 一、为什么用双 token

单 token 的矛盾：

- 有效期长 → 体验好，但泄露风险大、无法撤销
- 有效期短 → 安全，但频繁掉登录

**双 token**：

- `access token`：2 小时，每个请求携带，泄露窗口小
- `refresh token`：30 天，只用来换新 access，存服务端可撤销

用户只要 30 天内用过，refresh 自动续期 → **无感不掉登录**。

## 二、无感刷新的完整流程

```
① 登录 → 签发 access + refresh(jti) → Redis: SET refresh:{uid}:{jti} 1 EX 30d
② 调接口 → 中间件验 access
③ access 过期(401) → 客户端调 /token/refresh
     → 服务端验 refresh → GETDEL 消费旧 jti → 签发新 token 对（rotation）
④ 登出 → DEL refresh:{uid}:{jti}
```

### 关键点 1：用 GETDEL 原子消费

`Exists` + `Del` 是两条命令，中间有时间窗口，并发下两个请求都可能通过 → 都签发新 token，
rotation 就失效了。`GETDEL` 是原子命令，只有一个请求能成功。

### 关键点 2：rotation + 复用检测

每次刷新都换新 refresh，旧的作废。
如果旧 jti 不存在却仍被使用 → 可能被盗用 → **撤销该用户所有 refresh**（强制下线）。

### 关键点 3：并发刷新怎么办

5 个请求同时 401 会触发 5 次刷新，rotation 会让第 2~5 次用旧 token → 被判定盗用。

解法：

1. **客户端 single-flight**：刷新进行中，其他请求等待同一个结果
2. 服务端 `GETDEL` 防双签发
3. 宽限期：消费标记短 TTL，区分正常重试和盗用

## 三、JWT 的安全要点

```go
// 必须校验签名算法，防 alg=none / 算法混淆
if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
    return nil, fmt.Errorf("unexpected signing method")
}
```

其他要点：

- payload 是 **base64 不是加密**，只放 user_id/username，绝不放密码
- secret 从配置读，不硬编码
- access 短命 + refresh 可撤销

## 四、好友关系：双向两行

A、B 成为好友后插 `(A,B)` 和 `(B,A)` 两行。

- 查「我的好友」只需 `WHERE user_id=?`
- 每行可独立存备注/分组/星标
- 代价：写入要写两行 → **必须用事务**

## 五、接受好友申请：事务 + 条件更新

```go
tx.Transaction(func(tx *gorm.DB) error {
    // 条件更新：只有「发给我的、待处理的」才能接受
    res := tx.Model(&FriendRequest{}).
        Where("id = ? AND to_user_id = ? AND status = 0", reqID, userID).
        Update("status", 1)
    if res.RowsAffected == 0 {
        return errors.New("申请不存在或已被处理")
    }
    // 插两条好友关系
    upsertFriendship(tx, fromID, toID)
    upsertFriendship(tx, toID, fromID)
})
```

`WHERE status=0` 让「判断 + 修改」成为原子操作，天然抗并发重复接受。

## 六、踩过的坑

### 坑 1：软删除 + 唯一索引

删除好友只是 `status=2`，行还在。重新加好友时 INSERT 会撞唯一索引。
解法：`Unscoped()` 查旧行，存在就恢复 `status=1`。

### 坑 2：GORM 零值陷阱

改资料时只传昵称，其余字段是零值。用结构体 `Updates` 可能清空字段。
解法：**请求用指针 / 用 map 组装 / Select 指定字段**。

### 坑 3：先查后写的竞态

注册查重后插入，并发下两个请求都可能通过。
**唯一索引是最后防线**，业务层查重只是为了友好提示。
