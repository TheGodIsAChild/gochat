## 一、里程碑目标

做一个「账号 + 好友」闭环：

- 注册 / 登录（**双 token 无感刷新**）
- 资料查看 / 修改 / 用户搜索 / 隐私设置
- 好友申请（发 / 收 / 接受 / 拒绝）、好友列表、备注、删除、黑名单

验收（已全部实测通过）：

| # | 场景 | 结果 |
|---|---|---|
| 1 | 注册 | 200 |
| 2 | 重复注册 | 400 用户名已存在 |
| 3 | 密码错误登录 | 401 |
| 4 | 登录拿双 token | 200 |
| 5 | refresh 换新 token | 200 |
| 6 | 旧 refresh 再用 | 401（rotation 生效） |
| 7 | 登出 | 200 |
| 8 | 登出后 refresh | 401 |
| 9 | 无 token 访问 | 401 |
| 10 | 好友申请 → 接受 → 列表 | 200 |
| 11 | 重复接受 | 400（条件更新拦截） |
| 12 | 删除好友后重新加回 | 200（软删恢复） |

## 二、分层架构

```
HTTP 请求
  ↓
router/<domain>/  (handler：参数绑定、响应、鉴权取值)
  ↓
service/<domain>/ (业务逻辑、事务、事务边界)
  ↓
model / global.DB / global.Redis
```

**关键原则**：

1. **Handler 不写业务**：只做「解析 → 调 service → 写响应」。
2. **Service 是事务边界**：一个业务动作涉及多表时，事务写在 service。
3. **Handler 用 `*gin.Context`，Service 用 `context.Context`**：
   - 解耦：service 不依赖 gin，M6 拆 gRPC 时不用改
   - 可测试：单测 service 不用构造 gin.Context
   - 衔接：`c.Request.Context()`

## 三、数据库设计（6 张表）

| 表 | 作用 | 关键约束 |
|---|---|---|
| `users` | 用户主体 | `username` 唯一；`phone`/`email` 可空唯一 |
| `user_settings` | 隐私/通知设置（1:1） | `user_id` 唯一 |
| `friend_requests` | 好友申请 | `UNIQUE(from_user_id,to_user_id)` + `INDEX(to_user_id,status)` |
| `friendships` | 好友关系（**双向两行**） | `UNIQUE(user_id,friend_id)` |
| `friend_groups` | 好友分组 | `UNIQUE(user_id,name)` |
| `blacklist` | 黑名单 | `UNIQUE(user_id,blocked_user_id)` |

### 设计决策 1：好友关系存「双向两行」

A、B 成为好友后，插 `(A,B)` 和 `(B,A)` 两行。

- ✅ 「查我的好友」只需 `WHERE user_id=?`，不用 `OR`、不用排序
- ✅ 每行可以独立存「备注、分组、星标」（A 备注 B ≠ B 备注 A）
- ❌ 写入要写两行 → **必须用事务**

### 设计决策 2：软删除

- `friendships.status`：1 正常 / 2 已删除
- `friend_requests.status`：0 待处理 / 1 已接受 / 2 已拒绝

软删除保留历史，便于审计和"重新加好友"时恢复。

### 设计决策 3：可空字段用指针

`Phone *string`、`Birthday *time.Time`：区分「没填」和「填了空值」。
配合 MySQL 唯一索引「允许多个 NULL」，多个用户可以都不填手机号。

## 四、认证：双 Token 无感刷新（重点）

### 4.1 为什么需要双 token

| | 单 token | 双 token |
|---|---|---|
| 有效期长 | 体验好，但泄露风险大、无法撤销 | — |
| 有效期短 | 安全，但频繁掉登录 | — |
| 双 token | — | access 短（2h）+ refresh 长（30d），体验和安全兼得 |

- **access token**：2 小时，每个请求携带
- **refresh token**：30 天，只用来换新 access
- **refresh 的 jti 存 Redis**：让无状态 JWT 可以「撤销」

### 4.2 全流程

```
① 登录
  用户 → POST /login {username,password}
  服务端：查用户 → bcrypt 校验 → 签 access(2h) + refresh(30d,jti)
        → Redis: SET refresh:{uid}:{jti} 1 EX 30d
        → 返回 {access_token, refresh_token, user}

② 调业务接口
  客户端 → GET /users/me  Header: Authorization: Bearer <access>
  中间件：验签 → 校验 exp → 校验 type=access → c.Set("userId") → 放行

③ access 过期（401）→ 无感刷新
  客户端拦截器 → POST /token/refresh {refresh_token}
  服务端：验 refresh → 校验 type=refresh
        → Redis GETDEL refresh:{uid}:{jti}   ← 原子消费
        → 签新 access + 新 refresh（rotation）
        → Redis SET 新 jti
        → 返回新 token 对
  客户端：用新 access 重试原请求（用户无感）

④ 登出
  DELETE Redis 里的 refresh jti → refresh 立即失效
```

### 4.3 关键设计点

**① 为什么用 `GETDEL` 原子消费？**

`Exists` + `Del` 是两步，中间有时间窗口，并发下两个请求都可能通过 → 都签发新 token（rotation 失效）。
`GETDEL` 把「取 + 删」合成一个原子操作 → 只有一个请求能成功。

**② rotation（轮换）**

每次刷新都签发新 refresh，旧的作废。这样被盗的 refresh 只能用一次，且会触发复用检测。

**③ 复用检测**

旧 jti 不存在（被消费/已撤销）却仍被使用 → 可能是盗用 → **撤销该用户所有 refresh**（强制全设备下线）。
代价：客户端并发刷新会被误判。所以客户端要做 **single-flight（刷新单飞）**。

**④ 用户不存在/禁用时也要撤销**

刷新时查用户，若用户被删/禁用 → `DeleteAllRefreshJtiinRedis`，避免"已删除用户的 token 还能用"。

### 4.4 为什么 Parse 里必须校验算法

```go
if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
    return nil, fmt.Errorf("unexpected signing method")
}
```

不校验会有 **算法混淆攻击**：

- `alg=none`：攻击者把算法改成 none、签名留空，某些库会直接放行
- HS256/RS256 混淆：用服务端公开的 RSA 公钥当 HMAC 密钥签名，骗过服务端

## 五、好友模块

### 5.1 发好友申请要拦哪些情况

1. 不能加自己
2. 目标用户必须存在
3. 不能已是好友
4. 不能重复发「待处理」申请（已拒绝的可以重发）
5. 对方拉黑了我 → 拒绝（且用模糊提示，不暴露"你被拉黑"）
6. 对方关闭了「允许加好友」

> 这些「先查后写」的检查只是为了友好提示，**并发兜底靠数据库唯一索引**。

### 5.2 接受申请为什么必须用事务

一次接受要做两件事：

1. 把申请状态改成「已接受」
2. 插入两条好友关系（A→B、B→A）

不用事务的后果：

- 改了状态但插好友失败 → 申请显示已通过，但还不是好友（数据不一致）
- 插了好友但状态没改 → 可以重复接受，重复插入

### 5.3 用「条件更新 + RowsAffected」抗并发

```go
res := tx.Model(&FriendRequest{}).
    Where("id = ? AND to_user_id = ? AND status = 0", reqID, userID).
    Update("status", 1)
if res.RowsAffected == 0 {
    return errors.New("申请不存在或已被处理")
}
```

- `WHERE ... AND status=0` 让「判断」和「修改」成为**一个原子操作**
- 影响行数 = 0 → 被别人抢先处理 / 不是发给我的 / 不存在
- 天然抗「双击」「重试」「并发接受」

### 5.4 软删除 + 唯一索引的坑

两个真实踩过的坑（都在代码里修了）：

**坑 1：删除好友后重新加，INSERT 撞唯一索引**

`friendships` 有 `UNIQUE(user_id, friend_id)`，删除只是把 `status` 改成 2，行还在。
再次加好友时直接 `INSERT` → 撞唯一索引失败。

**解法**：`upsertFriendship()` 先 `Unscoped()` 查（含软删行），存在就恢复 `status=1`，不存在才插入。

**坑 2：重新发好友申请失败**

`friend_requests` 有 `UNIQUE(from_user_id, to_user_id)`，同一对用户只能有一行。
第二次发申请直接 `INSERT` → 撞唯一索引。

**解法**：先查旧行，存在就复用（重置 `status=0`、更新 message），不存在才插入。

> **面试点**：软删除 + 唯一索引天然冲突。要么复用旧行、要么把唯一索引加上删除标记列、要么对这类"开关型"数据用物理删除（如黑名单）。

## 七、注意点清单（本项目真实踩过的坑）

1. **GORM 的 `First` 返回 `*gorm.DB`**，不是 `(值, error)`：用 `.Error` 取错误
2. **`if err != nil` 分支必须处理 err**：不要 `return nil`（吞错误）
3. **GORM 零值陷阱**：结构体零值字段会被忽略 → 部分更新用**指针 / map / Select**
4. **`gorm.Model.ID` 是 `uint`**，JWT claims 是 `uint64`，注意转换
5. **双指针**：`var u *User; DB.First(&u)` 是 `**User`，应 `var u User; DB.First(&u)`
6. **`c.Get("key")` 的 key 必须和 `c.Set` 一致**，用常量防手滑
7. **`GetUint` vs `GetUint64`**：类型不匹配返回 0，不报错（极难查）
8. **`c.Abort()` 后要 `return`**，否则当前函数继续执行
9. **soft delete + 唯一索引**：重新创建会撞索引，要复用/恢复旧行
10. **N+1 查询**：批量 ID 用 `IN` 一次查，别循环查

## 九、最佳实践总结

| 实践 | 说明 |
|---|---|
| 分层单向依赖 | router → service → model |
| service 用 context.Context | 解耦框架、可测试、可迁移 gRPC |
| 统一响应格式 | `{code,message,data}`，handler 用共享包 |
| 常量代替魔法字符串 | context key、状态值 |
| 错误要向上抛 | 不吞 error、不把错误伪装成业务结果 |
| 事务尽量短 | 不在事务里做网络/IO |
| 唯一索引兜底并发 | 业务查重只是提示，DB 是最后防线 |
| 条件更新抗并发 | `WHERE status=0` + `RowsAffected` |
| 批量查询防 N+1 | `IN` 一次查 |
| DTO 分离 | 自己看 vs 别人看 vs 设置，别用一个 struct 到处返回 |
