## 一、复用会话抽象

M2 已经把「会话 + 成员 + 消息」抽象好了，所以群聊几乎是免费的：

- 群聊 = `type=2` 的会话 + `groups` 表（群元信息）
- 群消息发送/推送完全复用 M2 的 `SendMessage` / `PushMessage`

M3 新增的只是**群的生命周期管理**：建群、拉人、踢人、改资料、解散。

> 这就是好抽象的复利：M2 多花点心思，M3 直接受益。

## 二、groups 表设计

| 字段 | 说明 |
|---|---|
| conversation_id | 关联会话（唯一） |
| owner_id | 群主 |
| name / avatar | 群名称/头像 |
| announcement | 群公告 |
| member_count | 冗余人数 |
| max_members | 上限（默认 200） |
| status | 1 正常 / 2 已解散 |

### 为什么冗余 member_count

群列表要显示人数。不冗余的话每次都 `COUNT(*)`。
加人/踢人时用 `gorm.Expr("member_count + ?")` **原子自增**，避免并发覆盖。

## 三、建群必须用事务

建群要做 4 件事：

1. 创建会话（type=2）
2. 创建 groups 行
3. 插入群主（role=1）
4. 插入其他成员

不做事务的后果：

- 有会话没群 → 会话列表出现无名会话
- 有群没群主 → 没人能管理
- 有群没会话 → 群消息发不出去

## 四、权限模型

| 操作 | 谁可以 |
|---|---|
| 拉人进群 | 任何成员（类微信） |
| 踢人 | 只有群主 |
| 退群 | 任何成员（群主不能直接退） |
| 改群名/公告 | 只有群主 |
| 解散群 | 只有群主 |

统一校验套路：

```go
g, err := getGroupByID(ctx, groupID)   // 存在且未解散
if uint64(g.OwnerID) != operatorID { return errors.New("只有群主可以...") }
ok, _ := isMember(ctx, g.ConversationID, userID)
```

## 五、并发问题

### 人数上限有竞态

两个请求同时拉人，可能都通过 `member_count + n > max` 的校验 → 超员。

解法：

1. 事务里 `SELECT ... FOR UPDATE` 锁群行（悲观锁）
2. Redis 分布式锁
3. 接受轻微超员（产品上可容忍）

### 计数用原子表达式

```go
tx.Model(&Group{}).Where("id = ?", g.ID).
    Update("member_count", gorm.Expr("member_count + ?", len(addIDs)))
```

不要「先读再写」，并发会丢更新。

## 六、解散群

```go
status = 2          // 群标记已解散
软删除 conversation  // 会话列表不再出现
```

**保留数据**：群消息、群记录保留，便于审计/回溯。
IM 的群和消息一般软删，个人数据（如黑名单）可以物理删。
