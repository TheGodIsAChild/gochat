> 并发是这个项目最重要的技术含量。
> 本文不讲语法，只讲**项目里真实存在的 7 个并发点**：为什么需要并发、用了什么手段、为什么不用别的手段。
> 所有代码都来自 `internal/ws/` 和 `internal/service/`，可直接对照源码。

## 一、先复习：Go 并发的 4 个工具

| 工具 | 解决什么 | 什么时候用 |
|---|---|---|
| `goroutine` | 让任务并行执行 | IO 密集（网络、数据库）、需要后台处理 |
| `channel` | goroutine 之间传数据 / 排队 | 生产者-消费者、任务队列 |
| `sync.Mutex/RWMutex` | 保护共享内存 | 多个 goroutine 读写同一份数据 |
| `context` | 取消、超时、传值 | 所有可能阻塞的调用 |

### 一句话原则

> **能用 channel 传数据，就别共享内存；必须共享内存，才加锁。**
> **能用数据库的原子操作（唯一索引/条件更新）解决，就不要加锁。**

## 二、场景 1：HTTP 请求天然并发（gin 已经帮你做了）

```go
r.POST("/api/v1/register", Register)
```

gin 每收到一个请求就开一个 goroutine 执行 handler。所以「100 个用户同时注册」对 gin 来说是 100 个 goroutine 并行跑 `Register`。

**你不需要写任何并发代码，但必须知道共享了什么。**

### 陷阱：普通 map 并发读写会直接 panic

```go
// ❌ 两个请求同时执行 → fatal error: concurrent map writes
var userCache = map[uint64]string{}

func handler(c *gin.Context) {
    userCache[1] = "alice"    // 并发写，直接崩
}
```

**Go 的 map 不是并发安全的**。要么加锁，要么用 `sync.Map`，要么（更好）用 Redis。

本项目里 `global.DB`、`global.Redis` 都是并发安全的（内部有连接池和锁），可以放心在多 goroutine 里用。

## 三、场景 2：Hub 的读写锁（连接管理）

一个用户可能同时有手机、电脑、网页三个连接，所以 Hub 要维护 `userID → 多个连接`：

```go
type Hub struct {
    mu      sync.RWMutex
    clients map[uint64]map[*Client]struct{}
}
```

### 为什么用 RWMutex 而不是 Mutex

| 操作 | 频率 |
|---|---|
| 推送消息（读 clients） | **非常频繁** |
| 连接建立/断开（写 clients） | 相对少 |

读多写少 → 用读写锁，多个读可以并发，只有写才互斥。

### 注册和注销（真实代码）

```go
func (h *Hub) Register(c *Client) {
    h.mu.Lock()
    defer h.mu.Unlock()
    if h.clients[c.UserID] == nil {
        h.clients[c.UserID] = make(map[*Client]struct{})
    }
    h.clients[c.UserID][c] = struct{}{}
}

func (h *Hub) Unregister(c *Client) {
    h.mu.Lock()
    defer h.mu.Unlock()
    if conns, ok := h.clients[c.UserID]; ok {
        delete(conns, c)
        if len(conns) == 0 {
            delete(h.clients, c.UserID)   // 空 map 也删掉，避免内存泄漏
        }
    }
}
```

**注意 `defer h.mu.Unlock()`**：即使中间 panic 也能解锁。如果手写 `h.mu.Unlock()` 放在函数末尾，中间 return 就会死锁。

### 推送：先复制，再解锁（关键技巧）

```go
func (h *Hub) SendToUser(userID uint64, payload []byte) bool {
    h.mu.RLock()
    conns := h.clients[userID]
    // 复制一份连接列表，避免持锁期间做 channel 操作
    list := make([]*Client, 0, len(conns))
    for c := range conns {
        list = append(list, c)
    }
    h.mu.RUnlock()          // ← 先解锁

    for _, c := range list {
        c.Enqueue(payload)  // ← 锁外做 channel 操作
    }
    return len(list) > 0
}
```

**为什么必须这样写**：

如果持着读锁去 `c.Enqueue(payload)`，而 `Enqueue` 里可能触发 `c.Close()`（关闭连接）→ `Close` 里可能要拿写锁 → **死锁**（读锁还没释放，写锁拿不到）。

即使不死锁，持锁做 IO 也会把所有其他 goroutine 卡住。

> **这是并发编程最重要的习惯**：**锁只保护内存访问，不保护任何可能阻塞的操作。**

## 四、场景 3：读写双泵（gorilla/websocket 的限制）

```go
type Client struct {
    UserID uint64
    conn   *websocket.Conn
    hub    *Hub
    send   chan []byte     // 发送队列
    once   sync.Once
}
```

每个连接启动两个 goroutine：

```go
go client.WritePump()   // 唯一往 socket 写
go client.ReadPump()    // 唯一从 socket 读
```

### 为什么必须分开

`gorilla/websocket` 的文档明确写着：**一个连接同时只允许一个 goroutine 写**。
如果两个 goroutine 同时 `WriteMessage`，会 panic：

```
panic: concurrent write to websocket connection
```

所以设计成：

- 写操作 **只有** `WritePump` 能做
- 其他 goroutine 想发消息 → 往 `send channel` 塞数据 → `WritePump` 取出来写

这是「**共享资源单 goroutine 独占 + channel 排队**」的经典模式。

### WritePump 还负责心跳

```go
func (c *Client) WritePump() {
    ticker := time.NewTicker(pingPeriod)   // 每 54 秒
    defer func() {
        ticker.Stop()
        c.Close()
    }()

    for {
        select {
        case payload, ok := <-c.send:
            _ = c.conn.SetWriteDeadline(time.Now().Add(writeWait))
            if !ok {
                _ = c.conn.WriteMessage(websocket.CloseMessage, []byte{})
                return
            }
            _ = c.conn.WriteMessage(websocket.TextMessage, payload)
        case <-ticker.C:
            _ = c.conn.SetWriteDeadline(time.Now().Add(writeWait))
            if err := c.conn.WriteMessage(websocket.PingMessage, nil); err != nil {
                return
            }
        }
    }
}
```

**两个 select 分支**：一个是「有消息要发」，一个是「到点发心跳」。这就是写 goroutine 的全部工作。

**`SetWriteDeadline` 很重要**：如果客户端网络卡住，`WriteMessage` 会一直阻塞，没有超时就会**永久占用一个 goroutine**（goroutine 泄漏）。

## 五、场景 4：慢消费者隔离（真实代码）

问题：如果某个客户端网络很慢（或故意不读），它的 `send` 队列会一直满。推送方如果阻塞等待，**所有人都会被它拖死**。

解法（`client.go` 真实代码）：

```go
func (c *Client) Enqueue(payload []byte) {
    defer func() { _ = recover() }()   // 连接关闭后 channel 可能已关闭
    select {
    case c.send <- payload:
        // 入队成功
    default:
        // 发送队列满 → 直接断开这个慢连接，避免拖垮服务
        c.Close()
    }
}
```

### 逐行解释

- `defer recover()`：连接已经被关闭时，`send` channel 也关闭了，再往里写会 panic `send on closed channel`。这里兜住
- `select { case c.send <- payload: ... default: ... }` —— **non-blocking 写**：
  - 队列有空间 → 入队
  - 队列满 → 走 `default` → 断开这个连接
- **为什么是「断开」而不是「丢弃消息」**：WebSocket 是有序的，丢一条后面就乱了。断开让客户端重连、重新拉历史，语义更干净

> 这就是「**慢消费者隔离**」：一个慢客户端不能影响其他 999 个用户。

## 六、场景 5：群消息扇出限并发（真实代码）

200 人的群发一条消息，要给 200 个用户推送。如果无脑起 200 个 goroutine：

- goroutine 数量瞬时暴涨
- 对 Hub 的锁和网络造成尖峰压力

解法：带缓冲的 channel 当**信号量**：

```go
const pushConcurrency = 16
var pushSem = make(chan struct{}, pushConcurrency)

func fanout(memberIDs []uint64, frame []byte) {
    // 小会话：顺序推送，省掉 goroutine 开销
    if len(memberIDs) <= 10 {
        for _, uid := range memberIDs {
            DefaultHub.SendToUser(uid, frame)
        }
        return
    }

    // 大会话：并发 + 信号量限流
    var wg sync.WaitGroup
    for _, uid := range memberIDs {
        wg.Add(1)
        pushSem <- struct{}{}          // 获取令牌（满了就阻塞）
        go func(uid uint64) {
            defer wg.Done()
            defer func() { <-pushSem }()   // 释放令牌
            DefaultHub.SendToUser(uid, frame)
        }(uid)
    }
    wg.Wait()
}
```

### 三个细节

1. **`pushSem <- struct{}{}` 在 `go` 之前**：先拿令牌再起 goroutine，保证同时最多 16 个
2. **`go func(uid uint64)` 显式传参**：Go 1.22 之前，闭包直接捕获循环变量会出 bug（所有 goroutine 拿到最后一个值）
3. **小会话走顺序推送**：10 个人起 10 个 goroutine 反而慢，同步循环更快

## 七、场景 6：并发控制交给数据库（最推荐）

很多并发问题不需要锁，**数据库的原子操作就够了**。

### 6.1 唯一索引兜底

```sql
UNIQUE (sender_id, client_msg_id)   -- 并发重复发消息，第二条直接报 Duplicate
UNIQUE (from_user_id, to_user_id)   -- 并发重复加好友
```

```go
if errors.Is(err, gorm.ErrDuplicatedKey) {
    // 并发重复，返回已有数据（幂等）
}
```

**为什么不能只靠"先查后插"**：查和插之间有时间窗口，两个请求可能都通过查询。

### 6.2 条件更新（判断 + 修改原子化）

```go
res := tx.Model(&FriendRequest{}).
    Where("id = ? AND to_user_id = ? AND status = 0", reqID, userID).
    Update("status", 1)
if res.RowsAffected == 0 {
    return errors.New("申请不存在或已被处理")
}
```

`WHERE status = 0` 让「判断是否待处理」和「改成已处理」变成**一条原子语句**。

用户双击「接受」两次，第二次 `RowsAffected = 0`，直接报错——不会插入重复好友。

### 6.3 原子表达式（防丢更新）

```go
// ❌ 先读再写：并发下会丢更新
g := getGroup(id)
updateGroup(id, g.MemberCount + n)

// ✅ 交给数据库原子自增
tx.Model(&Group{}).Where("id = ?", id).
    Update("member_count", gorm.Expr("member_count + ?", n))
```

## 八、场景 7：优雅退出（信号 + context）

```go
// main.go
quit := make(chan os.Signal, 1)
signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
<-quit                                    // 阻塞等信号

srv.Shutdown(ctx)                         // 1. 停止接收新请求，等在途请求完成
ws.DefaultHub.CloseAll()                  // 2. 主动断开所有 WebSocket
mqCancel()                                // 3. 通知 worker 退出
grpcServers.Stop()                        // 4. 停 gRPC
core.CloseBaseServices()                  // 5. 释放 DB/Redis
```

### 顺序为什么重要

- 先停 HTTP：不再有新请求进来
- 再关 WS：客户端立刻感知并重连（不断开的话客户端会「假在线」）
- 最后关依赖：如果先关 DB，正在处理的请求会报错

### 每个后台 goroutine 都要有退出路径

```go
ctx, cancel := context.WithCancel(context.Background())
go mq.StartOutboxWorker(ctx)    // 内部 for { select { case <-ctx.Done(): return ... } }

// 退出时
cancel()
```

**没有退出路径的 goroutine = 泄漏**。

## 九、并发 bug 清单（都踩过）

| bug | 现象 | 原因 | 修复 |
|---|---|---|---|
| 数据竞争 | 偶发数据错乱 | 多 goroutine 读写同一变量 | `go test -race` |
| goroutine 泄漏 | 内存/协程数持续涨 | goroutine 阻塞在 channel/IO 上 | 加超时、加 ctx |
| 死锁 | 程序卡死 | 锁顺序不一致 / 持锁做 IO | 统一锁顺序、锁外做 IO |
| `send on closed channel` | panic | 连接关闭后仍推送 | `once` 关闭 + `recover` |
| 循环变量捕获 | 所有 goroutine 用同一个值 | 闭包捕获循环变量 | 显式传参 |
| map 并发写 | `fatal error` 直接崩 | 未加锁 | mutex / sync.Map |

## 十、怎么验证并发安全

```bash

# 2. 并发压测：同时 200 个连接注册/推送/注销

# 3. 看 goroutine 数量（接 pprof 后）
```

## 十二、面试怎么答（背这 3 句）

**问：你们项目的并发点在哪？**

> 主要在 WebSocket：Hub 管理所有连接（读多写少，用 RWMutex）、每个连接读写双泵、群消息扇出限 16 并发、
> 慢消费者用 non-blocking 入队隔离；另外业务层的并发控制交给数据库（唯一索引 + 条件更新），不加锁。

**问：为什么说锁里不能做 IO？**

> 持锁做 IO 会把锁持有时间放大到不可控。项目里 `Hub.SendToUser` 先持读锁复制连接列表，**立刻释放锁**，再在锁外 `Enqueue`。
> 如果持锁调用 `Enqueue`，而它可能触发 `Close()`（要拿写锁），就会死锁。

**问：怎么限制并发数？**

> 用带缓冲 channel 当信号量：`sem := make(chan struct{}, 16)`，起 goroutine 前 `sem <- struct{}{}`，结束时 `<-sem`。
> 项目里群消息扇出就是这样：小群（≤10 人）顺序推，大群并发但限制同时 16 个。
