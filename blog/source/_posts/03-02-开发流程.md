> 新手最常问：「我知道语法，但拿到需求不知道从哪下手。」
> 本文给一套可复用的 9 步流程，并用「消息撤回」这个真实需求完整走一遍。

## 一、9 步流程总览

```
1. 读懂需求 → 2. 拆功能点 → 3. 定数据模型（要不要加字段/表）
→ 4. 定接口（URL/入参/出参/错误）→ 5. 写 service（业务+事务）
→ 6. 写 handler（协议转换）→ 7. 接路由 + 权限
→ 8. 自测（curl/单测）→ 9. 补文档 + 提交
```

**顺序很重要**：先想清楚「数据长什么样、接口长什么样」，再写代码。
反过来（先写 handler）会导致反复返工。

## 二、第 1 步：读懂需求（问出隐藏约束）

需求：「用户能撤回自己发的消息，2 分钟内。」

要追问的隐藏问题：

| 问题 | 影响 |
|---|---|
| 撤回后对方还能看到吗？ | 显示「已撤回」提示 vs 直接消失 |
| 超过 2 分钟怎么办？ | 返回什么错误 |
| 群主能撤回别人消息吗？ | 权限模型 |
| 撤回要不要记审计？ | 是否软删 |
| 撤回后未读数要不要减？ | 数据一致性 |

**经验**：需求里没写清楚的，就是将来要返工的地方。

## 三、第 2 步：拆功能点

```
① 撤回接口：POST /messages/:id/recall
② 校验：是不是发送者、是否 2 分钟内、是否已撤回
③ 更新消息状态（软删/status=2）
④ 通知会话成员（WebSocket 推送 message_recalled）
⑤ 前端：气泡变成「你撤回了一条消息」
```

## 四、第 3 步：定数据模型

先看现有表够不够：

```go
type Message struct {
    // ...
    Status uint8 `gorm:"not null;default:1"`  // 1 正常 2 撤回
}
```

**结论**：`status` 字段已经存在（当初设计时预留了），**不需要改表**。

> 这就是「表设计留扩展位」的价值：`type`/`status` 用小整数枚举，加功能不用改结构。

如果确实要加字段：

```sql
ALTER TABLE messages ADD COLUMN recalled_at DATETIME NULL;
```

**注意**：给已有大表加字段要评估锁表时间（MySQL 8 支持 Online DDL，但仍需谨慎）。

## 五、第 4 步：定接口

```
POST /api/v1/messages/:id/recall
鉴权：需要登录

成功：200 { "code": 0, "message": "ok", "data": { "message_id": 123 } }
失败：
  400 消息不存在
  403 只能撤回自己的消息
  400 超过 2 分钟不能撤回
  400 消息已撤回
```

**接口设计三问**：

1. 资源是什么？（message）→ URL 用名词
2. 动作是什么？（撤回）→ 用 POST + 子路径
3. 失败怎么区分？（业务错误 vs 系统错误）→ 统一 code + message

## 六、第 5 步：写 service（核心）

```go
const recallWindow = 2 * time.Minute

func RecallMessage(ctx context.Context, userID, messageID uint64) error {
    var msg chatmodel.Message
    if err := global.DB.WithContext(ctx).First(&msg, messageID).Error; err != nil {
        if errors.Is(err, gorm.ErrRecordNotFound) {
            return errors.New("消息不存在")
        }
        return fmt.Errorf("查询消息失败: %w", err)
    }

    // 权限：只能撤回自己的
    if uint64(msg.SenderID) != userID {
        return errors.New("只能撤回自己的消息")
    }

    // 时间窗口
    if time.Since(msg.CreatedAt) > recallWindow {
        return errors.New("超过 2 分钟，不能撤回")
    }

    // 幂等：条件更新，已撤回则 RowsAffected=0
    res := global.DB.WithContext(ctx).Model(&chatmodel.Message{}).
        Where("id = ? AND status = ?", messageID, 1).
        Update("status", 2)
    if res.Error != nil {
        return fmt.Errorf("撤回失败: %w", res.Error)
    }
    if res.RowsAffected == 0 {
        return errors.New("消息已撤回")
    }

    // 异步通知（走 MQ，和发消息同一套机制）
    return nil
}
```

**这段代码体现的 5 个开发思路**：

1. **先查后判**：先拿到数据，再校验权限/时间
2. **错误分层**：业务错误用 `errors.New`，系统错误用 `%w` 包装
3. **幂等**：条件更新而不是「先查 status 再 update」
4. **软删**：改状态不删数据（IM 要可追溯）
5. **副作用异步化**：通知走 MQ，不阻塞返回

## 七、第 6 步：写 handler

```go
func RecallMessage(c *gin.Context) {
    userID := c.GetUint64(middleware.CtxUserID)
    idStr := c.Param("id")
    id, err := strconv.ParseUint(idStr, 10, 64)
    if err != nil {
        resp.Fail(c, http.StatusBadRequest, "消息 ID 非法")
        return
    }

    if err := chatservice.RecallMessage(c.Request.Context(), userID, id); err != nil {
        resp.Fail(c, http.StatusBadRequest, err.Error())
        return
    }
    resp.OK(c, gin.H{"message_id": id})
}
```

**handler 只做三件事**：取参数 → 调 service → 写响应。**不做业务判断**。

## 八、第 7 步：接路由 + 配置权限

```go
// internal/router/chat_router/chat_api.go
priv.POST("/messages/:id/recall", RecallMessage)
```

`priv` 组已经挂了 `middleware.Auth()`，所以自动要求登录。

**检查清单**：

- 路由放在公开组还是鉴权组？
- 需不需要额外限流？
- 前端有没有对应按钮？

## 九、第 8 步：自测

```bash
# 1. 发一条消息，拿到 id
curl -X POST $U/conversations/1/messages -H "Authorization: Bearer $TOKEN" \
     -d '{"client_msg_id":"t1","type":1,"content":"测试撤回"}'

# 2. 撤回
curl -X POST $U/messages/123/recall -H "Authorization: Bearer $TOKEN"
# 期望 {"code":0,...}

# 3. 重复撤回 → 期望 400 消息已撤回
# 4. 撤回别人的消息 → 期望 400 只能撤回自己的消息
# 5. 查历史 → 确认 content 或 status 已变
```

**自测要覆盖**：正常路径、权限拒绝、幂等重试、边界（时间窗口）。

## 十、第 9 步：补文档 + 提交

- 更新接口文档（README 的 API 表）
- 如果是重要功能，写一段设计说明
- `git commit -m "feat(chat): 消息撤回（2 分钟窗口 + 权限校验 + 幂等）"`

## 十一、这套流程的通用性

| 需求 | 复用这套流程的方式 |
|---|---|
| 消息已读回执 | 表用 last_read_message_id（已有）→ 新接口 → 推送 |
| 群公告 | groups 表加字段 → 改群信息接口扩展 |
| 好友分组 | friend_groups 表已有 → 接口 + 前端 |
| 消息搜索 | 新查询 + 索引/ES，不用改写入链路 |
| 拉黑后禁止发消息 | 在 SendMessage 里加一层校验 |

**核心**：先看「数据模型支不支持」，再看「接口怎么设计」，最后写代码。

## 十二、新手最容易犯的 5 个错

| 错误 | 后果 |
|---|---|
| 不追问需求直接写 | 返工 |
| 先写代码后想数据模型 | 改表改到崩溃 |
| 业务逻辑塞 handler | 无法复用/测试 |
| 只测正常路径 | 上线被边界情况打脸 |
| 不做幂等 | 用户连点产生脏数据 |

## 十三、面试问法

1. 接到一个需求你的开发流程是什么？
2. 怎么判断要不要加表/加字段？
3. 接口设计要考虑哪些方面？
4. 你怎么保证接口幂等？
5. 你怎么自测？只测正常路径吗？
6. 需求不明确时你会怎么办？
