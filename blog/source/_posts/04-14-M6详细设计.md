## 一、里程碑目标

把单体按职责拆成两个内部服务，用 **gRPC** 通信，再加一个 HTTP gateway：

```
客户端 ──HTTP──► gateway(:8080) ──gRPC──► user service(:9001)
                                  └──────► chat service(:9002)
```

验收（已实测）：

| 场景 | 结果 |
|---|---|
| gRPC 端口监听 | 9001 / 9002 |
| gateway → gRPC 查用户 | 200 |
| gateway → gRPC 批量查用户 | 200 |
| gateway → gRPC 发消息 | 200 |
| gateway → gRPC 拉历史 | 200 |
| gRPC NotFound 错误传播 | 502 + `code = NotFound` |

## 二、为什么拆微服务？单体哪里会痛？

| 痛点 | 单体 | 微服务 |
|---|---|---|
| 扩缩容 | 整包一起扩（聊天流量大也要把用户服务一起扩） | 按需扩某个服务 |
| 故障隔离 | 一个模块 OOM 全挂 | 只挂一个服务 |
| 团队协作 | 所有人改一个仓库 | 按服务划分 ownership |
| 技术栈 | 绑定一套 | 各服务可独立选型 |
| 部署 | 改一行要全量发布 | 只发布改动的服务 |

**代价**：分布式复杂度（网络调用失败、数据一致性、服务发现、链路追踪）。

> **面试话术**："我们项目 M0–M5 先做单体跑通，M6 再拆——因为只有先体会单体的痛点，
> 才知道为什么拆。拆分时按领域边界（用户域 / 聊天域），不是按技术分层。"

---

## 三、怎么拆：按领域，不按技术

```
❌ 错误拆法：controller 服务 / service 服务 / dao 服务（按技术分层）
✅ 正确拆法：用户服务（注册/资料/好友） / 聊天服务（会话/消息/WS） / 网关
```

本项目 M6 拆成：

| 服务 | 职责 | 端口 |
|---|---|---|
| **user service** | 用户查询、批量查询（后续可扩注册/好友） | 9001 |
| **chat service** | 发消息、拉历史（后续可扩会话/群） | 9002 |
| **gateway** | HTTP 入口 + 鉴权 + 限流 + 调 gRPC | 8080 |

## 四、gRPC 核心知识（面试必问）

### 4.1 gRPC vs REST

| | REST/JSON | gRPC |
|---|---|---|
| 传输 | HTTP/1.1 | **HTTP/2**（多路复用） |
| 序列化 | JSON（文本） | **protobuf**（二进制，体积小） |
| 契约 | OpenAPI（可选） | **.proto 强契约** |
| 流式 | 不支持（除 SSE） | **支持四种流** |
| 性能 | 一般 | 高（尤其内部服务间） |
| 浏览器支持 | 原生 | 需要 grpc-web |

**结论**：对外用 REST/HTTP，内部服务间用 gRPC。

### 4.2 gRPC 的四种调用

1. **Unary**（一元）：一请求一响应（本项目使用）
2. **Server streaming**：服务端流（如订阅消息）
3. **Client streaming**：客户端流（如上传）
4. **Bidirectional streaming**：双向流

### 4.3 本项目的特殊说明：用 JSON codec 代替 protobuf

标准流程是：

```
写 .proto → protoc 生成 .pb.go → 用生成的服务端/客户端代码
```

**本机没有 protoc/buf**（buf 安装被网络中断），所以本项目用 gRPC 的**自定义 codec**：

```go
// 传输层仍然是真正的 gRPC（HTTP/2、超时、状态码、流控）
// 只是 body 用 JSON 而非 protobuf
grpc.NewServer(grpc.ForceServerCodec(JSONCodec{}), ...)
conn.Invoke(ctx, method, req, resp, grpc.ForceCodec(JSONCodec{}))
```

**换回 protobuf 只需**：把 `contract.go` 的 struct 换成 .proto 生成的类型、把 codec 换成默认 proto codec。
**服务实现逻辑完全不用改**——这正好说明：微服务的核心是「服务边界 + 接口契约」，不是序列化格式。

> 面试时如实说："我用 gRPC + 自定义 JSON codec 实现，因为环境没有 protoc；
> 换成 protobuf 只需替换 codec 和生成代码，架构不变。"

## 五、gateway 模式

### 5.1 为什么需要 gateway

内部服务用 gRPC，但浏览器/App 不直接说 gRPC。gateway 负责：

- **协议转换**：HTTP/JSON ↔ gRPC
- **鉴权**：统一在入口做 JWT 校验（内部服务信任 gateway）
- **限流**：在入口限流保护后端
- **聚合**：一个页面要调多个服务时，gateway 聚合返回

### 5.2 本项目 gateway 路由

| 路径 | 作用 |
|---|---|
| `GET /api/v1/rpc/users/:id` | → user service GetUser |
| `GET /api/v1/rpc/users?ids=` | → user service BatchGetUsers |
| `POST /api/v1/rpc/messages` | → chat service SendMessage |
| `GET /api/v1/rpc/conversations/:id/messages` | → chat service ListMessages |

### 5.3 错误码映射

gRPC 状态码 → HTTP：

| gRPC code | HTTP |
|---|---|
| NotFound | 404（本项目 gateway 统一返回 502 + 原始信息） |
| InvalidArgument | 400 |
| Internal | 500 |
| Unavailable | 503 |

## 六、微服务必须面对的 5 个新问题

1. **服务发现**：怎么知道 user service 的地址？（配置 / Consul / Etcd / K8s Service）
2. **超时与重试**：网络调用会失败，必须设超时（`context.WithTimeout`），重试要幂等
3. **熔断**：下游持续失败时快速失败，避免雪崩
4. **链路追踪**：一个请求跨多个服务，需要 trace_id 串起来
5. **数据一致性**：跨服务不能用一个事务 → 用 MQ / Saga / TCC（M7 讲）

> **面试高频**：微服务拆分的难点不是拆，是拆完后的分布式问题。

## 八、注意点清单

1. **按领域拆，不按技术层拆**
2. **内部服务不要直接对外暴露**，统一走 gateway
3. **鉴权在 gateway 做**，内部服务信任 gateway（或用 mTLS/内部 token）
4. **gRPC 调用必须带超时**（`context.WithTimeout`），否则下游卡死会拖垮调用方
5. **错误要映射**：gRPC status → HTTP 状态码
6. **一个进程内起多个 gRPC server 只是演示**，真实部署是独立进程/容器
7. **protobuf 版本管理**：字段只加不删，用 reserved 标记废弃字段
8. **服务地址不要硬编码**，生产用服务发现
