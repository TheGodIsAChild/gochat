> 面试常问：「群里 10 个人同时发消息，怎么保证大家看到的顺序一致？」
> 这题的关键不是"加锁"，而是先想清楚：**顺序由谁决定**。

## 一、先把问题拆开：三种"顺序"

很多人答不清，是因为没说清在说哪种顺序：

| 顺序 | 含义 | 谁需要 |
|---|---|---|
| **入库顺序** | 消息在数据库里落下来的先后 | 服务端 |
| **推送顺序** | 客户端收到 WebSocket 通知的先后 | 客户端（可容忍乱序） |
| **展示顺序** | 界面上气泡的上下顺序 | **用户（必须一致）** |

**结论**：入库顺序必须唯一且单调；推送顺序不保证；展示顺序由客户端按"权威顺序"重排。

## 二、本项目的答案：**数据库自增主键 = 唯一顺序源**

`messages` 表的主键 `id` 是 MySQL 自增列，**每次 INSERT 单调递增**。

```
A 发：INSERT → id=100
B 发：INSERT → id=101
C 发：INSERT → id=102
```

不管 A/B/C 的客户端时间谁快谁慢、网络谁先到，**最终顺序由数据库的写入顺序决定，所有人一致**。

### 为什么不用 `created_at` 排序？

| 方案 | 问题 |
|---|---|
| 客户端时间 | 各设备时钟不准，甚至可被篡改 |
| 服务端 `time.Now()` | 多实例时钟漂移；同一毫秒并发无法区分先后 |
| 雪花 ID / 时间戳 ID | 只保证"趋势递增"，跨实例仍可能倒挂 |
| **数据库自增 id** | ✅ 单库单表下严格单调、写入即定序 |

所以本项目所有列表查询都按 id 排序：

```sql
-- 历史消息（游标分页）
SELECT * FROM messages
WHERE conversation_id = ? AND id < ?
ORDER BY id DESC LIMIT 20;
```

**游标分页也依赖 id 单调**：用 `id < last_id` 翻页，天然不会乱序、不会重复。

## 三、那推送乱序了怎么办？

推送（WebSocket）只是"通知你去看"，**不是权威数据源**。

可能出现乱序的地方有 4 处：

| 场景 | 为什么会乱 |
|---|---|
| 不同发送者并发 | 各自请求到达服务端顺序 ≠ 界面顺序 |
| MQ 异步推送 | outbox worker 每 2 秒轮询，不同消息出队时间不同 |
| 多实例 consumer | 每个实例消费队列的一个子集，各推自己的在线用户 |
| 断线重连 | 断线期间的消息根本没收到 |

### 客户端的处理原则：**按 id 重排 + 去重 + 补洞**

本项目 `web/js/app.js` 做了三件事：

```js
// ① 按 id 升序排列（乐观消息 id<0，永远排在最后）
function sortMessages() {
  S.messages.sort((a, b) => {
    const aPending = a.pending || a.id < 0;
    const bPending = b.pending || b.id < 0;
    if (aPending && bPending) return a.id - b.id;
    if (aPending) return 1;      // 发送中的气泡放最后
    if (bPending) return -1;
    return a.id - b.id;          // 已确认消息按服务端 id 排
  });
}

// ② 去重：同 id 或同 client_msg_id 只保留一条
if (S.messages.some(x => x.id === m.id ||
    (x.client_msg_id && x.client_msg_id === m.client_msg_id && x.sender_id === m.sender_id))) return;

// ③ 重连补洞：断线期间可能漏推送，重新拉最新一页
WS.on('open', () => {
  if (S.currentConv) loadNewestMessages(S.currentConv.conversation_id);
});
```

> **核心思想：推送可以乱、可以丢；只要最终按 id 重排 + 从历史接口补齐，界面就是对的。**
> 这就是 IM 常说的「**推拉结合**」：推送保实时，拉取保正确。

## 四、如果是"严格顺序"场景，怎么做得更强

单库自增在本项目够用，但下面这些场景需要更强方案：

| 场景 | 问题 | 方案 |
|---|---|---|
| 分库分表 | 多个 MySQL 各自自增，id 不再全局单调 | **每会话序列号 seq** |
| 需要"严格连续、可检测缺失" | 自增 id 全局跳号（别的会话占号） | **每会话 seq** |
| 超大规模（万群 × 高并发） | 单表写入瓶颈 | **单写者分区** 或 分布式日志 |

### 方案 A：每会话序列号（最常用）

```
seq = INCR conversation:{id}:seq      （Redis 原子自增）
```

消息表加字段并建唯一索引：

```sql
ALTER TABLE messages ADD COLUMN seq BIGINT NOT NULL DEFAULT 0;
ALTER TABLE messages ADD UNIQUE KEY uk_conv_seq (conversation_id, seq);
```

好处：

- **每会话连续**：客户端可以检测 `seq` 是否跳号 → 发现缺失立刻拉取
- 与分库分表兼容（每个会话一个序列）
- 排序直接用 `ORDER BY seq`

代价：多一次 Redis 调用；Redis 挂了要降级（用数据库行锁/表自增兜底）。

### 方案 B：单写者分区（Kafka / MQ 顺序）

```
按 conversation_id 哈希 → 同一分区的消息由同一个消费者串行处理
```

- 优点：分区内严格有序，天然水平扩展
- 缺点：需要消息中间件支持（Kafka partition 有序；RabbitMQ 单队列单消费者有序，多消费者会分散）

### 方案 C：分布式共识（Raft/Paxos）

etcd、ZooKeeper、TiKV 这类系统用共识算法给写入定序。**IM 场景一般用不到**，成本太高。

### 四种方案对比

| 方案 | 顺序强度 | 复杂度 | 适用 |
|---|---|---|---|
| **数据库自增 id**（本项目） | 单库全局单调 | ⭐ 最低 | 单体/单库 |
| 每会话 seq（Redis） | 每会话连续 | ⭐⭐ | 中等规模、分库分表 |
| 单写者分区 | 分区内严格 | ⭐⭐⭐ | 大规模、已有 MQ |
| Raft/Paxos | 强一致全局 | ⭐⭐⭐⭐ | 金融级/元数据 |

## 五、本项目的取舍与改进路径

### 现在够用的原因

- 单库单表，`id` 严格单调
- 所有查询按 id 排序 + 游标分页
- 客户端按 id 重排 + 重连补拉

### 如果将来要升级

| 触发条件 | 改造点 |
|---|---|
| 消息表分库分表 | 加 `seq`（每会话 Redis INCR）+ 唯一索引，排序改用 seq |
| 要支持"消息不丢"检测 | 客户端按 seq 连续性判断，缺了主动拉 `after_seq` |
| 群成员几十万 | 扇出改"读扩散"（拉模型）+ 未读数分离 |
| 多写多读一致性要求高 | 写入走单写者（按会话路由） |

> **面试可以主动说**：我们现在用数据库自增 id 保证顺序，因为单库；如果分库分表，会引入每会话 seq。

## 六、顺带一个常被追问的点：群消息扇出顺序

群消息推给 200 人时，`fanout` 是**并发推送**（信号量限 16）——这意味着**不同成员收到推送的先后不同**。

这没关系，因为：

1. 推送只是通知，顺序不重要
2. 每个成员打开会话时都会拉历史（按 id 排序）
3. 客户端收到推送后也按 id 重排

> 如果要求"所有成员同时看到同一条消息"，那是**同步/广播语义**，需要换成"按成员串行推送"或"客户端预约同步展示"，成本高、IM 一般不做。

## 七、面试问答（8 题）

**1. 群消息并发，怎么保证顺序？**

> 顺序由单一权威源决定：数据库自增主键 id。写入顺序即最终顺序。
> 客户端按 id 排序展示，推送乱序不影响结果。

**2. 为什么不用时间戳排序？**

> 客户端时钟不可信、多实例服务端时钟有漂移、同毫秒并发无法区分先后。自增 id 没有这些问题。

**3. MQ 异步推送会不会乱序？**

> 可能。但推送只是通知，客户端按 id 重排 + 从历史接口补拉，最终展示顺序仍然正确（推拉结合）。

**4. 多实例部署下顺序还一致吗？**

> 一致。顺序由数据库写入决定，与哪个实例推送无关；每个实例只推自己的在线用户。

**5. 断线期间的消息怎么办？**

> 重连后拉最新一页（本项目 `loadNewestMessages`），或用游标 `after_id`/`after_seq` 增量补。

**6. 分库分表后自增 id 还单调吗？**

> 不单调了。要引入每会话序列号 `seq`（Redis INCR 或号段），并建 `UNIQUE(conversation_id, seq)`。

**7. 怎么检测消息缺失？**

> 全局自增 id 会跳号（别的会话占号），不能靠 +1 检测；
> 每会话 seq 是连续的，客户端发现 seq 跳号即可主动拉取。

**8. 群消息扇出并发会破坏顺序吗？**

> 不会影响最终展示顺序。扇出并发只影响"谁先收到通知"，客户端以 id 排序为准。
