> Go 的 `error` 是需要认真设计的。处理得好，线上问题 5 分钟定位；处理得差，只能靠猜。
> 本文讲清 4 件事：错误怎么产生、怎么包装、怎么分层、怎么记日志。

## 一、Go 错误的三种类型

```go
// ① 哨兵错误：预定义的、可比较的错误值
var ErrUserNotFound = errors.New("用户不存在")

// ② 自定义错误类型：带上下文字段
type ValidationError struct{ Field, Msg string }
func (e *ValidationError) Error() string { return e.Field + ": " + e.Msg }

// ③ 包装错误：加一层上下文，保留原始错误链
return fmt.Errorf("查询用户失败: %w", err)
```

## 二、%w 与错误链

```go
// 底层
if err := db.First(&user, id).Error; err != nil {
    return fmt.Errorf("查询用户失败: %w", err)     // %w 包装，保留因果链
}

// 上层判断
if errors.Is(err, gorm.ErrRecordNotFound) {       // Is：判断是不是某个哨兵错误
    return errors.New("用户不存在")
}
```

| 函数 | 作用 |
|---|---|
| `errors.Is(err, target)` | 错误链里有没有 target |
| `errors.As(err, &target)` | 错误链里能不能转成某个类型 |
| `%w` | 包装并保留链 |
| `%v` | 只格式化，丢失链（无法 Is/As） |

**常见错误**：用 `%v` 包装 → 上层 `errors.Is` 失效。

## 三、分层错误处理

```
db 层：返回原始错误（gorm.ErrRecordNotFound / driver 错误）
  ↓
service：包装成业务语义（fmt.Errorf("查询消息失败: %w", err)）
  ↓
handler：翻译成用户可读 + HTTP 状态码
```

### 本项目示例

```go
// service：系统错误用 %w，业务错误用 errors.New
func RecallMessage(...) error {
    if err := global.DB.First(&msg, id).Error; err != nil {
        if errors.Is(err, gorm.ErrRecordNotFound) {
            return errors.New("消息不存在")            // 业务错误
        }
        return fmt.Errorf("查询消息失败: %w", err)      // 系统错误
    }
    if uint64(msg.SenderID) != userID {
        return errors.New("只能撤回自己的消息")          // 业务错误
    }
    return nil
}

// handler：统一返回
if err := chatservice.RecallMessage(...); err != nil {
    resp.Fail(c, http.StatusBadRequest, err.Error())
    return
}
```

**关键原则**：**业务错误可以直接给用户看；系统错误不要暴露细节**。

## 四、绝不吞错误

```go
// ❌ 吞掉：上层以为成功
if err != nil {
    return nil
}

// ❌ 只打日志不返回：调用方继续执行，数据可能不一致
if err != nil {
    log.Println(err)
}

// ✅ 要么处理，要么返回
if err != nil {
    return fmt.Errorf("xxx 失败: %w", err)
}
```

**检查方法**：搜代码里 `if err != nil {` 后面是不是都有 `return` / `continue` / 明确处理。

## 五、panic 与 recover

**原则**：`panic` 只用于「程序无法继续」的场景（如初始化失败、数组越界等编程错误）。
**业务错误永远不要 panic**。

```go
// main：初始化失败 → 无法继续 → log.Fatal（退出码 1）
if err := core.InitBaseServices(); err != nil {
    log.Fatalf("初始化基础服务失败: %v", err)
}

// 中间件：兜住 handler 里的 panic，避免整个进程挂掉
func Recovery() gin.HandlerFunc {
    return gin.CustomRecovery(func(c *gin.Context, err any) {
        log.Printf("panic: %v\n%s", err, debug.Stack())
        resp.Fail(c, 500, "服务器内部错误")
    })
}
```

| 场景 | 用什么 |
|---|---|
| 可预期的失败（用户不存在） | `return error` |
| 不可恢复（配置错、端口占用） | `log.Fatal` |
| 防御第三方库 panic | `recover` |
| 业务逻辑错误 | **绝不 panic** |

## 六、日志规范

### 分级

| 级别 | 用途 | 例子 |
|---|---|---|
| DEBUG | 开发调试 | SQL、入参 |
| INFO | 正常关键事件 | 服务启动、用户登录 |
| WARN | 可恢复的异常 | MQ 连接失败降级、重试 |
| ERROR | 需要人工介入 | DB 失败、未知 panic |
| FATAL | 进程无法继续 | 端口占用、配置缺失 |

### 结构化日志

```go
// ❌ 字符串拼接，无法检索
log.Printf("user %d login success from %s", uid, ip)

// ✅ 结构化，方便 ELK/Loki 检索
log.Printf("event=login user_id=%d ip=%s result=success", uid, ip)
```

生产建议用 `slog`（Go 1.21+ 标准库）或 `zap`：

```go
slog.Info("login success", "user_id", uid, "ip", ip)
```

### 必须记录的信息

| 场景 | 记录内容 |
|---|---|
| 请求入口 | method、path、userID、耗时、状态码 |
| 外部调用失败 | 目标服务、耗时、错误 |
| 状态变更 | 谁、做了什么、结果 |
| 异常 | 错误链 + 堆栈 + 上下文 |

### 绝不能记录的信息

```
❌ 密码、密码哈希
❌ token / refresh token（完整值）
❌ 手机号/身份证完整值（脱敏：138****8000）
❌ 数据库连接串（含密码）
❌ 完整配置结构体
```

> 本项目踩过坑：启动时 `log.Printf("%+v", global.Config)` 会把 DB 密码和 JWT secret 打进日志。

## 七、请求日志中间件

```go
func Logger() gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()
        c.Next()                       // 执行后续 handler
        cost := time.Since(start)
        log.Printf("method=%s path=%s status=%d cost=%s ip=%s user_id=%v",
            c.Request.Method, c.Request.URL.Path, c.Writer.Status(),
            cost, c.ClientIP(), c.Get(middleware.CtxUserID))
    }
}
```

**注意**：`c.Next()` 之前是进入，之后才能拿到状态码和耗时。

## 八、错误与日志的配合

```go
// 错误逐层包装（保留因果链），只在最外层记录一次完整日志
func handler(c *gin.Context) {
    if err := svc.DoSomething(ctx); err != nil {
        log.Printf("event=do_something_failed user_id=%d err=%v", uid, err)  // 记日志
        resp.Fail(c, 500, "操作失败")                                        // 返回给用户
        return
    }
}
```

**反模式**：每一层都 log 一次 → 一条错误刷屏 3 次，难以定位。

## 九、错误处理检查清单

- [ ] 每个 `if err != nil` 都有明确处理（return / 降级 / 打日志）
- [ ] 系统错误用 `%w` 包装，业务错误用 `errors.New`
- [ ] 不把原始错误直接返回给用户（防泄露）
- [ ] panic 只在初始化 / 防御第三方库时使用
- [ ] 日志有级别、有上下文、不含敏感信息
- [ ] 错误日志只在最外层记录一次
