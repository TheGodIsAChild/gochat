> 这是整套文章里**最重要的一篇**。
> 我们以「用户注册」为例，从一条 curl 命令开始，一路追到 MySQL 的 INSERT 语句，
> 把中间经过的 **9 个环节**全部拆开，每段代码都来自项目真实源码。

看完这篇，项目里 80% 的代码你都能读懂。

## 一、先看请求长什么样

```bash
curl -X POST http://127.0.0.1:8080/api/v1/register \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"123456","nickname":"爱丽丝"}'
```

成功响应：

```json
{"code":0,"message":"ok","data":{"user_id":1,"username":"alice","nickname":"爱丽丝"}}
```

失败响应（用户名重复）：

```json
{"code":400,"message":"用户名已存在"}
```

**这条请求要经过 9 个环节**才能变成数据库里的一行数据。

## 二、全景图

```
 ①  net/http  收到 TCP 连接，解析 HTTP 报文
 ②  Gin 引擎  匹配路由 POST /api/v1/register
 ③  中间件链  RateLimit(20/分钟) → handler
 ④  handler   ShouldBindJSON 解析 + 校验请求体
 ⑤  service   查重 → bcrypt 加密 → 开事务
 ⑥  GORM      Create(user) → INSERT users
 ⑦  GORM      Create(settings) → INSERT user_settings
 ⑧  事务提交 / 回滚
 ⑨  resp.OK   序列化成 JSON 写回
```

下面一站一站走。

## 三、第 1 站：请求怎么进来的（main.go）

```go
srv := &http.Server{
    Addr:    global.Config.Server.Addr,
    Handler: router.NewRouter(),   // ← 所有请求交给 Gin 处理
}
go srv.ListenAndServe()
```

**逐行解释**：

- `http.Server` 是 Go 标准库的 HTTP 服务器
- `Handler: router.NewRouter()` 把 Gin 引擎作为请求处理器。Gin 实现了 `http.Handler` 接口，所以能直接塞进去
- `go srv.ListenAndServe()` 在一个 goroutine 里阻塞监听——**主 goroutine 继续往下走去等退出信号**（这就是优雅退出能实现的原因）

> **你可能问**：为什么不用 `r.Run()`？
> `r.Run()` 内部也是 `http.ListenAndServe`，但它是阻塞的，没机会处理 SIGTERM 信号。用 `http.Server` 才能 `srv.Shutdown()` 优雅关闭。

## 四、第 2 站：路由怎么匹配到的（router.go）

```go
func NewRouter() *gin.Engine {
    r := gin.Default()          // 带 Logger + Recovery 中间件

    health.HealthRouter(r)
    userapi.UserRouter(r)       // ← 用户相关路由在这里注册
    // ... 其他模块

    return r
}
```

`internal/router/user_router/user_api.go`：

```go
func UserRouter(r *gin.Engine) {
    // 公开组：不需要登录
    pub := r.Group("/api/v1")
    {
        pub.POST("/token/refresh", Refresh)
    }

    // 登录/注册：挂限流中间件
    authGroup := r.Group("/api/v1", middleware.RateLimit(20, time.Minute))
    {
        authGroup.POST("/register", Register)
        authGroup.POST("/login", Login)
    }

    // 鉴权组：整组挂 Auth 中间件
    priv := r.Group("/api/v1", middleware.Auth())
    {
        priv.POST("/logout", Logout)
        priv.GET("/users/me", GetUserProfile)
        // ...
    }
}
```

**逐行解释**：

- `r.Group("/api/v1")` 创建路由组，组内路径自动加前缀
- `r.Group("/api/v1", middleware.Auth())` —— 第二个参数是中间件，**组内所有路由执行前都会先跑它**
- **为什么分组**：把「需要登录」和「不需要登录」的接口分开。如果一个个加中间件，早晚会漏掉一个——那就是安全事故

Gin 内部用 **radix tree（前缀树）** 存路由。`/api/v1/register` 会被拆成节点，匹配时按字符逐段比对，时间复杂度接近 O(路径长度)，比线性遍历所有路由快得多。

## 五、第 3 站：中间件链怎么执行的

注册接口挂了限流中间件。中间件的执行模型是**洋葱模型**：

```
请求 → [限流 进入] → [handler] → [限流 返回] → 响应
```

代码长这样（示意）：

```go
func RateLimit(limit int, window time.Duration) gin.HandlerFunc {
    return func(c *gin.Context) {
        if 超限 {
            c.AbortWithStatusJSON(429, gin.H{"code": 429, "message": "请求过于频繁"})
            return          // ← 必须 return
        }
        c.Next()            // 交给下一个中间件/handler
    }
}
```

### 三个必须记住的点

1. **`c.Next()` 之前是「进入」，之后是「返回」**——可以做耗时统计、响应日志
2. **`c.Abort()` 只是打标记**，当前函数还会继续跑。所以 `Abort` 之后必须 `return`
3. **注册顺序 = 执行顺序**。`gin.Default()` 里 Logger 在前、Recovery 在后，所以 panic 能被 Recovery 兜住

### 鉴权中间件（真实代码）

```go
func Auth() gin.HandlerFunc {
    return func(c *gin.Context) {
        header := c.GetHeader("Authorization")
        if header == "" {
            abortUnauthorized(c, "缺少 Authorization")
            return
        }

        parts := strings.SplitN(header, " ", 2)
        if len(parts) != 2 || !strings.EqualFold(parts[0], "Bearer") {
            abortUnauthorized(c, "Authorization 格式错误")
            return
        }

        claims, err := auth.Parse(global.Config.JWT.Secret, parts[1])
        if err != nil {
            abortUnauthorized(c, "token 已过期或无效")
            return
        }

        // 关键：只接受 access token
        if claims.Type != auth.TypeAccess {
            abortUnauthorized(c, "token 类型错误")
            return
        }

        c.Set(CtxUserID, claims.UserID)
        c.Set(CtxUsername, claims.Username)
        c.Next()
    }
}
```

**逐行解释**：

- `strings.SplitN(header, " ", 2)` —— **只切一刀**。如果 token 里含空格（理论上不会有，但防御），用 `Split` 会被切成多段导致解析失败
- `strings.EqualFold(parts[0], "Bearer")` —— 忽略大小写比较（`bearer`/`Bearer` 都接受）
- **`claims.Type != auth.TypeAccess` 这一行是关键安全点**：refresh token 的签名也合法，但它是长期凭证，如果能拿来调业务接口，等于把 30 天的权限暴露出去
- `c.Set(CtxUserID, ...)` 把身份写进上下文，后面的 handler 用 `c.GetUint64(middleware.CtxUserID)` 取
- **为什么用常量 `CtxUserID`**：中间件写、handler 读，两边必须用同一个字符串。手写字符串写错一个字母不报错，只会永远拿到 0——极难排查

## 六、第 4 站：handler 逐行（真实代码）

```go
// Register 用户注册
// POST /api/v1/register
func Register(c *gin.Context) {
    var req registerReq
    if err := c.ShouldBindJSON(&req); err != nil {
        resp.Fail(c, http.StatusBadRequest, "参数错误: "+err.Error())
        return
    }

    u, err := userservice.UserRegister(req.Username, req.Password, req.Nickname)
    if err != nil {
        resp.Fail(c, http.StatusBadRequest, err.Error())
        return
    }
    resp.OK(c, gin.H{"user_id": u.ID, "username": u.Username, "nickname": u.Nickname})
}
```

**逐行解释**：

- `var req registerReq` —— 声明请求体结构体
- `c.ShouldBindJSON(&req)` —— 两件事：**解析 JSON** + **按 `binding` tag 校验**
- 校验失败直接 `resp.Fail` + `return`。**`return` 不能省**，否则会继续往下执行 service
- `userservice.UserRegister(...)` —— 所有业务逻辑在这一行
- `resp.OK(c, gin.H{...})` —— 只挑三个字段返回，**不返回整个 model**（model 里有 `PasswordHash`）

### handler 的职责边界

| 该做 | 不该做 |
|---|---|
| 解析请求、参数校验 | 写业务规则（查重、权限判断） |
| 调 service | 直接操作数据库 |
| 写响应 | 开事务 |

**判断标准**：如果 handler 里出现了 `global.DB` 或 `if count > 0`，说明业务逻辑漏到这一层了。

## 七、第 5 站：请求体结构体与校验

```go
type registerReq struct {
    Username string `json:"username" binding:"required,min=3,max=32"`
    Password string `json:"password" binding:"required,min=6,max=64"`
    Nickname string `json:"nickname" binding:"required,max=32"`
}
```

**两个 tag**：

- `json:"username"` —— JSON 字段名。注意：Go 字段 `Username` 默认会匹配 `Username`（大小写不敏感），但显式写 tag 更明确
- `binding:"required,min=3,max=32"` —— gin 内置校验器：
  - `required` 不能为空
  - `min/max` 长度范围（对字符串是长度，对数字是值）

**校验失败时** `ShouldBindJSON` 返回类似：

```
Key: 'registerReq.Password' Error:Field validation for 'Password' failed on the 'min' tag
```

所以 handler 里拼上 `"参数错误: "` 前缀，用户就能看到原因。

### 为什么校验放 handler，不放 service？

| 层 | 校验什么 | 例子 |
|---|---|---|
| handler | **格式**（协议契约） | 必填、长度、邮箱格式 |
| service | **业务规则**（领域知识） | 用户名是否重复、是否好友、是否群主 |

因为 service 可能被 gRPC、定时任务、CLI 调用——它不应该依赖 HTTP 的校验规则。

## 八、第 6 站：service 逐行（真实代码）

```go
func UserRegister(username string, password, nickname string) (*usermodel.User, error) {
    // ① 用户名查重
    var count int64
    if err := global.DB.Model(&usermodel.User{}).
        Where("username = ?", username).
        Count(&count).Error; err != nil {
        return nil, fmt.Errorf("用户查询失败：%w", err)
    }
    if count > 0 {
        return nil, fmt.Errorf("用户名已存在")
    }

    // ② 密码加密
    hash, err := auth.Hash(password)
    if err != nil {
        return nil, fmt.Errorf("密码加密失败：%w", err)
    }

    // ③ 事务：创建用户 + 默认设置
    user := &usermodel.User{
        Username:     username,
        PasswordHash: hash,
        Nickname:     nickname,
    }

    err = global.DB.Transaction(func(tx *gorm.DB) error {
        if err := tx.Create(user).Error; err != nil {
            return err
        }
        settings := &usermodel.UserSettings{UserID: user.ID}
        if err := tx.Create(settings).Error; err != nil {
            return err
        }
        return nil
    })
    if err != nil {
        return nil, fmt.Errorf("创建用户失败：%w", err)
    }
    return user, nil
}
```

### 逐段拆解

**① 查重**

```go
global.DB.Model(&usermodel.User{}).Where("username = ?", username).Count(&count)
```

- `Model(&User{})` 指定操作哪张表
- `Where("username = ?", username)` —— **`?` 是占位符，防 SQL 注入**。千万不要写 `"username = '" + username + "'"`
- `Count(&count)` 执行 `SELECT count(*) FROM users WHERE username = ?`
- `.Error` —— GORM 的链式调用返回 `*gorm.DB`，错误在 `.Error` 字段

**注意**：这次查重**不能防并发**。两个请求同时通过查重、同时 INSERT，第二个会撞唯一索引报错。所以真正兜底的是 `users.username` 上的 `uniqueIndex`（后面讲）。

**② 密码加密**

```go
hash, err := auth.Hash(password)
```

底层是 bcrypt。**关键特性**：同一个密码每次加密结果不同（内部有随机 salt）。

| 加密方式 | 能否反推 | 同密码结果 | 适用 |
|---|---|---|---|
| MD5/SHA | 彩虹表可破 | 相同 | ❌ 不要用于密码 |
| bcrypt | 计算上不可能 | **不同**（随机 salt） | ✅ 密码首选 |

**③ 事务**

```go
err = global.DB.Transaction(func(tx *gorm.DB) error {
    if err := tx.Create(user).Error; err != nil { return err }
    settings := &usermodel.UserSettings{UserID: user.ID}
    if err := tx.Create(settings).Error; err != nil { return err }
    return nil
})
```

**三个关键点**：

1. **`Transaction` 接收一个函数**，函数返回 `error` 就自动回滚，返回 `nil` 就提交
2. **回调里必须用 `tx`，不能用 `global.DB`**——用 `global.DB` 是独立事务，回滚管不到它（这是最容易犯的错）
3. **`tx.Create(user)` 之后 `user.ID` 会被 GORM 回填**（取自增主键），所以下一行能用 `user.ID`

**为什么用户和设置要放同一个事务**：它们 1:1 必须成对出现。只创建用户不创建设置，用户进设置页会报错——这是「脏数据」。

## 九、第 7 站：GORM 实际执行了什么 SQL

```go
tx.Create(user)
```

GORM 会生成：

```sql
INSERT INTO `users` (`created_at`,`updated_at`,`deleted_at`,`username`,`password_hash`,`nickname`,...)
VALUES ('2026-11-14 12:00:00','2026-11-14 12:00:00',NULL,'alice','$2a$10$...','爱丽丝',...)
```

然后是第二条：

```sql
INSERT INTO `user_settings` (`created_at`,`updated_at`,`user_id`,...) VALUES (...,1,...)
```

两条 INSERT 在**同一个事务**里，要么都成功，要么都回滚。

### 想看真实 SQL 怎么办

```go
global.DB.Debug().Create(&user)
```

或者配置 GORM 的 logger。调试时打开 `Debug()`，能看到完整 SQL 和参数。

## 十、第 8 站：model 长什么样

`internal/model/user_model/user_model.go`：

```go
type User struct {
    model.Model          // 嵌入：ID / CreatedAt / UpdatedAt / DeletedAt

    Username     string `gorm:"type:varchar(32);uniqueIndex;not null" json:"username"`
    PasswordHash string `gorm:"type:varchar(255);not null" json:"-"`
    Nickname     string `gorm:"type:varchar(32);not null;default:''" json:"nickname"`
    Avatar       string `gorm:"type:varchar(255);not null;default:''" json:"avatar"`
    // ...
}

func (User) TableName() string { return "users" }
```

**逐行解释**：

- **嵌入 `model.Model`** —— 内部是 `gorm.Model`，提供 `ID/CreatedAt/UpdatedAt/DeletedAt` 四个字段
- **`DeletedAt` 的意义**：GORM 的软删除。查询会自动加 `WHERE deleted_at IS NULL`，删除只是把时间写进去
- **`uniqueIndex`** —— 建唯一索引。这是并发注册的**最后防线**
- **`json:"-"`** —— 序列化时忽略这个字段。`PasswordHash` 永远不会出现在响应里
- **`TableName()`** —— 显式指定表名。不写的话 GORM 会做单复数推断（`User` → `users`），容易猜错

## 十一、第 9 站：响应怎么写回去

`internal/router/resp/resp.go`：

```go
func OK(c *gin.Context, data any) {
    c.JSON(http.StatusOK, gin.H{"code": 0, "message": "ok", "data": data})
}

func Fail(c *gin.Context, status int, msg string) {
    c.JSON(status, gin.H{"code": status, "message": msg})
}
```

**统一格式的价值**：前端只写一套解析逻辑：

```js
const res = await fetch(...);
const json = await res.json();
if (json.code !== 0) throw new Error(json.message);
return json.data;
```

如果每个接口返回格式不同，前端要写 N 套判断。

## 十二、三条错误路径分别怎么走

### 路径 A：参数不合法

```
curl 传 {"username":"ab"}
→ ShouldBindJSON 校验失败（min=3）
→ handler 直接 resp.Fail(400, "参数错误: ...")
→ 不进 service，不打数据库
```

### 路径 B：用户名重复

```
→ 校验通过 → service 查重 count>0
→ return errors.New("用户名已存在")
→ handler resp.Fail(400, "用户名已存在")
```

### 路径 C：数据库挂了

```
→ service 查重时 .Error 非空
→ return fmt.Errorf("用户查询失败：%w", err)
→ handler resp.Fail(400, err.Error())
```

**注意路径 C 的问题**：直接把 `err.Error()` 返回给用户，可能泄露 SQL 细节。
生产环境应该区分：业务错误返回原文，系统错误统一返回「服务器内部错误」并记日志。

## 十三、为什么要这么分层（改需求时最能体现）

假设需求变成「注册后自动给用户发一条欢迎消息」：

| 分层方式 | 要改哪里 |
|---|---|
| 全部写在 handler | handler 里不断堆代码，很快失控 |
| 分层 | 只改 `UserRegister`（service 里加一步），handler 不动 |

再假设需求变成「gRPC 也要支持注册」：

| 分层方式 | 结果 |
|---|---|
| service 里 import 了 gin | 无法复用，必须重写一份 |
| service 只依赖普通参数 | gRPC handler 直接调同一个 `UserRegister` |

**这就是为什么本项目 service 层里你看不到 `*gin.Context`。**

## 十五、面试怎么答（背这 3 句）

**问：一次请求在你们项目里经过哪几层？**

> handler 只做协议转换（解析请求、参数校验、写响应）；service 放业务逻辑和事务；model 只描述表结构。
> service 层不依赖 gin，所以 M6 拆 gRPC 时能直接复用。

**问：为什么参数校验要分两层？**

> handler 校验**格式**（必填、长度、类型），service 校验**业务规则**（用户名是否重复、是否好友、是否群主）。
> 因为 service 可能被 gRPC、定时任务、CLI 调用，它不应该依赖 HTTP 的校验规则。

**问：注册为什么要开事务？**

> 要同时写 `users` 和 `user_settings`，它们 1:1 必须成对；不开事务可能只成功一半，产生「有用户没设置」的脏数据。
> 事务回调里必须用 `tx`，不能用 `global.DB`——那是独立事务，回滚管不到。
