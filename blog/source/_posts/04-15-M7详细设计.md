## 一、里程碑目标

用消息队列把「发消息」和「推送消息」解耦：

- RabbitMQ 连接 + 持久化队列
- **本地消息表（Transactional Outbox）**：业务写入和事件写入同一事务
- 后台 worker：轮询 outbox → 发 MQ → 标记已发送
- 消费者：消费事件 → WebSocket 推送
- MQ 不可用时**降级为同步推送**

验收（已实测）：

| 场景 | 结果 |
|---|---|
| 发消息后立即查 outbox | 有 status=0 记录 |
| 消费者异步推送 | 对方 WS 收到消息 |
| 3 秒后查 outbox | status=1（已发送） |
| 服务日志 | 无 outbox 错误 |
| RabbitMQ 队列 | 有 active consumer |

## 二、为什么需要消息队列

| 场景 | 不用 MQ | 用 MQ |
|---|---|---|
| 发消息后推送 | 请求里同步查成员 + 逐个推送，慢 | 只写 outbox，worker 异步推送 |
| 群消息扇出 200 人 | 请求耗时随人数增长 | 请求快速返回，后台慢慢推 |
| 流量高峰 | 直接打满服务 | 队列削峰 |
| 服务解耦 | A 直接调 B，B 挂了 A 也挂 | A 只发消息，B 自己消费 |
| 跨服务一致性 | 无法用本地事务 | 最终一致性 |

**代价**：系统复杂度上升（消息丢失/重复/顺序/积压都要处理）。

## 三、核心：Transactional Outbox（本地消息表）

### 3.1 问题：落库和发 MQ 无法原子

```
方案 A：先落库，再发 MQ
  落库成功，发 MQ 失败 → 消息永远不会被推送（丢失）

方案 B：先发 MQ，再落库
  发 MQ 成功，落库失败 → 推了一条不存在的消息（脏数据）
```

**两个操作不在同一个事务里，就无法保证一致。**

### 3.2 解法：把「发 MQ」变成「写数据库」

```
业务事务 {
    写 messages 表
    更新 conversations 表
    写 outbox_messages 表（status=0）   ← 同一个本地事务，原子
}
        ↓
后台 worker：轮询 outbox(status=0) → 发 RabbitMQ → 标记 status=1
        ↓
消费者：消费 MQ → 实际处理（推送 WS）
```

**关键洞察**：写数据库是事务性的，发 MQ 不是。所以把"要发 MQ"这件事先记在数据库里，再由后台可靠地补发。

### 3.3 至少一次投递

- worker 发 MQ 成功但标记 status=1 失败 → 下次会重复发（**至少一次**）
- 所以消费方必须**幂等**

本项目消费动作是「推送给在线用户」——重复推最多让客户端收到两次相同消息，客户端可用消息 id 去重，问题不大。
如果消费动作是「加积分」「扣库存」，就必须做严格幂等（去重表 / 唯一索引）。

## 四、RabbitMQ 基础（面试必备）

### 4.1 核心概念

| 概念 | 说明 |
|---|---|
| **Producer** | 生产者（本项目 outbox worker） |
| **Consumer** | 消费者 |
| **Queue** | 队列（本项目 `gochat.events`） |
| **Exchange** | 交换机（本项目用默认交换机，直接路由到队列） |
| **Binding** | 交换机到队列的绑定规则 |
| **Ack** | 消费确认（手动 ack 保证不丢） |

### 4.2 本项目用到的可靠性设置

```go
// 1. 队列持久化（RabbitMQ 重启后队列还在）
ch.QueueDeclare("gochat.events", true /*durable*/, false, false, false, nil)

// 2. 消息持久化（消息写入磁盘）
amqp.Publishing{
    DeliveryMode: amqp.Persistent,
    ...
}

// 3. 手动 ack（处理成功才确认）
ch.Consume(queue, "", false /*autoAck*/, ...)
d.Ack(false)
```

三者结合 = 「至少一次」投递。

### 4.3 交换机类型（了解）

| 类型 | 路由规则 |
|---|---|
| direct | 按 routing key 精确匹配 |
| fanout | 广播到所有绑定队列 |
| topic | 按模式匹配（`order.*.created`） |
| headers | 按 header 匹配 |

本项目用默认交换机（空字符串）+ 队列名当 routing key，最简单。

## 五、本项目的完整链路

```
HTTP/WS 发消息
   ↓
chatservice.SendMessage
   ├─ 事务：写 messages + 更新 conversations + 写 outbox(status=0)
   └─ 返回
   ↓
OutboxWorker（每 2 秒）
   ├─ SELECT * FROM outbox_messages WHERE status=0
   ├─ Publish 到 RabbitMQ
   └─ UPDATE status=1（失败则 retry_count+1，5 秒后重试）
   ↓
Consumer
   ├─ 消费消息（手动 ack）
   ├─ 解析 MessageCreatedPayload
   └─ ws.PushToConversation 推送给会话成员
   ↓
在线用户的 WebSocket 收到消息
```

### 降级设计

```go
// MQ 可用：走 outbox + 异步推送
// MQ 不可用：handler 直接同步推送（保证功能不挂）
if global.MQ == nil || !global.MQ.Enabled {
    ws.PushMessage(convID, item)
}
```

**面试点**：外部依赖要设计降级路径，不能因为 MQ 挂了整个聊天就不可用。

## 六、消息队列还要考虑的问题（面试延伸）

| 问题 | 方案 |
|---|---|
| 消息丢失 | 持久化队列 + 持久化消息 + 手动 ack + 生产者确认（publisher confirm） |
| 消息重复 | 消费幂等（去重表/唯一索引/消息 id） |
| 消息顺序 | 单队列单消费者；或按业务 key 分区 |
| 消息积压 | 加消费者、扩容、死信队列 |
| 毒消息 | 重试次数上限 + 死信队列（DLQ） |
| 事务消息 | RocketMQ 事务消息 / 本地消息表 / Saga |

> 本项目用了「本地消息表」，这是最简单可靠的最终一致性方案。

## 八、注意点清单

1. **落库和发 MQ 不能原子** → 用 outbox
2. **outbox 必须在业务事务内写**
3. **至少一次投递 → 消费必须幂等**
4. **队列和消息都要持久化**
5. **手动 ack**，处理成功才确认；格式错误的消息 nack 且不重入队（防毒消息）
6. **`amqp.Table` 的 value 不支持 `uint`**（本项目踩过：`outbox_id` 要转 `int64`）
7. **MQ 要可降级**，不能因为它挂了业务全挂
8. **消费失败要有重试上限 + 死信队列**
9. **事件契约用中立的 struct**，避免上下游循环依赖
10. **监控队列积压**
