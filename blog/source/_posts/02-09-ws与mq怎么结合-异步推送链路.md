> 很多人学完 WS、学完 MQ，但**不知道两者怎么接起来**。
> 这篇讲清楚本项目的一条真实链路：

```
发消息请求 → 事务(写消息 + 写 outbox) → worker 轮询 → RabbitMQ → consumer → WebSocket 推送
```

> 所有代码来自 `internal/mq/mq.go`、`internal/outbox/outbox.go`、`internal/ws/`，可直接对照。

![Outbox 模式异步投递链路](/blog/images/outbox.svg)

## 一、先看结论：项目里有两条推送路径

推送到底"同步做"还是"异步做"，由 **MQ 是否可用** 决定：

| 路径 | 触发条件 | 谁来做 | 延迟 |
|---|---|---|---|
| **同步推送**（降级） | MQ 未启用 | 发消息的 handler 直接调用 `ws.PushMessage` | 立即 |
| **异步推送**（正常） | MQ 已启用 | outbox worker → RabbitMQ → consumer → `ws.PushToConversation` | 0~2 秒 |

### 关键代码 1：写入 outbox（MQ 启用时）

`internal/service/chat_service/message_service.go` 的事务里：

```go
err = global.DB.Transaction(func(tx *gorm.DB) error {
    if err := tx.Create(msg).Error; err != nil { return err }

    // 更新会话冗余字段
    tx.Model(&Conversation{}).Where("id = ?", convID).Updates(...)

    // 【关键】MQ 启用时，在同一个事务里写 outbox 记录
    if global.MQ != nil && global.MQ.Enabled {
        return outbox.Enqueue(tx, mqmodel.EventMessageCreated, mqmodel.MessageCreatedPayload{
            ID:             uint64(msg.ID),
            ConversationID: uint64(msg.ConversationID),
            SenderID:       uint64(msg.SenderID),
            ClientMsgID:    msg.ClientMsgID,
            Type:           msg.Type,
            Content:        msg.Content,
            CreatedAt:      msg.CreatedAt.Unix(),   // 注意是 Unix 秒
        })
    }
    return nil
})
```

> **为什么写在事务里**：保证「消息落库」和「待投递事件」要么都成功、要么都回滚。
> 否则可能出现：消息存了但事件没记（永远不推送），或事件记了但消息没存（推一条不存在的消息）。

### 关键代码 2：决定是否同步推送（MQ 未启用时）

`internal/ws/client.go` 的 `handleText`：

```go
// 1. 给发送者回 ack
c.SendJSON(map[string]any{
    "type": "ack", "client_msg_id": msg.ClientMsgID,
    "message_id": msg.ID, "conversation_id": msg.ConversationID,
})

// 2. 推给会话所有成员
// M7：启用 MQ 时由异步消费者推送；未启用则同步推送
if global.MQ == nil || !global.MQ.Enabled {
    PushMessage(uint64(msg.ConversationID), chatservice.ToItem(msg))
}
```

**注意这个 if**：MQ 启用时这里**什么都不做**（推送交给消费者），避免重复推两遍。

## 二、为什么要解耦：不在 handler 里直接推

如果把推送写在 handler 里，会有 4 个问题：

| 问题 | 具体表现 |
|---|---|
| **响应变慢** | 群消息 200 人，要在请求里查成员 + 逐个推送 |
| **推送失败就丢了** | 没有重试机制，用户掉线期间就永久错过 |
| **多实例推不到** | 用户连在实例 B，实例 A 的 Hub 里没有他的连接 |
| **没有削峰** | 突发流量直接打到推送逻辑 |

解耦后：

- 请求只做「落库 + 记录事件」，**毫秒级返回**
- 推送失败由 worker 重试（`retry_count` + `next_retry`）
- 每个实例的 consumer 都消费同一条事件 → **各推自己本机的在线用户**（天然广播）
- 消息堆积在队列里，consumer 按自己节奏消费（削峰）

## 三、完整链路（一次发消息）

```
① 客户端 A 发消息（WS 或 HTTP）
        │
        ▼
② chatservice.SendMessage
   ┌─────────────────────────────────────┐
   │ 事务:                                │
   │   INSERT messages                    │
   │   UPDATE conversations               │
   │   INSERT outbox_messages (status=0)  │  ← 原子
   └─────────────────────────────────────┘
        │
        ▼
③ 立刻回 ack（客户端看到「已发送」，不等推送）
        │
        ▼
④ OutboxWorker（每 2 秒轮询一次）
   SELECT * FROM outbox_messages WHERE status=0 AND next_retry <= now LIMIT 100
        │
        ├── 发布成功 → UPDATE status=1
        └── 发布失败 → retry_count+1, next_retry=now+5s（下轮再试）
        │
        ▼
⑤ RabbitMQ 队列 gochat.events（durable + Persistent 消息）
        │
        ▼
⑥ Consumer（每个实例一个）
   解析 payload → ws.PushToConversation(convID, {type:"message", data:payload})
        │
        ▼
⑦ Hub 查会话成员 → 逐个 SendToUser（多端都推）→ 在线客户端收到
        │
        ▼
⑧ 手动 ack（处理成功才确认，失败可以重新投递）
```

## 四、代码走读：4 个文件各管一段

### 4.1 `internal/outbox/outbox.go` —— 只负责"记一笔"

```go
func Enqueue(tx *gorm.DB, eventType string, payload any) error {
    b, _ := json.Marshal(payload)
    return tx.Create(&mqmodel.Outbox{
        EventType: eventType,
        Payload:   string(b),
        Status:    0,               // 0=待发送
        NextRetry: time.Now(),
    }).Error
}
```

**为什么单独一个包**：打破循环依赖。

```
chatservice → outbox → mqmodel
           ↘ mqmodel
```

如果 `chatservice` 直接 import `internal/mq`，而 `mq` 又要 import `ws`（推送）→ `ws` 又 import `chatservice` → **循环依赖**。
把"写记录"和"发 MQ"拆开，依赖就单向了。

### 4.2 `internal/mq/mq.go` 的 `publishPending` —— 可靠投递

```go
// 每 2 秒跑一次，一次最多 100 条
rows := SELECT * FROM outbox_messages
        WHERE status = 0 AND next_retry <= now()
        ORDER BY id ASC LIMIT 100

for _, r := range rows {
    err := channel.PublishWithContext(ctx, "", QueueName, false, false, amqp.Publishing{
        DeliveryMode: amqp.Persistent,          // 消息持久化
        Body:         []byte(r.Payload),
        Headers: amqp.Table{
            "event_type": r.EventType,
            "outbox_id":  int64(r.ID),          // ← 注意类型
        },
    })
    if err != nil {
        // 失败：重试次数 +1，5 秒后再试
        UPDATE outbox_messages SET retry_count = retry_count + 1,
               next_retry = now() + 5s WHERE id = r.ID
        continue
    }
    UPDATE outbox_messages SET status = 1 WHERE id = r.ID
}
```

> **坑**：`amqp.Table` 的 value **不支持 `uint`**，必须转 `int64`，
> 否则报 `table field "outbox_id" value uint not supported`。

### 4.3 `mq.handleDelivery` —— 消费后推 WS

```go
eventType := d.Headers["event_type"].(string)

switch eventType {
case mqmodel.EventMessageCreated:
    var p mqmodel.MessageCreatedPayload
    if err := json.Unmarshal(d.Body, &p); err != nil {
        d.Nack(false, false)   // 毒消息：不重入队，避免无限循环
        return
    }
    ws.PushToConversation(p.ConversationID, map[string]any{
        "type": "message",
        "data": p,
    })
    d.Ack(false)              // 处理成功才 ack
default:
    d.Ack(false)              // 未知事件直接确认，避免堆积
}
```

**为什么手动 ack（`autoAck=false`）**：处理成功才确认；处理中途崩溃 → 消息会重新投递（至少一次）。

### 4.4 `ws.PushToConversation` —— 最后一段

```go
func PushToConversation(convID uint64, payload any) {
    frame, _ := json.Marshal(payload)
    memberIDs, _ := chatservice.ListMemberIDs(context.Background(), convID)
    fanout(memberIDs, frame)     // 小会话顺序推；大会话并发 + 信号量限 16
}
```

## 五、"至少一次"意味着可能重复，怎么办

Outbox + 手动 ack 的组合是 **at-least-once（至少一次）**，重复发生在：

| 场景 | 结果 |
|---|---|
| worker 发布成功，但标记 `status=1` 失败 | 下次会重发 |
| consumer 处理成功，但 ack 前进程崩溃 | 消息重新投递 |

### 本项目的处理

1. **消息本身不会重复入库**：`UNIQUE(sender_id, client_msg_id)` 保证幂等
2. **重复推送影响小**：推送只是"通知"，且消费动作是幂等的（推给在线用户）
3. **前端去重**：按 `id` 和 `client_msg_id` 过滤（`appendMessage` 里做了）

> 如果换成"加积分"这类副作用，就必须加**消费去重表**（记录已处理的事件 id）。
> **面试点**：至少一次 + 幂等消费 = 事实上的"恰好一次"效果。

## 六、为什么这套设计天然支持多实例

```
实例 1                         实例 2
┌──────────────┐              ┌──────────────┐
│ WS Hub       │              │ WS Hub       │
│ 用户A 在线    │              │ 用户B 在线    │
│ Consumer ────┼──┐        ┌──┼──── Consumer │
└──────────────┘  │        │  └──────────────┘
                  ▼        ▼
              RabbitMQ 队列（同一条事件）
```

- 每个实例都有 consumer，**同一条事件会被所有实例消费**
- 每个实例只推**自己 Hub 里在线的用户**
- 合起来 = 全量用户都收到，且不会漏

> 这就是"用 MQ 做 WS 多实例广播"的经典方案（比 Redis Pub/Sub 多了一个持久化和重试能力）。

## 七、本地怎么验证（3 个实验）

### 实验 1：看 outbox 表的状态流转

```bash
# 发一条消息，然后立刻查
docker exec -it gochat-mysql mysql -uroot -proot gochat -e \
  "SELECT id, event_type, status, retry_count, created_at FROM outbox_messages ORDER BY id DESC LIMIT 5;"
```

刚插入时 `status=0`，2 秒后再查变成 `status=1`。

### 实验 2：看 RabbitMQ 队列

```bash
docker exec -it gochat-rabbitmq rabbitmqctl list_queues name messages
# 应看到 gochat.events
```

### 实验 3：停掉 MQ 观察降级

```bash
docker stop gochat-rabbitmq
# 重启服务 → 日志出现：RabbitMQ 连接失败，消息将使用同步推送
# 此时发消息仍然能收到（走同步推送路径），验证降级有效
docker start gochat-rabbitmq
```

> 这验证了"外部依赖挂了，功能不中断"——面试可以主动讲这个降级设计。

## 八、常见问题

| 现象 | 原因 | 解决 |
|---|---|---|
| 消息延迟 1~3 秒 | outbox worker 每 2 秒轮询 | 正常；要求更低延迟可缩短间隔或改直接发布 |
| outbox 表一直增长 | worker 没跑 / MQ 不可用 | 查日志 `[outbox]`；确认 worker 已启动 |
| 收不到推送 | consumer 没起来 / 队列没绑定 | 看 `rabbitmqctl list_queues`；看服务日志 |
| 推了两遍 | MQ 启用但 handler 里也同步推了 | 检查 `handleText` 里的 `if !Enabled()` |
| `table field "outbox_id" value uint not supported` | `amqp.Table` 不接受 uint | 转 `int64` |
| 毒消息无限重试 | `Nack(requeue=true)` | 解析失败要 `Nack(false,false)` |

## 九、面试问答（8 题）

**1. WS 和 MQ 怎么结合的？**

> 发消息时在业务事务里写一条 outbox 记录（事件），后台 worker 轮询把事件投递到 RabbitMQ，
> consumer 消费后调用 `ws.PushToConversation` 推给会话在线成员。WS 是"最后一公里"，MQ 负责解耦和可靠性。

**2. 为什么不直接在发消息的 handler 里推？**

> 请求会变慢（群消息要查成员+逐个推）、推送失败没有重试、多实例推不到、无法削峰。

**3. 为什么要有 outbox 表，直接发 MQ 不行吗？**

> 落库和发 MQ 无法放进同一个事务。先落库后发 MQ 可能丢消息，先发 MQ 后落库可能推不存在的消息。
> outbox 把"发 MQ"变成"写数据库"，和业务数据在同一个事务里，再由 worker 可靠补发。

**4. 怎么保证消息不丢？**

> 三层：① 事务内写 outbox（业务与事件原子）；② 队列持久化 + 消息 Persistent + 手动 ack；
> ③ worker 发布失败会 `retry_count+1` 并延迟重试。

**5. 怎么保证不重复？**

> 严格说是"至少一次"，可能重复。三层防护：消息落库有 `UNIQUE(sender_id, client_msg_id)`；
> 消费动作（推送）本身幂等；前端按 `id`/`client_msg_id` 去重。

**6. 多实例怎么保证每个用户都收到？**

> 每个实例都有 consumer，同一条事件被所有实例消费，各自推自己 Hub 里的在线用户。

**7. MQ 挂了会怎样？**

> 服务启动时 MQ 是可选依赖，连不上只打日志；业务侧 `if !Enabled()` 走同步推送，功能不中断。
> 已落库的消息不会丢（outbox 里还在，恢复后会补发）。

**8. 消费失败怎么办？**

> 解析失败（毒消息）→ `Nack(false,false)` 不重入队并记录日志；处理异常可以 `requeue` 或进死信队列。
