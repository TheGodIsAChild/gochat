> 表设计不是「把字段列出来」，而是**用约束表达业务规则**。
> 本文逐张表讲：为什么有这张表、每个字段干什么、索引为什么这么建。

![gochat 数据库 ER 图](/blog/images/db-er.svg)

## 一、5 条设计原则

| 原则 | 说明 | 例子 |
|---|---|---|
| **按领域分表** | 一张表只服务一个业务概念 | `friend_requests` 与 `friendships` 分开 |
| **软删除** | 保留历史，IM 需要审计/回溯 | `friendships.status=2` |
| **双向两行** | 好友关系（A,B）(B,A) 两行 | 查询只走 `user_id` 索引 |
| **唯一索引兜底** | 并发安全最后防线 | `uk_from_to`、`uk_sender_client` |
| **冗余换读性能** | 热点字段冗余 | `conversations.last_message_at` |

## 二、用户域

### users

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | 自增 |
| username | VARCHAR(32) UNIQUE | 登录名 |
| phone / email | VARCHAR(20/128) NULL UNIQUE | **可空**（多个 NULL 不冲突） |
| password_hash | VARCHAR(255) | bcrypt，**绝不明文** |
| nickname/avatar/gender/signature/region | | 资料 |
| status | TINYINT | 0 正常 / 1 禁用 |

**设计点**：

- `phone/email` 用 `*string`（Go 指针）→ 区分「没填」和「填空」
- `password_hash` 的 JSON tag 是 `json:"-"` → 永远不会返回给前端
- `deleted_at`（GORM 软删除）→ 注销用户后仍可追溯

### user_settings（1:1）

| 字段 | 说明 |
|---|---|
| user_id UNIQUE | 一人一条 |
| allow_search_by_phone | 隐私开关 |
| allow_friend_request | 是否允许被加好友 |
| need_verify | 加好友要验证 |

**为什么单独一张表？** 设置字段多、变动频繁，且只有设置页需要；塞进 users 会让主表臃肿。

## 三、好友域

### friend_requests

```sql
UNIQUE (from_user_id, to_user_id)          -- 同一对用户只有一条申请记录
INDEX  (to_user_id, status)                -- 「我收到的待处理申请」
```

**关键设计**：唯一索引导致「删除好友后重新申请」会冲突 → 代码里**复用旧行**（重置 status=0）。

### friendships（双向两行）

```sql
UNIQUE (user_id, friend_id)   -- 防重复
INDEX  (user_id)              -- 查「我的好友」
```

| 字段 | 说明 |
|---|---|
| remark | 备注（只在**我这一侧**生效） |
| group_id | 好友分组 |
| is_starred | 星标 |
| status | 1 正常 / 2 已删除（软删） |

**为什么要两行**：查好友只 `WHERE user_id=?`，不用 `OR`、不用排序；代价是写两行必须用事务。

### friend_groups / blacklist

- `friend_groups`：`UNIQUE(user_id, name)`，分组名不能重复
- `blacklist`：`UNIQUE(user_id, blocked_user_id)`；**取消拉黑用物理删除**（否则软删行会挡住下次拉黑）

## 四、聊天域（核心）

### conversations

| 字段 | 说明 |
|---|---|
| type | 1 单聊 / 2 群聊（**单群共用一张表**） |
| last_message_id / last_message_at | 冗余最后消息，会话列表直接读 |

**为什么单群共用**：消息表不用区分单聊/群聊，统一按 `conversation_id` 查。

### conversation_members

```sql
UNIQUE (conversation_id, user_id)   -- 一个会话一个成员一条
INDEX  (user_id)                    -- 查「我的所有会话」
```

| 字段 | 说明 |
|---|---|
| last_read_message_id | **未读数关键**：id > 它且 sender≠我 = 未读 |
| role / mute | 群主 / 免打扰 |

### messages

```sql
INDEX  (conversation_id)                  -- 按会话拉历史
UNIQUE (sender_id, client_msg_id)         -- 幂等
INDEX  (sender_id)
```

| 字段 | 说明 |
|---|---|
| client_msg_id | **客户端生成的唯一 ID**，重试不重复 |
| type | 1 文本 2 图片 3 语音 4 文件（tinyint 便于扩展） |
| content | TEXT，文本/URL/元信息 JSON 都能放 |
| status | 1 正常 / 2 撤回 |

**分页查询**（必须走索引）：

```sql
SELECT * FROM messages
WHERE conversation_id = ? AND id < ?   -- 游标
ORDER BY id DESC LIMIT 20;
```

## 五、群聊域

### groups

```sql
UNIQUE (conversation_id)   -- 一个群对应一个会话
INDEX  (owner_id)
```

| 字段 | 说明 |
|---|---|
| member_count | 冗余人数（避免每次 COUNT） |
| max_members | 上限 200 |
| status | 1 正常 / 2 已解散 |

**为什么冗余 member_count**：群列表要显示人数；加人/踢人时用 `gorm.Expr("member_count + ?")` 原子更新。

## 六、通话域

### call_records

| 字段 | 说明 |
|---|---|
| caller_id / callee_id | 主被叫 |
| status | 1 呼叫中 2 已接通 3 拒绝 4 取消 5 结束 6 未接 |
| started_at / ended_at / duration | 时长计算 |

## 七、消息队列域

### outbox_messages

| 字段 | 说明 |
|---|---|
| event_type | 事件类型（message.created） |
| payload | 事件内容 JSON |
| status | 0 待发送 / 1 已发送 |
| retry_count / next_retry | 重试控制 |

## 八、索引清单与验证

```sql
-- 看某张表的索引
SHOW INDEX FROM messages;
SHOW INDEX FROM friend_requests;
```

| 表 | 索引 | 支撑的查询 |
|---|---|---|
| users | uk_username, uk_phone, uk_email | 登录/搜索 |
| friend_requests | uk_from_to, idx_to_status | 防重、收申请列表 |
| friendships | uk_user_friend, idx_user | 好友列表 |
| conversation_members | uk_conv_user, idx_user | 我的会话 |
| messages | idx_conv, uk_sender_client | 拉历史、幂等 |

## 九、常见表设计错误

| 错误 | 后果 |
|---|---|
| 不用唯一索引，只靠代码查重 | 并发下重复数据 |
| 软删除 + 唯一索引不处理 | 删除后无法重建 |
| 用 `status` 语义混用（业务状态 vs 删除） | 查询条件混乱 |
| 大字段（content）放主表热点索引 | 索引膨胀 |
| 不冗余计数，每次 COUNT | 列表变慢 |
| 手机号用 NOT NULL | 多用户不填会冲突 |
