> 本文回答一个问题：**这个项目为什么长成这样**。
> 角色：需求 → 拆模块 → 定分层 → 定通信方式 → 定部署形态。

![gochat 系统架构](/blog/images/architecture.svg)

## 一、需求决定了架构

先看需求，不要先看代码：

| 需求 | 对架构的要求 |
|---|---|
| 用户能登录、长期在线 | 认证 + 会话（JWT/Redis） |
| 加好友、建群 | 关系数据模型（好友/群） |
| 实时收到消息 | **长连接**（WebSocket） |
| 消息不能丢、不重复 | 持久化 + 幂等 + 游标分页 |
| 语音通话 | **P2P 通信（WebRTC）+ 信令** |
| 系统能演进、能扩展 | **分层 + 可拆分的服务边界** |

**关键结论**：IM 的架构难点不在 CRUD，而在 **长连接、实时性、消息一致性**。

## 二、分层：为什么是这四层

```
router/handler  →  service  →  model / global.DB  →  MySQL / Redis
```

| 层 | 只做 | 绝不做 |
|---|---|---|
| handler | 解析请求、参数校验、写响应 | 不写业务规则、不碰事务 |
| service | 业务规则、事务、调 model | 不 import gin（可被 gRPC 复用） |
| model | 描述表结构 | 不写业务逻辑 |
| 基础设施 | 连接、缓存、消息 | 不感知业务 |

### 为什么要这么分？两个真实收益

1. **M6 拆微服务时**：service 完全不用改，只是把 handler 从 Gin 换成 gRPC。因为我们从第一天就把 `*gin.Context` 挡在 handler 层。
2. **可测试**：service 是纯 Go 函数，单测不用起 HTTP 服务。

### 反面教材

```go
// ❌ service 里直接用 gin.Context → 和 HTTP 框架绑死
func Register(c *gin.Context) { ... c.JSON(...) }
```

## 三、单体 vs 微服务：为什么要走两遍

本项目 **M0–M5 是单体，M6 才拆**。这不是偷懒，是刻意设计。

### 单体的三个真实痛点（只有自己写过才懂）

| 痛点 | 场景 |
|---|---|
| 扩缩容粒度粗 | 聊天流量大，但用户服务也得跟着扩 |
| 故障不隔离 | 一个模块 OOM 全挂 |
| 部署耦合 | 改一行全量发布 |

### 拆分方式：按领域，不按技术层

```
❌ controller 服务 / service 服务 / dao 服务（按技术分层）
✅ 用户服务（user :9001）/ 聊天服务（chat :9002）/ 网关
```

**判断标准**：一个服务应该能独立回答「它负责什么业务」，而不是「它负责哪一层」。

## 四、通信方式怎么选

| 场景 | 方式 | 原因 |
|---|---|---|
| 浏览器 → 后端 | HTTP + WebSocket | 浏览器原生支持 |
| 客户端 → 内部服务 | **只经过 gateway** | 统一鉴权/限流，不暴露内部 |
| 内部服务之间 | **gRPC** | 强契约、性能高、支持流 |
| 消息异步推送 | **MQ（RabbitMQ）** | 解耦、削峰、最终一致性 |
| 实时上行 | WebSocket 帧 | 低延迟双向 |

### 同步 vs 异步的边界

```
同步（用户要立即拿到结果）：
  登录 → 签发 token → 返回

异步（用户不需要立即知道结果）：
  发消息 → 落库 → 写 outbox → （后台）发 MQ → 消费者推送
```

**判断标准**：用户/调用方是否必须等待结果才能继续。必须等 → 同步；可以稍后 → 异步。

## 五、数据流：一条消息的完整旅程

```
① A 发消息
   HTTP/WS → gateway → chat 服务 → 事务{ messages + conversations + outbox }
② outbox worker 每 2s 轮询 → 发 RabbitMQ
③ consumer 消费 → 查会话成员 → ws.PushToConversation
④ 在线成员 WebSocket 收到；离线成员消息已在 DB，上线拉历史
```

**为什么消息要绕一圈 MQ 而不是直接推？**

- 请求快速返回（不用在请求里查成员+逐个推）
- 推送失败有重试（outbox）
- 消费方可以独立扩容

## 六、部署形态

单进程演示（本项目）：

```
一个 gochat 进程内同时启动：
  HTTP :8080（gateway + 前端 + 博客）
  gRPC :9001（user 服务）
  gRPC :9002（chat 服务）
  MQ worker + consumer
```

真实微服务部署：

```
gateway(容器) ──gRPC──► user(容器) / chat(容器)
     │                      │
     └──── RabbitMQ ────────┘
              │
      MySQL / Redis（独立或集群）
```

> 本项目把两者合在一个进程，是为了**演示方便**；代码边界已经按微服务划好了。

## 七、微服务化带来的新问题（面试高频）

| 问题 | 本项目现状 | 生产做法 |
|---|---|---|
| 服务发现 | 配置写死地址 | Consul/Etcd/K8s Service |
| 超时 | context 超时 | 每个调用设 deadline |
| 重试 | 未做 | 幂等 + 有限重试 |
| 熔断 | 未做 | Sentinel/Hystrix |
| 链路追踪 | 未做 | OpenTelemetry + trace_id |
| 数据一致性 | Outbox + 最终一致 | Saga/TCC/本地消息表 |

## 八、架构评审会怎么问

1. 为什么先单体后微服务？
2. 服务按什么拆？为什么不按技术层？
3. 为什么内部用 gRPC、对外用 HTTP？
4. 哪些操作用同步、哪些用异步？判断标准是什么？
5. 微服务后怎么做鉴权？→ gateway 统一校验，内部信任或 mTLS
6. 消息为什么走 MQ？不走行不行？→ 可以，但会慢且不削峰
