> 接口设计是前后端协作的契约。设计得好，联调半小时；设计得烂，扯皮一星期。
> 本文给一套能直接抄的规范，并对照本项目的真实接口。

## 一、URL 设计：名词 + 层级

```
✅ /api/v1/conversations              列出会话
✅ /api/v1/conversations/1/messages   会话 1 的消息
✅ /api/v1/groups/1/members           群 1 的成员
❌ /api/v1/getConversationList        动词出现在 URL
❌ /api/v1/conversation_list          下划线混用
```

**规则**：

1. 资源用**名词复数**
2. 层级表达从属关系（会话 → 消息）
3. 全小写 + 中划线/直接用单词，不混风格
4. 版本号放最前 `/api/v1`

## 二、HTTP 方法语义

| 方法 | 语义 | 幂等 | 本项目例子 |
|---|---|---|---|
| GET | 查询 | ✅ | `GET /users/me` |
| POST | 创建 / 非幂等动作 | ❌ | `POST /register`、`POST /messages/:id/recall` |
| PUT | 全量更新 | ✅ | `PUT /users/me` |
| PATCH | 部分更新 | 视实现 | （未用，统一用 PUT+指针） |
| DELETE | 删除 | ✅ | `DELETE /friends/:id` |

**注意**：`POST /messages/:id/recall` 这种「动作型」接口，REST 里没有标准动词，
用 `POST + 子路径` 是社区通用做法。

## 三、状态码 vs 业务 code

**两种流派**：

| 流派 | 做法 | 优点 |
|---|---|---|
| 纯 HTTP 状态码 | 200/400/401/403/404/500 表达一切 | 标准、网关友好 |
| 全部 200 + body code | body 里 `code` 表达业务结果 | 前端统一处理 |

**本项目采用混合**：HTTP 状态码表达「协议层结果」，body 里的 `code` 表达业务结果。

```json
// 成功
HTTP 200
{"code": 0, "message": "ok", "data": {...}}

// 业务失败（参数错、重复注册）
HTTP 400
{"code": 400, "message": "用户名已存在"}

// 未登录
HTTP 401
{"code": 401, "message": "未登录或登录已过期"}

// 系统错误
HTTP 500
{"code": 500, "message": "服务器内部错误"}
```

**约定**：`code = 0` 表示成功，非 0 表示失败。

## 四、统一响应封装

```go
func OK(c *gin.Context, data any) {
    c.JSON(http.StatusOK, gin.H{"code": 0, "message": "ok", "data": data})
}

func Fail(c *gin.Context, status int, msg string) {
    c.JSON(status, gin.H{"code": status, "message": msg})
}
```

**好处**：前端只写一套解析逻辑，不用每个接口判断字段。

## 五、参数校验

```go
type registerReq struct {
    Username string `json:"username" binding:"required,min=3,max=32"`
    Password string `json:"password" binding:"required,min=6,max=64"`
    Nickname string `json:"nickname" binding:"required,max=32"`
}
```

**校验放在 handler**（协议层职责），业务规则放 service：

| 层 | 校验什么 |
|---|---|
| handler | 必填、格式、长度（`binding` tag） |
| service | 业务规则（用户名重复、是否好友、是否群主） |

**为什么**：格式校验是「接口契约」，业务规则是「领域知识」，职责不同。

## 六、分页规范

### 两种分页

| 方式 | 参数 | 优点 | 缺点 |
|---|---|---|---|
| 页码分页 | `page=1&size=20` | 能跳页 | 深翻页慢、数据变动会错位 |
| **游标分页** | `before_id=123&limit=20` | 稳定、快 | 不能跳页 |

**本项目消息用游标**（因为消息是持续追加的流）：

```
GET /conversations/1/messages?before_id=100&limit=30
```

响应：

```json
{
  "code": 0,
  "data": {
    "messages": [...],
    "has_more": true
  }
}
```

### 前端怎么用

```js
// 首次加载：不带 before_id
const first = await api.listMessages(convId, 0, 30);
// 上翻加载更多：带上一页最旧的 id
const older = await api.listMessages(convId, first.messages[0].id, 30);
```

## 七、幂等设计

**问题**：网络重试、用户连点、MQ 重复投递都会产生重复请求。

| 场景 | 幂等手段 |
|---|---|
| 发消息 | `client_msg_id` + 唯一索引 |
| 创建订单 | `Idempotency-Key` header + 去重表 |
| 接受好友申请 | 条件更新 `WHERE status=0` |
| 撤回消息 | 条件更新 `WHERE status=1` |

```go
// 客户端生成唯一 id
const clientMsgID = uid()
// 服务端唯一索引兜底
UNIQUE (sender_id, client_msg_id)
```

## 八、错误码设计

小项目用「HTTP 状态码 + message」够用；大项目需要**业务错误码表**：

| code | 含义 | HTTP |
|---|---|---|
| 0 | 成功 | 200 |
| 10001 | 用户名已存在 | 400 |
| 10002 | 用户名或密码错误 | 400 |
| 20001 | 好友申请已存在 | 400 |
| 20002 | 不是好友关系 | 403 |
| 30001 | 不是群成员 | 403 |
| 30002 | 只有群主可以操作 | 403 |

**为什么需要**：前端要根据 code 做不同处理（弹窗/跳转/提示），靠 message 不可靠（会被改）。

## 九、鉴权与安全

```
Authorization: Bearer <access_token>
```

| 注意 | 说明 |
|---|---|
| 401 vs 403 | 401 未认证；403 已认证但无权限 |
| 不返回敏感字段 | `PasswordHash`、`DeletedAt` 不出现在响应 |
| 不在 URL 放敏感信息 | token 不要放 query（日志会记录） |
| 限流 | 登录/注册接口必须限流 |
| 错误信息不泄露内部细节 | 不要把 SQL 错误原样返回 |

## 十、反例清单

| 反例 | 问题 |
|---|---|
| `GET /deleteUser?id=1` | 用 GET 做写操作 |
| 全部返回 200，错误放 message | 网关/监控无法区分 |
| 分页用 `offset` 深翻 | 慢 |
| 接口返回整个 model | 泄露密码字段 |
| 错误直接返回 `err.Error()` | 泄露 SQL/内部结构 |
| URL 用驼峰 `getUserInfo` | 风格不统一 |
| 无版本号 | 无法平滑升级 |
