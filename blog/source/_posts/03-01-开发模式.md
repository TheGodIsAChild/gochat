> 「模式」不是背概念，而是**遇到某类问题时，前人验证过的解法**。
> 本文只讲本项目真正用到的 8 种，每种都给 Go 代码和「什么时候该用」。

## 一、分层模式（Layered Architecture）

```
handler → service → repository/model → db
```

**规则**：依赖只能单向向下。

```go
// handler 只做协议转换
func Register(c *gin.Context) {
    var req registerReq
    if err := c.ShouldBindJSON(&req); err != nil { resp.Fail(...); return }
    u, err := userservice.UserRegister(req.Username, ...)   // 调 service
    ...
}
```

| 优点 | 缺点 |
|---|---|
| 各层可替换、可测试 | 层多时样板代码多 |
| 换框架只改 handler | 简单 CRUD 会显得啰嗦 |

> 什么时候用：**几乎所有业务后端**。什么时候不该用：极简单的脚本/工具。

## 二、Service 层（业务逻辑集中地）

**问题**：如果业务逻辑写在 handler 里，gRPC/定时任务/CLI 都需要复制一份。

```go
// ✅ service 只接收普通参数和 context，不依赖 gin
func UserRegister(username, password, nickname string) (*usermodel.User, error)
```

**判断标准**：`import "github.com/gin-gonic/gin"` 出现在 service 里 = 分层被破坏。

## 三、Repository 模式

**目的**：把「数据访问」和「业务逻辑」隔开，业务不关心是 MySQL 还是 Redis。

本项目是**轻量版**：直接用 `global.DB` + model（没有独立 repository 层）。

```go
// 轻量版：service 里直接写查询
global.DB.Model(&User{}).Where("username = ?", username).Count(&count)
```

**什么时候引入完整 Repository**：

- 同一实体有多种存储（MySQL + 缓存）
- 需要 mock 数据库做单测
- 团队规模大，需要明确职责边界

**权衡**：Repository 会让代码多一层；本项目为了「初学者能读懂」选择了轻量版。

## 四、依赖注入 vs 全局变量

```go
// ❌ 全局变量（本项目当前做法，简单但有耦合）
global.DB.Create(&user)

// ✅ 构造函数注入（可测试、依赖显式）
type UserService struct{ db *gorm.DB }
func NewUserService(db *gorm.DB) *UserService { return &UserService{db: db} }
```

| 方式 | 优点 | 缺点 |
|---|---|---|
| 全局变量 | 少写代码、初学易懂 | 难 mock、隐式依赖、测试困难 |
| 构造函数注入 | 显式依赖、易测试 | 样板代码多，需要 wire/fx 等工具 |

> 面试常问：「你的项目为什么用全局 DB？」→ 诚实回答：演示项目追求可读性，生产建议注入。

## 五、Functional Options（函数式选项）

**问题**：配置项多的时候，构造函数参数爆炸。

```go
// ❌ 参数越来越多
func NewServer(addr string, timeout int, debug bool, tls bool, ...)

// ✅ 选项模式
type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }

func NewServer(addr string, opts ...Option) *Server {
    s := &Server{addr: addr, timeout: 30 * time.Second}
    for _, o := range opts { o(s) }
    return s
}

// 使用
srv := NewServer(":8080", WithTimeout(10*time.Second))
```

**Go 生态里到处都是**：`gorm.Open(dsn, &gorm.Config{})`、`redis.NewClient(&redis.Options{})`、`grpc.NewServer(opts...)`。

## 六、中间件链（责任链 + 装饰器）

```go
r := gin.Default()                                   // Logger + Recovery
priv := r.Group("/api/v1", middleware.Auth())        // 鉴权
authGroup := r.Group("/api/v1", middleware.RateLimit(20, time.Minute))  // 限流
```

**执行顺序**：注册顺序 = 执行顺序，`c.Next()` 前是「进入」，后是「返回」。

```go
func Auth() gin.HandlerFunc {
    return func(c *gin.Context) {
        // 进入时：校验 token
        if invalid { c.AbortWithStatusJSON(401, ...); return }
        c.Set(CtxUserID, uid)
        c.Next()          // 交给下一个中间件/handler
        // 返回时可以做事（如统计耗时）
    }
}
```

**其他典型中间件**：CORS、请求日志、panic 恢复、链路追踪、压缩、超时。

## 七、事件驱动（Event-Driven）

**问题**：发消息后要通知很多人，同步做会拖慢请求。

```go
// 业务事务里：只写「事件记录」
tx.Create(&message)
outbox.Enqueue(tx, mqmodel.EventMessageCreated, payload)

// 后台 worker：轮询 → 发 MQ → 消费者推送
```

| 优点 | 缺点 |
|---|---|
| 解耦、削峰、可重试 | 最终一致（有延迟） |
| 生产者不关心消费者 | 需要处理幂等/顺序 |

**关键概念**：最终一致性、至少一次投递、幂等消费、死信队列。

## 八、状态机模式（State Machine）

**问题**：通话有 6 个状态，不能随便跳（如「已结束」不能再「接听」）。

```go
type CallStatus int
const (
    CallStatusCalling  CallStatus = 1
    CallStatusAccepted CallStatus = 2
    CallStatusRejected CallStatus = 3
    CallStatusCanceled CallStatus = 4
    CallStatusEnded    CallStatus = 5
    CallStatusMissed   CallStatus = 6
)

// 状态迁移用「条件更新」表达：只有当前状态允许才迁移
res := tx.Model(&Call{}).
    Where("id = ? AND status = ?", callID, CallStatusCalling).
    Update("status", CallStatusAccepted)
if res.RowsAffected == 0 { return errors.New("状态不允许此操作") }
```

**为什么不用 if 判断再 update**：并发下「判断」和「更新」之间会被插队，条件更新是原子的。

## 九、DTO / VO：请求和响应结构体

```go
// 请求 DTO：只包含客户端能传的字段
type registerReq struct {
    Username string `json:"username" binding:"required,min=3,max=32"`
    Password string `json:"password" binding:"required,min=6"`
}

// 响应 VO：绝不包含密码哈希
type UserProfile struct {
    ID       uint64 `json:"id"`
    Username string `json:"username"`
    Nickname string `json:"nickname"`
    Avatar   string `json:"avatar"`
    // PasswordHash 故意没有这个字段
}
```

**为什么不直接返回 model**：model 有 `PasswordHash`、`DeletedAt` 等不该暴露的字段；
DTO/VO 还能做字段裁剪、格式转换（时间戳→字符串）。

## 十、模式选择速查

| 你的问题 | 用哪个模式 |
|---|---|
| 业务逻辑放哪 | Service 层 |
| 换存储/换框架 | Repository / 分层 |
| 配置项多 | Functional Options |
| 横切逻辑（鉴权/日志/限流） | 中间件 |
| 异步、解耦 | 事件驱动 + Outbox |
| 状态不能乱跳 | 状态机 + 条件更新 |
| 接口字段裁剪 | DTO/VO |
| 依赖难测试 | 依赖注入 |
